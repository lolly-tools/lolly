## What the package does

It unpacks a prebuilt web build (`shells/web/dist` from the Lolly repository, with the neutral "lolly-start" brand and the English documentation) into the install directory and serves it with nginx. There is no application service or database. YunoHost stores the package settings on the server; users' work stays on their devices.

## Who can reach it

Access is the standard YunoHost permission on the app (`lolly.main`). The default is public (`visitors`), which matches how Lolly is normally offered: everyone who opens it works on their own device. Restrict it to a group if the domain should stay private to your users. Lolly itself has no accounts and no SSO login, so there is nothing to map users to.

## Your own brand

Open the app, then **Brand** in the sidebar: import design tokens (DTCG, Tokens Studio or Penpot exports) or build the palette, type and logos in place. The brand lives in the browser that made it. To hand the same brand to other people, export it as a `.lolly` file from the brand room and share that file; recipients add it from the same screen.

A governed, server-side brand for a whole team is what the separate **Lolly Work** package does, on top of this app.

## Headers and content policy

The nginx configuration ships the same default `Content-Security-Policy` as the hosted lolly.tools deployment. It is in `/etc/nginx/conf.d/<domain>.d/lolly.headers.inc`. This file is generated by the package; direct edits are replaced on upgrade. The app shell at `/any-site/` gets a second policy, `lolly.any-site.inc`, which differs only in `frame-src`: a person who turns on **Allow pages from any site** in their profile reloads there so Design can show pages from any https site. Your extra storage origins apply to both files. If your YunoHost portal lives on a different domain than the app, the portal overlay button may not load on Lolly pages, because the policy does not allow connections to that domain; the app is unaffected.

### Allow your own Nextcloud, WebDAV or S3 server

In YunoHost, open **Apps → Lolly → Configuration → Browser storage connections** and set **Additional storage origins**. You can also set it from the command line:

```bash
sudo yunohost app config set lolly main.storage.csp_extra_connect_src \
  --value 'https://cloud.example.org https://storage.example.org:8443'
```

Enter HTTPS origins separated by spaces. Each entry is a hostname with an optional port, not the full WebDAV folder URL. A trailing slash is accepted and removed. Paths, credentials, wildcards, other schemes and CSP directives are refused. Use the ASCII (punycode) spelling for international domain names. The list is limited to 4096 characters.

Saving checks and reloads nginx immediately. The saved `csp_extra_connect_src` app setting survives upgrades, backup/restore and domain changes, and extends only `connect-src`. With an empty setting, the default policy is unchanged. To remove your additions:

```bash
sudo yunohost app config set lolly main.storage.csp_extra_connect_src --value ''
```

Reload the Lolly page after changing the setting. The storage server must separately allow the Lolly site's origin through CORS, including preflight requests, the WebDAV methods and authorization headers it uses, and access to the `ETag` and `Last-Modified` response headers. Allowing a host in Lolly's CSP does not configure CORS on that host. After changing Lolly's domain, update that server's CORS rule too.

## Keep the on-device models on this server

By default browsers fetch the on-device AI models (background removal, upscaling, speech, depth and the rest) from the project's release host, `lolli.li`, the first time a tool needs them. A server that must not depend on that host can hold its own copy.

```bash
sudo yunohost app config set lolly main.models.models_source --value local
```

The change fetches every file in the release's model manifest into the app's data directory, checks its size and sha256 against the manifest and only then switches nginx. The download is several GB, so run it from the command line rather than the web admin, and make sure the data disk has room. A run that stops can be started again: verified files are skipped. Until every file checks out, the app keeps using `lolli.li`.

With this server selected:

- nginx serves `/models/` from `/home/yunohost.app/lolly/models/` with range support, strong `ETag` values and the same security headers as the rest of the app. Files in hash-named folders are cached as immutable.
- The content policy no longer lists `lolli.li` in `connect-src`, so the browser cannot reach that host from Lolly.
- The browser still checks the size and sha256 of every model it downloads, whichever host answered.
- The model files are rebuildable, so they are not in the YunoHost backup. A restore fetches them again.
- An upgrade fetches only the files the new manifest adds.

To go back, set the value to `lolli`. The data directory keeps the files until the app is removed.

How it works: the web build asks its own origin for `/models-base.txt` at startup. An empty answer means "use this server"; a 404 keeps the built-in host. The package needs a release whose build includes that probe and a `models-manifest.json`. Older releases ignore the setting.

## Upgrades

`yunohost app upgrade lolly` replaces the build whole. Browsers pick up the new build on the next load (the app shell is never cached), and the offline service worker refreshes itself.
