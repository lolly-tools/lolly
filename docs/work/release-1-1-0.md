Engine and core versions describe their own contracts. They are not reset to the
product version. Lolly's private workspace package version is also separate from
the desktop product version. `engine-pin.json` carries the exact Lolly origin,
packed content hashes and schema hashes; `content-resolver-pin.json` carries the

The Work server consumes that unmodified engine and core. The Chromium worker is
a separate image qualified with the same signed Lolly shell and catalog.
The release workflow published both server and worker tags as 1.1.0;
the chart uses that application version for both default image tags and the
migration Job. Production installations should select the qualified immutable
digests. The worker remains optional and disabled by default.

## Prepare and qualify

Use clean isolated source checkouts and preserve the existing deployment's data,
configuration, keys, pin and rollback artifacts. From the final committed Lolly
source, refresh Work with the maintained producers:

```text
node scripts/vendor-content-resolver.ts --write
pnpm run repin-engine --apply
pnpm run verify:engine-pin
pnpm run typecheck
```

The committed `vendor/lolly` checkout must be the exact release source. Re-pinning
packs its actual engine/core/schema bytes, updates the lockfile and runs its
coherence and local test gates. Do not edit the resulting hashes or patch vendor
source. A local test skip is not qualification for the skipped component.

Before a version tag or image publication, require ordinary CI on the exact
final Work commit and the exact Lolly source. Require the native server image
checks and the actual Chromium worker checks with the matched signed shell,
including real SVG/PNG rendering, cancellation and egress controls. Preserve
the original workflow, source, archive, image and pin receipts. The tagged
server and worker must come from that same Work commit. Neither an older
qualified tuple nor a successful metadata-only rehearsal admits these images.

Generic installers remain supported for their own targets. Existing production
instances follow their current authority handoff and guarded cohort publication
route. Preserve immutable pin, pack, shell and configuration identities, complete
owner and storage guards, and actual runtime acceptance before switching them.
Never mount an active asset volume into a staging Pod.

## YunoHost packaging

`1.1.0~ynh3` is the current beta test candidate for the engine 1.259 cohort. It pairs
Work runtime source `464ac88d4498b00985dfbcdb47dd96655425f426` with the genuine
signed neutral Lolly build of source
`0359d8106bccbd1da56b5552605199f0bf705472`. The web archive is published at
`https://lolli.li/lolly-web-1.1.0-ynh3.tar.gz`, with full SHA-256
`8bc8121a68e6fee6dda3902ed48d5e2669353bcfd101ca3822990235a2099376`.
It was built with models base `https://lolli.li`; model bodies are excluded.
Its complete archive bytes, included-file hashes, signed P256 catalog and decoded
gzip copies passed local checks, and its published HTTPS bytes were verified.
These checks establish the artifact, rather than a YunoHost installation.

The published [Work archive](https://lolli.li/lolly-work-1.1.0-ynh3.tar.gz) is
11,889,092 bytes with SHA-256
`e7b70e269b261bfed4bc5f7c6dce69eec84885ce2b0bf9335143a1cc3ff2efbb`.
It was cut from clean packaging source
`9ba7104377f6aa3102053fb26e407fa67463d336` using the maintained producer.
That source adds release documentation and excluded deployment
metadata to the qualified runtime source; its installed server, engine, console,
lockfile and other runtime files remain literal. The original producer command was:

```text
node scripts/yunohost-release.ts --ynh-rev 3 --shell-url https://lolli.li/lolly-web-1.1.0-ynh3.tar.gz --shell-sha256 8bc8121a68e6fee6dda3902ed48d5e2669353bcfd101ca3822990235a2099376 --out ABS_NEW_ARTIFACT_DIRECTORY
```

The producer uses the held Git tree with a fixed UTC timestamp of one second
after epoch, canonical file permissions and deterministic gzip. Each packaging
revision uses a distinct archive name, and an existing output is refused. The
adjacent `.source.json` records the actual commit, tree, archive size, full
checksum and shell pin; it does not assert runtime compatibility. Review and
commit the generated manifest, then recut into a separate directory and require
full archive byte equality. Deployment metadata is excluded from the archive,
so that manifest commit preserves the checksum. Release documentation is
included and must be recorded as an explicit source change.
Reproducing those archive bytes requires the original packaging source. A new
cut, including this documentation update, requires a new revision and filename;
never replace the published `ynh3` archives or hand-edit their pins.

After both immutable archives are published and the package directory is mirrored,
run `.github/workflows/yunohost-runtime.yml` with the reviewed full 40-character
mirror commit and exact version `1.1.0~ynh3`; the command is documented in
[the package README](../deploy/yunohost/README.md). It uses a fresh Ubuntu runner
and the official Incus checker on `amd64` Debian Bookworm, requiring successful
root and multiple-instance installation, upgrade, backup/restore and URL-change
results. The package also tests upgrading from mirror commit
`db60f651fbeb561e4b330a1dd44bd4aaf463e635` (`0.2.0~ynh1`).

The actual [runtime run](https://github.com/lolly-tools/lolly-work/actions/runs/38284099878)
used mirror commit `583cdc4af5322e683991a548428859b79084db2d` on amd64 Debian
Bookworm with YunoHost 12.1.41.2. Six current-package checks passed: root installation

The complete seven-check run failed while preparing the historical `0.2.0~ynh1`

For a fresh beta installation, use the exact reviewed package:

## Migration and recovery

This preparation adds no SQL migration. The maintained migration history contains56 files
through `0066_catalog_delivery_sequence.sql`. Before upgrading, verify the actual
database migration history with `pnpm run migrate:status`, take a fresh verified backup and
complete an independent restore. Apply the maintained migration runner or the
reviewed chart migration Job only against the selected instance. Preserve the
generation and sequence tables and do not reset their rows to make an old
catalog appear current.

Retain the previously accepted server and worker digests, shell and pack roots,
public key pin, configuration generation, owning Deployment specification and
recovery receipts. If a new cohort fails acceptance, use its reviewed inverse
application patch. A successful inverse patch still requires runtime observation.
Do not delete active or rollback volumes or automatically undo database changes.
Database restoration is a separately reviewed recovery operation. The replica
and room-routing limits, permissions and instance credentials remain unchanged.
