# S3-compatible bucket (kind: `s3`)

No app registration and no Lolly-side config: the USER brings their own
bucket in /profile → Connected services. Works with AWS S3, MinIO, Cloudflare
R2, Backblaze B2, Garage - anything speaking SigV4. Keys are stored on the
device only (never in backups; wiped by Disconnect and Clear-all), and every
upload is a browser-signed `PUT` straight to the bucket - path-style
addressing, real payload hash, no SDK.

## What the bucket owner sets up (once)

1. A **dedicated access key** limited to the target bucket/prefix, never a
   root key. For sending exports only, write rights are enough (AWS: an IAM
   user with `s3:PutObject` on `arn:aws:s3:::<bucket>/<prefix>*`; MinIO/R2: a
   scoped API token). **Device sync** also reads: add `s3:GetObject` on the
   same resource.
2. **CORS on the bucket**, for the web app only (the desktop and mobile apps
   do not need it, see 3). Allow the deploy origin; methods `GET`, `PUT` and
   `HEAD`; the headers `authorization`, `content-type`,
   `x-amz-content-sha256`, `x-amz-date`, `if-match` and `if-none-match`; and
   expose `ETag` and `Last-Modified`. AWS example:

```json
[{
  "AllowedOrigins": ["https://lolly.tools", "http://localhost:5173"],
  "AllowedMethods": ["GET", "PUT", "HEAD"],
  "AllowedHeaders": ["authorization", "content-type", "x-amz-content-sha256", "x-amz-date", "if-match", "if-none-match"],
  "ExposeHeaders": ["ETag", "Last-Modified"],
  "MaxAgeSeconds": 3000
}]
```

   Why each part matters for sync: without `GET` another device cannot
   download the synced copy; without the exposed `ETag` the app cannot tell a
   newer copy from its own; `if-match` lets the bucket itself refuse an upload
   that would overwrite a copy another device wrote a moment earlier. A bucket
   whose rule predates sync still works: the app retries once without
   `if-match`, and relies on its own check just before the upload.
3. Where it works:
   - **Web app on a hosted deploy (lolly.tools):** no. The deploy's
     `connect-src` CSP cannot list every person's bucket.
   - **Self-hosted web app:** yes, when the instance owner adds the bucket
     host to `connect-src` and the bucket has the CORS rule above.
   - **Desktop and mobile apps:** yes, with no CORS rule. Requests go through
     the apps' native request command, which accepts HTTPS endpoints on
     public addresses only. A bucket on a private address (a home network, a
     LAN-only MinIO) is refused there.
   The in-app error names the CORS / CSP case when the fetch is blocked.

## The /profile form

Endpoint URL (e.g. `https://s3.eu-central-1.amazonaws.com`, or a MinIO/R2
endpoint), region (`us-east-1` when the store does not care), bucket, key id +
secret, optional key prefix (`lolly/`), optional public base URL (only if the
bucket/CDN is public - it makes the outcome link clickable).

**Save & test** runs a signed `HEAD` on a key that should not exist:
404 = keys and CORS both work; 403 = wrong keys/region; "could not reach" =
CORS or CSP in the way.

## Share links

**Create a share link** makes a presigned GET address on the device with the
saved keys, valid for 1 to 7 days (S3's limit). Nothing is sent to make it and
it cannot be switched off before it expires. For a permanent link, set the
public base URL above instead.
