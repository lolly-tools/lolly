# データ転送: `lolly-backup`バンドル

バックアップバンドルは、Lollyがデバイス上に保持する個人ライブラリを移動します。あるインストール環境で書き出し、ファイルを運び(USB、AirDrop、自分へのメール、ネットワーク共有)、別の環境にインポートします。書き出しとインポートにサーバーは不要で、移行先はオフラインでもかまいません。

これは、バックアップに関連するシェル、ツール、スクリプトを作る人向けの形式仕様です。自分の作品を移動するには、[作品を別のデバイスに移す](/info/find-your-work.html#move-your-work-to-another-device)をご覧ください。

![インストール環境全体を移す2つのボタン: Export my dataが1つのzipを書き出し、Import dataが読み戻します](/t/url-shot?url=%2F%23%2Fsettings%3Ffocus%3Dstorage-section&width=1440&height=1800&dpi=192&waitMs=2400&css=.store-move%3Ediv%3Anth-of-type%282%29%2C.store-move%3Ep%3Alast-of-type%7Bdisplay%3Anone%7D&waitSelector=%5Bdata-store-group%3Dmove%5D&drive=click%3A%5Bdata-store-group%3Dmove%5D%3Esummary&walker=1&format=svg&cropSelector=%5Bdata-store-group%3Dmove%5D&dark=1&filename=pd-transfer-controls)

::: note 対象範囲
バンドルが運ぶのは*ユーザーデータ*で、カタログのツールではありません。カタログのツールとアセットは別に同期され、移行先にすでに存在し、バージョンが異なるとしても新しい側であることを前提とします。ユーザーが作ったツールは`profile.json`内に含まれます。インポートでカタログのツールがインストールされたり、アップグレードされたりすることはありません。
:::

## 目標

- <!--i:box--> **すべてのシェルで1つの形式。** Webアプリ、デスクトップアプリ、モバイルアプリ、将来のシェルは、同じエンベロープとパートのスキーマを共有します。任意のパートは各シェルの機能に応じて決まり、対応しないパートは報告されます。各機能ブリッジが、ストレージアダプターを提供します。
- <!--i:shieldcheck--> **転送中の破損に対応。** 転送中に破損したり途切れたりしたバンドルは、インポート時にエラーとなり、途中まで復元されることはありません。
- <!--i:clock--> **このバージョンを超えて使える。** 古いアプリは、新しいバンドルのうち認識できるパートをインポートします。互換性を壊す形式は、確実に拒否します。
- <!--i:check--> **安全にマージできる。** すでに使用中の環境にインポートしても、バンドルにないものが消去されることはありません。

## エンベロープ

バンドルは通常の`.zip`です。どの転送手段でも内容を損なわずに運べ、どの解凍ツールでも中身を確認できます。

ダウンロードの名前には所有者の名前を使います。`LollyTools-<First>-<Last>-<YYYY-MM-DD>-<n>.zip`という形式で、たとえば`LollyTools-Ada-Lovelace-2026-06-26-1.zip`です。名と姓はプロフィールから取得し、未設定なら省きます。プロフィールがなければ`LollyTools-2026-06-26-1.zip`、名だけなら`LollyTools-Ada-2026-06-26-1.zip`になります。各名前は、ファイル名として安全なトークンに変換されます(Unicodeの文字と数字を残し、空白と句読点を除去し、最大32文字)。`<n>`は日ごと、デバイスごとの連番で、同じ日に繰り返し書き出しても名前が衝突せず、順序が保たれます。`data-transfer.ts`の`backupFilename()`が名前を組み立てます。名前によってzipの内容が変わることはありません。

| パス | 必須 | 内容 |
|---|---|---|
| `manifest.json` | はい | 形式id、バージョン、件数、パートごとの整合性情報です。リーダーはこのファイルを最初に読みます。 |
| `profile.json` | 設定済みの場合 | ユーザーの`me`レコードです。名前、連絡先、顔写真の参照、フラグに加え、フォルダ、ゴミ箱、プロジェクトのひな形、ユーザーテンプレート、ユーザー作成ツール、お気に入り、非表示のツール、言語、絵文字の選択を含みます。`host.profile`経由で読み取ります。 |
| `sessions.json` | はい | すべての保存済みセッションです。スロット、ツールのidとバージョン、ラベル、サムネイル(データURL)、入力データ全体を含みます。`host.state`経由で読み取ります。 |
| `assets.json` | はい | アップロードされた各アセット(画像、フォント、ブランドトークン、ロゴ、ダウンロードの保存済みコピー)のメタデータで、それぞれ`assets/blobs/`内のバイト列を参照します。 |
| `assets/blobs/<n>.<ext>` | アセットごと | アセットの生のバイト列です。ほとんどが圧縮済みの形式なので、無圧縮で保存します。拡張子は見た目だけのもので、`assets.json`内のMIMEタイプが正式な情報です。 |
| `assets/blobs/<n>.c2pa` | 存在する場合 | 正確なバイナリのバイト列として抽出されたContent Credentialsで、アセットレコードの`_credentialFile`から参照されます。デバイスの署名鍵ではありません。 |
| `design-systems.json` | 存在する場合 | このインストール環境で作成または追加されたデザインシステムを、`{ active, records }`として保持します。[インポート規則](#import-rules)をご覧ください。 |
| `file-history.json` | 任意 | バージョン付きのアセットのスナップショット、完了したファイル操作のレポート、完全なバッチマニフェストで、独自のバージョンを持ちます。シェル内部の`fileHistory`バックアップアダプターが提供します。 |
| `revision-history.json` | 任意、手動バックアップ | 安定した作品ID、保持されたチェックポイント、サムネイル、順次更新される復元用下書きです。対応する環境では`host.state.history.backup`が提供します。 |
| `file-history/versions/` | スナップショットごと | 以前のアセットのバイト列と抽出されたクレデンシャルです。現在のアセットが存在するかどうかは問いません。 |
| `file-history/results/` | 完了した操作ごと | 正確な出力バイト列です。変換用に選ばれた元のファイルは、保持も同梱もされません。 |
| `prefs.json` | はい | ユーザーが所有するローカル設定です。`theme`、`sidebarWidth`、活動の集計`ct-metrics`を含みます。 |
| `lolly.txt` | はい | Lollyを使わずにzipを開く人向けの、読みやすいバンドルの要約(件数、プロフィール、ファイル名)です。書き出すたびに再生成され、インポート時に認識されるため、スキップされたパートとして数えられることはありません。整合性マップの後で書き込まれるため、マップはこのファイルを対象にしません。 |

::: details 書き出しでzipを作る仕組み
書き出しは、パートを1つずつzipに書き込みます(`shells/web/src/lib/zip-stream.ts`)。アップロード、保存済みの結果、保存済みのアセットのバージョンは、全体を一度に読むことなく、4 MiBずつ読み取ります。保存済みの結果とバージョンは、まず記録されたSHA-256と照合します。その後、各ファイルを読み取ってチェックサムと整合性ダイジェストを計算し、zipはその場のファイルを参照します。

何も再エンコードされません。すべてのパートは正確なバイト列とダイジェストを保つため、Content Credentialsを持つファイルは、署名の対象となるバイト列を保持します。同じパートと時刻であれば、zipは従来のメモリ内ライターによるものと同一です。ただし、16 MiBを超える履歴ファイルは分割して圧縮されます。`tests/backup-streaming.test.ts`が、記録された参照ダイジェストとの照合でこれを確認します。

Nodeで測定した192 MiBの合成ライブラリでは、バックアップの完了にライブラリとは別に約125〜150 MiBが必要でした。メモリ内ライターでは約850 MiBでした(`node scripts/bench-backup-finalise.ts`)。インポートは、引き続きzip全体をメモリに読み込みます。
:::

## `manifest.json`

```json
{
  "format": "lolly-backup",
  "formatVersion": 3,
  "minReader": 1,
  "app": "lolly",
  "exportedAt": "2026-06-22T09:30:00.000Z",
  "counts": { "profile": true, "sessions": 2, "userAssets": 4, "prefs": 3, "assetVersions": 1, "fileOperations": 1 },
  "integrity": {
    "profile.json": "sha256-…",
    "sessions.json": "sha256-…",
    "assets.json": "sha256-…",
    "assets/blobs/0.bin": "sha256-…",
    "file-history.json": "sha256-…",
    "file-history/versions/0.bin": "sha256-…",
    "file-history/results/0.bin": "sha256-…",
    "prefs.json": "sha256-…"
  }
}
```

| フィールド | 意味 |
|---|---|
| `format` | 常に`lolly-backup`です。これがないファイルは「Lollyのバックアップではありません」として拒否されます。 |
| `formatVersion` | このバンドルが**書き込まれた**ときのレイアウトです。パートの構成や形に変更があれば引き上げます。リーダーはこのフィールドで受け入れを判定**しません**。 |
| `minReader` | このバンドルを**安全に**インポートできるリーダーの最低バージョンです。リーダーはこのフィールドで受け入れを判定します。 |
| `app` | 診断用の、作成元アプリのidです。 |
| `exportedAt` | バンドルが作成された時刻のISOタイムスタンプです。 |
| `counts` | 表示と妥当性確認のための、ライターが格納した内容の件数です。 |
| `integrity` | 任意です。`manifest.json`以外の各パートを、その**非圧縮**バイト列のSRI形式の`sha256-<base64>`ダイジェストに対応付けます。 |

## バージョン方針

2つのバージョン番号により、古いインストール環境を取り残すことなく形式を拡張できます。

![バンドル形式の変更には、古いリーダーが無視できる追加的な変更と、誤ってインポートすると破損する非互換の変更がある。追加的な変更はformatVersionを上げ、minReaderを維持する。非互換の変更はformatVersionとminReaderを上げる。リーダーはminReaderが自身のバージョン以下の場合にインポートする。](/info/diagrams/concepts/backup-version-gate.svg)

- リーダーは、`manifest.minReader`が自身のリーダーバージョン以下の場合にバンドルをインポートします。バンドルがより新しいリーダーを要求する場合だけ、「より新しいバージョンのアプリが必要です」として拒否します。
- 新しい任意のパートや、マニフェストの新しい任意のフィールドなど、**追加的な**変更は、`formatVersion`を上げ、`minReader`はそのままにします。古いアプリも認識できるすべてのパートを引き続きインポートし、認識できないパートは黙って捨てずに、スキップしたものとして報告します。
- パートの誤ったインポートでデータが破損する場合や、任意のパートが必須になる場合など、**非互換の**変更は、`minReader`を上げます。古いアプリは、処理できないものをインポートせず、確実に拒否します。古いアプリはそのバンドルを確実に拒否します。
- 将来のバンドルが`formatVersion`を設定し、`minReader`を省いた場合、リーダーは`formatVersion`による判定に戻り、その変更を非互換として扱います。

::: note 作成者向けの判断基準
既存のすべてのリーダーが、追加部分を無視しても正しく動作するなら、その変更は追加的です。`formatVersion`を上げ、`minReader`はそのままにします。それ以外の場合は、`minReader`を上げます。
:::

## 整合性

`manifest.integrity`がある場合、リーダーは**何も書き込む前に**、一覧にある各パートのSHA-256を確認します。不一致(「整合性チェックに失敗」)やパートの欠落(「不完全」)があるとインポートが停止するため、部分的に復元されることはありません。これにより、途中で途切れたAirDrop、添付ファイルを再エンコードしたメールゲートウェイ、USBの不良セクターなど、転送時の破損を検出します。

整合性の確認は、可能な範囲で行われます。整合性情報は、Web Cryptoが使える環境(すべての安全なブラウザコンテキストと現行のNode)でのみ書き込まれ、マップとWeb Cryptoの両方がある場合にのみ確認されます。整合性機能がなかった頃のものなど、マップのないバンドルはそのままインポートされます。「検証できない」が「破損している」と見なされることはありません。

マニフェストには、それ自体も、再生成される`lolly.txt`も含まれません。

## インポート規則

インポートは、2つのモードのいずれかで実行されます。

- **Merge**は、**Import data…**と、同期への初回参加時の**Bring it to this device**が行う処理です。移行先のデータは残り、バンドルに含まれないものには何も変更を加えません。
- **Replace**は、デバイス同期がデバイス間の状態を揃えるために使う処理です。同期されたコピーのプロフィールレコード、設定、セッション、画像、有効なデザインシステムの選択を取り込みます。削除するのは、前回の同期以降に別のデバイスで削除された項目だけです。以前のコピーを復元する場合は、まずデバイスの状態を保存してから、そのコピーに合わせ、コピーに含まれないものをすべて削除します。利用者に見える動作は、[デバイスを同期する](/info/sync.html)で説明しています。

マージは、データの種類ごとに次のように処理します。

| データ | 移行先にすでにある場合 | バンドルにだけある場合 |
|---|---|---|
| セッション(スロット単位)とアップロードされた画像(id単位) | より新しく保存されたコピーを保持するため、古いバックアップが新しい作品を上書きすることはありません。時刻が同じか不明の場合は、移行先のコピーを保持します。 | 追加します |
| フォルダ | 移行先の名前と親を保持し、不足するバンドルのメンバーをフォルダに追加します。移行先のフォルダに入っているセッションは、そこに残ります。 | 追加します |
| お気に入り(ツール、カタログのアセット、Projectsの項目) | 統合します | 追加します |
| テンプレート、Projectsのテンプレート、ユーザーツール(id単位) | 移行先のレコードを保持します。 | 追加します |
| ゴミ箱の項目 | 移行先の項目を保持します。 | 追加するため、どちらかのインストール環境で復元できた項目は、引き続き復元できます。フォルダが移行先で再び使われている項目や、ゴミ箱のスロットが移行先ですでに使われている項目は省きます。 |
| その他のプロフィールフィールド(名前、連絡先情報、言語、機能フラグ、非表示のツール、その他の設定) | 移行先の値を保持します。 | 移行先のフィールドが空の場合に取り込みます |
| 設定(`prefs.json`) | 移行先の値を保持します。 | 移行先に値がない場合に書き込みます |
| デザインシステム(id単位) | バンドルのレコードで移行先のレコードを置き換えます。 | 追加します。バンドルの有効な選択が適用されるのは、移行先に独自のデザインシステムがない場合だけです。 |
| 作品の履歴 | より新しく保存されたコピーを現在の状態として保持し、もう一方は保護された下書きとして保持します。 | 追加します |

**保存済みセッションは、自動で画像に再リンクされます。** アセットの参照はidで保持されます。`blob:` URLは再読み込み後には使えないため、ブリッジは画像の復元後に参照を解決し直します。

**履歴レコードは、書き込まれた後は変わりません。** アセットのバージョンと操作IDを繰り返しインポートしても何も追加されず、すでに異なるバイト列や履歴を指すIDは、上書きせずに拒否されます。同一の現在のアセットを再インポートすると、そのバージョンは保持され、変更された現在のアセットは別のバージョンを持つ必要があります。

**作品の履歴には、さらにいくつかの規則があります。** 移行先で別の作品に使われているスロットを持つ作品は、別個の作品として追加され、移行先のゴミ箱にある作品はそこに残ります。チェックポイントのidが移行先で異なる内容を指す場合は、移行先のものを保持します。アーカイブが独自のチェックに失敗すると、プロフィール、セッション、アセット、設定を変更する前にインポートが停止し、同一のインポートを繰り返してもストレージ使用量は増えません。

**要約には処理結果が報告されます。** どのインポートも、`profile`、`sessions`、`userAssets`、`prefs`、`skipped`、`failedAssets`を返します。

- `failedAssets`は、デバイスのストレージがいっぱいなどの理由で復元できなかった、アップロードされたアセットを数えます。
- `skipped`は、このビルドが認識できなかった、より新しいライターのパートを数えます。アプリは件数を表示します(「… · 新しい項目をN件スキップしました」)。
- ファイルの履歴がある場合、要約には`assetVersions`、`fileOperations`、`fileBatches`、`failedHistory`が加わります。ストレージの枯渇や不変のIDの競合で復元が一部にとどまることがあり、その場合、アプリは元のバックアップを保持するように伝えます。
- 作品の履歴がある場合、このインポートで追加されたものだけを数える`revisions`と`recoveryDrafts`、各作品のマージ方法を示す`added`、`kept`、`replaced`、`copies`、`hidden`が加わります。`skippedCheckpoints`は、idが移行先で異なる内容を指すチェックポイントを数え、`historyLeftOut`は、デバイスの履歴用領域に収まらなかった古いチェックポイントや下書きを数えます。
- 置き換えインポートでは、`removed`と`failedRemovals`が加わります。

復元は、プロフィール、セッション、アセット、履歴の各ストアをまたぐ単一のトランザクションではありません。クラウド同期は、復元が一部にとどまった場合や未対応だった場合、適用済みリビジョンを先に**進めない**ため、そのコピーを使って再試行できます。

## 移行されないもの

- **カタログのキャッシュ**(ダウンロードしたアセットのメタデータとblob、ツールのインデックス)は、移行先で再同期します。
- **カタログのツールとカタログのアセット**は、移行先に存在するものとみなします。ユーザーが追加したブランドトークン、フォント、ロゴはユーザーアセットなので、移行されます。
- **`blob:`とオブジェクトURL**は、読み込み時にブリッジが再生成します。
- **変換元のファイル、実行中の実行リース、マシン固有のアクセス用または署名用のシークレット。** これらは移行可能な履歴ではありません。保存した結果はコピーです。元のソースがバックアップされたことを意味するものではありません。
- **書き出し連番カウンター**は、`localStorage`にある、ダウンロード時の命名用の日別カウンター(`lolly-export-seq`)です。`PREF_KEYS`に含めないため、バンドルで移行されることはありません。

ストレージメーターも同じ区分を表示します。Saved sessions、My images、File results & versionsはバンドルに含まれます。アセットのキャッシュ、ツールのプレビュー、オフライン用のピン留めは再構築できるため、移行されません。

## Lolly Workの組織データ

このバンドルは、デバイスの個人ライブラリをバックアップします。**Lolly Work**インスタンスのバックアップではありません。組織のアカウント、アクセスポリシー、共有プロジェクト、カタログのバージョン、承認、レンダリングジョブ、監査記録は、そのサービスが保持します。共有の作業に再びアクセスするには、再接続してサインインしてください。個人用バンドルを読み込んでも、そのアクセス権は得られません。

運用者は、Lolly Work専用のガイドである[バックアップと復元](/info/work-operations.html#backup-and-restore)と[Lolly Workのストレージとデータのライフサイクル](/info/work-data-lifecycle.html)に従って、サーバーデータをバックアップ、保持、消去します。デバイスのデータを消去したり書き出したりしても、これらのサーバー操作は行われません。

## シェル間での移行

`data-transfer.ts`は、機能ブリッジ(`host.profile`、`host.state`、`host.assets`)と共有の`localStorage`設定だけを通じて読み書きします。同じモジュールが、Web、デスクトップアプリ、モバイルアプリで、IndexedDBまたはファイルシステムのストレージを介して共通のエンベロープを読み書きします。任意の履歴パートは、そのアダプターが利用できる環境だけに含まれます。読み込みでは、未対応のパートをスキップしたと報告します。ヘッドレステストスイートは、メモリ内のブリッジを使って共通パートを検証し、履歴のトランザクションには実際のブラウザでのテストもあります。

2つのシェルは、この保証の対象外です。

- **単発実行のCLI**には移行するものがありません。状態はメモリ内にあり、1回の呼び出しの間だけ存在します。
- **TUI**は状態(セッション、フォルダ、プロフィール)を`~/.lolly`に保持します。Profileビューは、独自のより単純なバックアップアーカイブを書き出します。セッションごとの`saved-state/<slot>.json`と、`profile.json`、`folders.json`で構成され、マニフェスト、`formatVersion`、`minReader`、整合性マップはありません。この形式のリーダーは、名前が似ていても(`lolly-backup-<stamp>.zip`)、そのアーカイブを「Lollyのバックアップではない」として拒否します。両者の統一は、既知の未対応事項です。

## まだ移行できないもの

新しい種類の移行可能なデータは、後から追加パートとして組み込めます(`formatVersion`は新しくなり、`minReader`は同じままです)。デザインシステムは、すでにこの方法で、`design-systems.json`とそのユーザーアセットとして移行されます。

まだ移行されないデータのために、2つの名前が予約されています。

- **`tokens.json`**は、グループ、セット、テーマを含む[W3C DTCG](https://tr.designtokens.org/format/)のデザイントークンドキュメントを格納するためのものです。これは[Penpotが読み込みと書き出しに対応する形式](https://help.penpot.app/user-guide/design-systems/design-tokens/)です。ユーザー独自のブランドトークンは、すでに`assets.json`内の`user/tokens/brand`アセットとして移行され、デザインシステムのトークンはそのレコードとともに移行されます。
- **`penpot/`**は、取り込んだPenpotファイル、またはそのうちLollyに関係する部分を、ツールとして提供するために予約されています。

## 履歴パート

2つの履歴パートは任意で、それぞれ独自のバージョンを持ちます。

::: details 作成履歴(v3)
作成履歴があるWeb版の手動バックアップには、独自の`{ version: 1, documents, revisions, recoveries }`スキーマを持つ`revision-history.json`が含まれます。保持したID、正規化された入力スナップショット、バージョンスタンプ、ラスタープレビュー、書き手ごとの個別の下書きを格納します。履歴アダプターは、現在のセッションとその先頭リビジョンを1回の読み取りトランザクションで取得し、`sessions.json`は古いリーダー向けに同じ現在のスナップショットを使います。

復元では、ペイロードのSHA-256とバイト数、識別子の一意性、ドキュメントと先頭リビジョンの関係、祖先関係、タイムスタンプ、プレビューの種類と制限を確認してから、1回のトランザクションでアーカイブを確定します。圧縮整理された親への参照は、欠けている場合があります。既存の現在の作業が、通知なく置き換えられることはありません。同じ作品が両側にある場合、現在の状態として保持されなかった側は、保護された下書きになります。

アーカイブの転送上限は384 MiBです。保持するチェックポイントを切り詰めることなく、ストレージの上限を適用します。書き出しでは、`revision-history.json`と`sessions.json`を、1回の`JSON.stringify`と同じバイト列になるよう分割して書き込むため、ファイルのテキスト全体を保持することはありません。履歴ファイルが上限を超える場合は、その時点で破棄し、以降はサイズの集計だけを続けます。その後、最も古い自動チェックポイントを除いてアーカイブを再作成し、書き出しの概要で除外した分を`checkpointsLeftOut`として数えるか、アーカイブを拒否します。

この機能を持たないシェルは、通常のセッションを復元し、履歴パートをスキップしたと報告します。ネイティブのファイルシステム履歴は、そのアダプターが永続的な履歴トランザクションを提供するまで未対応のままです。非公開のコラボに参加するゲストには、永続的な履歴も復旧アーカイブもありません。

個人用スナップショットの同期には、作成履歴を含めません。履歴のあるローカルドキュメントにスナップショットを適用すると、以前の作業状態を別の復旧用下書きとして保持し、開いているエディターの書き込みトークンを無効化します。変更不可のチェックポイントは、デバイスに残ります。これにより、スナップショットの置き換え時にローカル履歴が保護されます。同時に進んだデバイス間の履歴を統合するものではありません。

過去のアセット参照は保持されますが、レンダリングでは引き続き移行先の既存のライブラリを通じてアセットを解決します。このアーカイブは、過去のアセットの正確なバイト列や過去のツールのレンダリングを、まだ保証しません。アセットのバージョンとファイル結果のバイト列は、専用のバックアップパートで移行されます。
:::

::: details 保存済みバージョンとファイル結果(v2)
任意の履歴パートは`{ version: 2, assetVersions: [...], operations: [...], batches: [...] }`を格納し、リーダーはバッチを含まない以前のhistory-v1形式も受け付けます。各スナップショットには、安定したアセットIDと正確なバージョン、保存時刻、バイト長、16進数のSHA-256に加え、`_file`と任意の`_credentialFile`がバイナリパートを指すアセットレコードが含まれます。操作には、元ファイルの情報、リクエスト、レポート、タイムスタンプ、任意の結果`_file`が含まれます。ストレージバックエンド名、OPFSハンドル、実行リースは移行されません。history v1だけに対応するリーダーは、読み込み前に新しい履歴バージョンを拒否するため、バッチへの所属が通知なく失われることはありません。

バッチのマニフェストは、処理前に選択されたすべてのソースを記録します。読み込まれなかったファイル、キャンセルされたメンバー、結果の保存領域を確保できなかったもの、中断された作業も含まれます。各メンバーには、安定した操作ID、ソースの参照と情報、要求された出力名、最終レポートがあります。未読のソースには申告された情報があり、架空のダイジェストはありません。読み込みでは、メンバーの識別情報と、含まれている操作レポートとの整合性を検証します。個々の結果を削除してもLolly Batchのレポートは利用できますが、受領記録があることは、出力のバイト列がまだ保存されていることを意味しません。

- **検証が先です。** プロフィールやアセットの読み込みで書き込みを行う前に、既知の履歴レコード、レポート、参照ファイルをすべて検証します。エンベロープに整合性マップがなくても、バイト列の欠落やSHA-256の不一致は失敗になります。抽出したクレデンシャルはバイト配列のまま保持されます。数値キーのオブジェクトとしてシリアライズしていた古いライターからの読み込みも同様です。
- **実行中の作業。** 実行中の操作は、バックアップ内では中断されたレコードとなり、失敗レポートを持ち、結果は持ちません。復元によってバックグラウンド作業が再開されたり、有効なリースが読み込まれたりすることはありません。再試行では元ファイルを再び選択し、記録済みのSHA-256があれば照合します。
- **ストレージ。** 復元した結果は、バイト列とメタデータをIndexedDBにまとめて確定します。通常の新しい結果は、利用できる場合はOPFSを使い、そうでなければIndexedDBを使います。既存の実行中の操作が、読み込みによって置き換えられることはありません。
- **バックアップの制限。** 書き出しでは、これらのバイト列をアーカイブにストリーム出力しますが、復元では依然としてバックアップ全体をメモリ内で展開するため、上限は変わりません。**履歴ペイロードは256 MiB**、**履歴メタデータは4 MiB**、最大**100操作**、**100バッチ**、**2,000スナップショット**です。書き出しは、上限を超えた履歴や不完全な履歴を明示的に拒否し、通知なく除外することはありません。古いローカルコピーを削除する前に、重要なバージョンと結果を1つずつダウンロードしてください。これらの上限は、スマートフォンでの実測に基づくピークメモリ使用量の保証ではありません。
- **ローカルの容量枠。** ローカルの結果履歴には512 MiBの容量枠と100レコードの上限があります。アセットのスナップショットには別の512 MiBの容量枠があり、過去のバージョンはアセットごとに最大20個です。抽出したクレデンシャルのバイト列もこの容量枠に算入されます。復元はこれらの制限に従い、既存のユーザーデータを通知なく削除することはありません。
- **バッチのメタデータ。** ローカルのバッチメタデータには別の4 MiBの容量枠があり、マニフェストは最大100個、メンバーはバッチごとに最大20個です。保留中のメンバーはメタデータの容量を予約し、レポートの上限はメンバーごとに32 KiBです。これは論理的な容量枠であり、ブラウザのディスク領域を保証するものではありません。実際に割り当て容量が不足するとエラーを表示し、メモリ内のレポートは引き続きダウンロードできます。バッチのメンバーを再試行すると、古いレポートを上書きせず、新しいバッチを作成します。バッチのレコードを削除しても、個々の結果のバイト列やライブラリのアセットは削除されません。
- **ライブラリ内の結果。** 変換結果は、正規化や再エンコードをせずに、ソースと出力のハッシュ、操作との関係を付けてライブラリに追加できます。繰り返し追加した場合は変更されていないコピーを再利用し、編集済みのコピーを上書きすることはありません。ラスター画像からは、現在のライブラリアセットIDを使う新しいLolly Designドキュメントを作れます。Lolly DesignのランタイムとURLの経路全体で、正確なバージョンの固定を徹底するのは別の作業です。SVG、HTML、PDF、ZIPの結果は、内容を解釈しないファイルアセットとして保持し、信頼済みのインタラクティブコンテンツやベクターコンテンツとしては扱いません。
- **表示される場所。** **Convert → Recent file operations**には、履歴の使用量、レポート、ダウンロード、バージョンマネージャーが表示されます。バージョンマネージャーでは、削除したライブラリアセットの過去のバージョンも見つけられます。スナップショットを復元すると、新しい現在のバージョンを作成し、選んだスナップショットも保持します。**Settings → Preferences → Storage**では、結果とバージョンを、破棄可能なキャッシュとは別に集計します。
- **クリーンアップ。** 明示的な一時ファイルのクリーンアップで削除するのは、操作に属する、参照されていないバイト列だけです。現在のレコードがそのファイルを保護し、新しいOPFSファイルには1時間の猶予期間があります。保存済みの結果とアセットのスナップショットは、自動では消去されません。

古いリーダーも引き続きv2のエンベロープ(`minReader: 1`)を受け付け、対応するパートを復元し、未対応の履歴パートはスキップしたものとして数えます。履歴全体の復旧には、`fileHistory`アダプターを備えたシェルが必要です。これはシェル内部の接続点であり、ツール向けの`HostV1`機能ではありません。実際の2デバイス間の復元は、ローカルのChromium検証ゲートで確認しています。インストール済みのデスクトップ、iOS、Androidアプリでの復旧は、まだ個別の受け入れ検証が必要です。
:::

## リファレンス

- モジュール: `shells/web/src/data-transfer.ts` (`exportBackup`、`importBackup`、`BACKUP_FORMAT`、`BACKUP_FORMAT_VERSION`、`BACKUP_READER_VERSION`。命名用の`backupFilename()`は内部用です)。
- 契約テスト: `tests/data-transfer.test.ts`。往復、マージ、整合性、前方互換性、リーダーのゲートを検証します。
- 履歴の契約テスト: `tests/file-history-backup.test.ts`、`tests/file-batch-history.test.ts`、`tests/file-result-library.test.ts`。ブラウザでの受け入れ検証: `tests/file-history.browser.test.ts`、`tests/file-batch-history.browser.test.ts`、`tests/file-result-reuse.browser.test.ts`。
- 使用するブリッジのインターフェース: `host.profile`、`host.state`、`host.assets`。[Host API](/info/host-api.html)をご覧ください。
