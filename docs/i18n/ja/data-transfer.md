# データ移行: `lolly-backup`バンドル

Lollyは、個人のライブラリをデバイス上に保持します。バックアップバンドルは、そのライブラリを移す方法です。あるインストールで書き出し、そのファイルを好きな方法(USB、AirDrop、自分宛てのメール、ネットワーク共有)で運び、別のインストールでインポートします。書き出しにもインポートにもサーバーは不要で、移行先はオフラインでも構いません。

このページは、バックアップに関するシェル、ツール、スクリプトを作る人向けの形式仕様です。zipの中身、バージョンの管理方法、インポートでのマージの仕方、検査される内容を説明します。ご自身の作業を移す人向けの手順は[作品を別のデバイスに移す](/info/find-your-work.html#move-your-work-to-another-device)です。

![インストール全体を移す2つのボタン: Export my dataは1つのzipを書き出し、Import dataはそれを読み戻す](/t/url-shot?url=%2F%23%2Fsettings%3Ffocus%3Dstorage-section&width=1440&height=1800&dpi=192&waitMs=2400&css=.store-move%3Ediv%3Anth-of-type%282%29%2C.store-move%3Ep%3Alast-of-type%7Bdisplay%3Anone%7D&waitSelector=%5Bdata-store-group%3Dmove%5D&drive=click%3A%5Bdata-store-group%3Dmove%5D%3Esummary&walker=1&format=svg&cropSelector=%5Bdata-store-group%3Dmove%5D&dark=1&filename=pd-transfer-controls)

> **範囲。** バンドルが運ぶのは*ユーザーデータ*であり、カタログのツールではありません。カタログのツールとカタログのアセットは別に同期され、移行先にすでに存在すると想定されます(最悪でもより高いバージョンで)。ユーザーが自分で作ったツールは`profile.json`の中で運ばれます。インポートでカタログのツールがインストールやアップグレードされることはありません。

## 目標

- <!--i:box--> **1つの形式、すべてのシェル。** Webアプリ、デスクトップアプリ、モバイルアプリ、将来のシェルは、同じエンベロープとパートのスキーマを共有します。任意のパートは各シェルのケイパビリティに依存し、非対応のパートは報告されます。各ケイパビリティブリッジが、独自のストレージアダプターを提供します。
- <!--i:shieldcheck--> **移動に耐える。** 転送中に壊れたり切り詰められたりしたバンドルは、インポート時にはっきり失敗し、中途半端に復元されることはありません。
- <!--i:clock--> **このバージョンより長く生きる。** 古いアプリでも、新しいバンドルのうち、認識できるパートはインポートできます。本当に互換性を壊す形式は、きれいに拒否されます。
- <!--i:check--> **安全にマージできる。** すでに使われているインストールにインポートしても、バンドルになかったものが消去されることはありません。

## エンベロープ

バンドルは通常の`.zip`なので、どんな転送でもそのまま届き、どのunzipツールでも中身を確認できます。

ダウンロードは、所有者にちなんで`LollyTools-<First>-<Last>-<YYYY-MM-DD>-<n>.zip`と名付けられます。たとえば`LollyTools-Ada-Lovelace-2026-06-26-1.zip`で、バックアップが並ぶダウンロードフォルダも読みやすいままです。姓と名はプロフィールから取られ、未設定の場合は省かれます。プロフィールがなければ`LollyTools-2026-06-26-1.zip`、名だけなら`LollyTools-Ada-2026-06-26-1.zip`になります。各名前は、ファイル名として安全なトークン(Unicodeの文字と数字は保持され、スペースと句読点は取り除かれ、最大32文字)に縮められます。`<n>`は、デバイスごと、日ごとの連番なので、同じ日に繰り返し書き出しても衝突せず、順序も保たれます。名前は`data-transfer.ts`の`backupFilename()`が作り、zipの中身は名前にかかわらず同じです。

| パス | 必須 | 内容 |
|---|---|---|
| `manifest.json` | はい | 形式ID、バージョン、件数、パートごとの整合性。リーダーが最初に見るもの。 |
| `profile.json` | 設定されている場合 | ユーザーの`me`レコード全体: 名前、連絡先、顔写真の参照とフラグ、さらにフォルダ、ごみ箱、プロジェクトのブループリント、ユーザーテンプレート、ユーザー作成のツール、お気に入り、非表示のツール、言語、絵文字の選択。`host.profile`経由で読み取る。 |
| `sessions.json` | はい | 保存済みのすべてのセッション: スロット、ツールIDとバージョン、ラベル、サムネイル(データURL)、入力データの全体。`host.state`経由で読み取る。 |
| `assets.json` | はい | アップロードした各アセット(画像、フォント、ブランドトークン、ロゴ、ダウンロードの保存コピー)のメタデータ。それぞれ`assets/blobs/`の下のバイト列を指す。 |
| `assets/blobs/<n>.<ext>` | アセットごと | 生のアセットのバイト列。ほとんどが圧縮済みの形式なので、非圧縮で保存される。拡張子は見た目だけのもので、`assets.json`のMIMEタイプが正式。 |
| `assets/blobs/<n>.c2pa` | ある場合 | 抽出されたContent Credentialsの、正確なバイナリのバイト列。アセットレコードの`_credentialFile`で参照される。これらはデバイスの署名鍵ではない。 |
| `design-systems.json` | ある場合 | このインストールで作成または追加されたデザインシステムを`{ active, records }`として保持。[インポートのルール](#import-rules)をご覧ください。 |
| `file-history.json` | 任意 | バージョン付きのアセットのスナップショット、完了したファイル操作のレポート、完全なバッチのマニフェスト。独自のバージョンを持つ。シェルの内部`fileHistory`バックアップアダプターが提供する。 |
| `revision-history.json` | 任意、手動バックアップ | 安定した作品ID、保持されたチェックポイント、サムネイル、ローリングの復旧用ドラフト。対応する環境では`host.state.history.backup`が提供する。 |
| `file-history/versions/` | スナップショットごと | 以前のアセットのバイト列と抽出されたクレデンシャル。現在のアセットがまだ存在するかどうかにかかわらない。 |
| `file-history/results/` | 完了した操作ごと | 出力の正確なバイト列。変換のために選択された元のファイルは保持も含めもされない。 |
| `prefs.json` | はい | ユーザー固有のローカル設定: `theme`、`sidebarWidth`、`ct-metrics`の活動集計。 |
| `lolly.txt` | はい | Lollyなしでzipを開く人のための、バンドルの読みやすい要約(件数、プロフィール、ファイル名)。書き出しのたびに再生成され、インポート時に認識されるため、スキップされたパートとして数えられることはない。整合性マップの後に書かれるため、マップはこのファイルをカバーしない。 |

::: details 書き出しがzipを書く方法
書き出しは、zipを1パートずつ書きます(`shells/web/src/lib/zip-stream.ts`)。アップロード、保存した結果、保存したアセットのバージョンは、全体ではなく4 MiBずつのスライスで読み込まれ、保存した結果とバージョンは、先に記録されたSHA-256と照合されます。その後、すべてのファイルがチェックサムと整合性ダイジェストのために読まれ、zipはそれをその場所で参照します。

何も再エンコードされないため、Content Credentialsを持つファイルは署名が対象とするバイト列をそのまま保ち、すべてのパートが正確なバイト列とダイジェストを保ちます。同じパートと時刻であれば、zipは以前のメモリ内ライターが作るものと同一ですが、16 MiBを超える履歴ファイルは分割して圧縮されます。`tests/backup-streaming.test.ts`が、記録された基準ダイジェストに対してこれを確認します。

192 MiBの合成ライブラリでNode上で測定したところ、バックアップの完了には、ライブラリに加えて約125〜150 MiBが必要で、メモリ内ライターの約850 MiBと比べて少なく済みました(`node scripts/bench-backup-finalise.ts`)。インポートは、今もzip全体をメモリに読み込みます。
:::

## `manifest.json`

```json
{
  "format": "lolly-backup",
  "formatVersion": 3,
  "minReader": 1,
  "app": "lolly",
  "exportedAt": "2026-06-22T09:30:00.000Z",
  "counts": { "profile": true, "sessions": 2, "userAssets": 4, "prefs": 3, "assetVersions": 1, "fileOperations": 1 },
  "integrity": {
    "profile.json": "sha256-…",
    "sessions.json": "sha256-…",
    "assets.json": "sha256-…",
    "assets/blobs/0.bin": "sha256-…",
    "file-history.json": "sha256-…",
    "file-history/versions/0.bin": "sha256-…",
    "file-history/results/0.bin": "sha256-…",
    "prefs.json": "sha256-…"
  }
}
```

| フィールド | 意味 |
|---|---|
| `format` | 常に`lolly-backup`。これがないファイルは「Lollyのバックアップではない」として拒否される。 |
| `formatVersion` | このバンドルが**書き込まれた**ときのレイアウト。パート構成や形の変更のたびに上がる。リーダーはこのフィールドでは**判定しない**。 |
| `minReader` | このバンドルを**安全に**インポートできる最低限のリーダーのバージョン。リーダーが判定に使うのはこのフィールド。 |
| `app` | 診断用の、作成したアプリのID。 |
| `exportedAt` | バンドルが作成されたISOタイムスタンプ。 |
| `counts` | ライターが入れたもの。表示と健全性チェック用。 |
| `integrity` | 任意。`manifest.json`以外のすべてのパートを、その**非圧縮**のバイト列のSRI形式`sha256-<base64>`ダイジェストに対応付ける。 |

## バージョンポリシー

2つのバージョン番号により、古いインストールを置き去りにせずに形式を成長させられます。

![バンドル形式の変更は、古いリーダーが無視できる追加的なものか、誤ったインポートでデータが壊れる互換性を壊すものかのいずれか。追加的な変更はformatVersionを上げてminReaderを維持し、互換性を壊す変更はformatVersionを上げてminReaderも上げる。リーダーは、minReaderが自身のバージョン以下のときにインポートする。](/info/diagrams/concepts/backup-version-gate.svg)

- リーダーは、`manifest.minReader`が自身のリーダーバージョン以下のときにバンドルをインポートします。バンドルが新しいリーダーを要求する場合にだけ、「needs a newer version of the app」として拒否します。
- 新しい任意のパートや任意のマニフェストフィールドのような**追加的な**変更は、`formatVersion`を上げ、`minReader`はそのままにします。古いアプリでも認識できるパートはすべてインポートでき、認識できないパートは黙って破棄されず、スキップとして報告されます。
- パートの誤ったインポートでデータが壊れる、または任意のパートが必須になるような**互換性を壊す**変更は、`minReader`を上げます。すると古いアプリは、扱えないものをインポートするのではなく、きれいに拒否します。
- 将来のバンドルが`formatVersion`を設定して`minReader`を省いた場合、リーダーは`formatVersion`での判定にフォールバックし、その変更を互換性を壊すものとして扱います。

> **作者向けの目安:** 既存のすべてのリーダーが、追加分を無視しても正しく動作するなら、その変更は追加的です。`formatVersion`を上げ、`minReader`はそのままにします。そうでなければ`minReader`を上げます。

## 整合性

`manifest.integrity`がある場合、リーダーは、**何かを書き込む前に**、一覧されたパートごとのSHA-256を確認します。不一致(「failed its integrity check」)またはパートの欠落(「incomplete」)があると、インポート全体が止まるため、部分的な復元は起こりません。これは、ファイル転送が引き起こしうる破損を検出します。途中で切れたAirDrop、添付ファイルを再エンコードしたメールゲートウェイ、USBの不良セクタなどです。

整合性の確認はベストエフォートです。Web Cryptoが使える場合(すべてのセキュアなブラウザコンテキストと最新のNode)にのみ書き込まれ、マップとWeb Cryptoの両方がある場合にのみ確認されます。整合性が導入される前のものなど、マップのないバンドルはそのままインポートされます。「確認できない」が「破損」として数えられることはありません。

マニフェストは、自分自身も再生成された`lolly.txt`も一覧しません。ダイジェストは、マニフェストが保証するパートをカバーします。

## インポートのルール

インポートは、2つのモードのいずれかで実行されます。

- **Merge**は、**Import data…**が行うもので、同期の最初の参加である**Bring it to this device**も行います。移行先のデータは残り、バンドルになかったものには触れません。移行先にあってバンドルになかったセッションは、インポート後も残ります。
- **Replace**は、デバイス同期がデバイスどうしを揃えるために使うものです。同期されたコピーのプロフィールレコード、設定、セッション、画像、有効なデザインシステムの選択を取り込み、最後の同期以降に別のデバイスで削除された項目だけを取り除きます。以前のコピーに復元する場合はさらに進み、先にデバイスを保存した後、そのコピーが保持していないものをすべて取り除いて、デバイスをそのコピーに一致させます。人に何が見えるかは[デバイスを同期する](/info/sync.html)で扱っています。

マージでは、移行先にしかないものはすべて残り、バンドル内の各種類のデータは次のように移行先と照合されます。

| データ | 移行先にすでにある場合 | バンドルにだけある場合 |
|---|---|---|
| セッション(スロット別)とアップロードした画像(ID別) | より新しく保存されたコピーが残るため、古いバックアップが新しい作業を上書きすることはない。時刻が等しいか不明な場合は、移行先のコピーを残す。 | 追加される |
| フォルダ | 移行先の名前と親が維持され、フォルダはバンドルのメンバーのうち不足しているものを取り込む。移行先でフォルダに入っているセッションは、そこに入ったまま。 | 追加される |
| お気に入り(ツール、カタログのアセット、Projectsの項目) | 結合される | 追加される |
| テンプレート、Projectsのテンプレート、ユーザーのツール(ID別) | 移行先のレコードが維持される。 | 追加される |
| ごみ箱の項目 | 移行先の項目が維持される。 | 追加されるため、どちらのインストールでも復元できた項目は、引き続き復元できる。移行先でフォルダがすでに使われているか、ごみ箱のスロットがすでに使われている項目は、除外される。 |
| その他のプロフィールのフィールド(名前、連絡先、言語、機能フラグ、非表示のツール、その他の設定) | 移行先の値が維持される。 | 移行先のフィールドが空の場合に取り込まれる |
| 設定(`prefs.json`) | 移行先の値が維持される。 | 移行先にない場合に書き込まれる |
| デザインシステム(ID別) | バンドルのレコードが移行先のものを置き換える。 | 追加される。バンドルの有効な選択は、移行先に独自のデザインシステムがない場合にのみ適用される。 |
| 作品の履歴 | より新しく保存されたコピーが現在のものとして残り、もう一方は保護されたドラフトとして保持される。 | 追加される |

**保存済みセッションは、画像に自動的に再リンクされます。** アセット参照はIDで保持され、画像が復元された後でブリッジが再解決します。`blob:` URLは再読み込みを越えて残らないため、これはいずれにせよ必要です。

**履歴の記録は、書き込まれた後に変更されません。** アセットのバージョンと操作IDを繰り返しインポートしても何も追加されず、すでに別のバイト列や履歴を指しているIDは、上書きされずに拒否されます。同一の現在のアセットを再インポートしてもそのバージョンは保たれ、変更された現在のアセットは別のバージョンを持つ必要があります。

**作品の履歴には、さらにいくつかのルールがあります。** 移行先で別の作品が使っているスロットを持つ作品は、別の作品として追加され、移行先のごみ箱にある作品はそこに残ります。移行先で別の内容を指すチェックポイントIDは、移行先のものが維持されます。アーカイブが自身の検査に失敗すると、プロフィール、セッション、アセット、設定が変更される前にインポートが止まり、同一の繰り返しインポートでストレージは増えません。

**要約は、何が起こったかを報告します。** すべてのインポートは、`profile`、`sessions`、`userAssets`、`prefs`、`skipped`、`failedAssets`を返します。

- `failedAssets`は、デバイスのストレージが満杯などの理由で復元できなかったアップロード済みアセットを数えます。
- `skipped`は、より新しいライターのパートのうち、このビルドが認識しなかったものを数えます。アプリはこれを表示し(「… · N newer items skipped」)、復元が何を残したかを示します。
- ファイル履歴がある場合、要約には`assetVersions`、`fileOperations`、`fileBatches`、`failedHistory`が加わります。ストレージの枯渇や変更不可のIDの競合により、部分的な復元が起きることがあり、その場合アプリは元のバックアップを保管するよう伝えます。
- 作品の履歴がある場合、`revisions`と`recoveryDrafts`(このインポートで追加された分のみを数える)が加わり、各作品がどうマージされたかを示す`added`、`kept`、`replaced`、`copies`、`hidden`も加わります。`skippedCheckpoints`は、移行先で別の内容を指すIDのチェックポイントを数え、`historyLeftOut`は、デバイスの履歴領域に収まらなかった古いチェックポイントとドラフトを数えます。
- Replaceのインポートでは、`removed`と`failedRemovals`が加わります。

復元は、プロフィール、セッション、アセット、履歴の各ストアにわたる1つのトランザクションではありません。クラウド同期は、部分的な復元または非対応の復元の後に、適用済みのリビジョンを進めないため、そのコピーは再試行のために残ります。

## 転送されないもの

- **カタログのキャッシュ**(ダウンロードしたアセットのメタデータとブロブ、ツールのインデックス)。移行先が無料で再同期します。
- **カタログのツールとカタログのアセット**。対象外で、移行先にすでにあると想定されます。ユーザーが追加したブランドトークン、フォント、ロゴはユーザーアセットなので、運ばれます。
- **`blob:`とオブジェクトURL**。ブリッジが読み込み時に再生成します。
- **変換の元ファイル、実行中のリース、マシン固有のアクセスまたは署名の秘密情報。** これらは持ち運べる履歴ではありません。保存した結果はコピーであり、元のソースがバックアップされたという約束ではありません。
- **書き出しの連番カウンター**。`localStorage`にある、日ごとのダウンロード名のカウンター(`lolly-export-seq`)。`PREF_KEYS`の外に置かれているため、バンドルに含まれることはありません。

ストレージメーターも同じ区分を表示します。保存済みセッション、My images、File results & versionsはバンドルに入ります。その下のアセットキャッシュ、ツールのプレビュー、オフラインのピン留めは、すべて再構築できるため、含まれません。

## Lolly Workの組織データ

このバンドルは、デバイスの個人ライブラリをバックアップするものです。**Lolly Work**インスタンスのバックアップではありません。組織のアカウント、アクセスポリシー、共有プロジェクト、カタログのバージョン、承認、レンダリングジョブ、監査記録は、そのサービスが保持しています。共有作業へのアクセスを取り戻すには、再接続してサインインしてください。個人のバンドルをインポートしても、そのアクセスは付与されません。

運用者は、Lolly Work自身のガイドである[バックアップと復元](/info/work-operations.html#backup-and-restore)と[Workのストレージとデータライフサイクル](/info/work-data-lifecycle.html)に従って、サーバーデータをバックアップ、保持、消去します。デバイスを消去したり書き出したりしても、サーバー側のこれらの操作は行われません。

## シェルをまたいで

`data-transfer.ts`は、ケイパビリティブリッジ(`host.profile`、`host.state`、`host.assets`)と共有の`localStorage`設定だけを通して読み書きします。同じモジュールが、IndexedDBまたはファイルシステムのストレージ上で、Webと、デスクトップ・モバイルアプリの共通のエンベロープを読み書きします。任意の履歴パートはそのアダプターがある場所にのみ現れ、非対応のパートはインポート時にスキップとして報告されます。ヘッドレスのスイートは、メモリ内ブリッジに対して共通のパートを検証し、履歴のトランザクションには実ブラウザのテストもあります。

この保証の外にあるシェルが2つあり、それぞれ理由が異なります。

- **ワンショットのCLI**には運ぶものがありません。その状態はメモリ内にあり、1回の呼び出しのあいだだけ続きます。
- **TUI**は、状態を`~/.lolly`(セッション、フォルダ、プロフィール)に保持し、そのProfileビューでバックアップできますが、独自のより単純なアーカイブを書き出します。セッションごとの`saved-state/<slot>.json`に、`profile.json`と`folders.json`が加わり、マニフェスト、`formatVersion`、`minReader`、整合性マップはありません。この形式ではこれをインポートできず(リーダーは「not a Lolly backup」として拒否)、名前もまぎらわしいほど似ています(`lolly-backup-<stamp>.zip`)。2つの統一は既知の課題です。

## まだ持ち運べないもの

エンベロープはマニフェストと名前付きのパートで構成されるため、持ち運べるデータの新しい種類は、後から追加的なパート(新しい`formatVersion`、同じ`minReader`)として加えられ、今日のリーダーは認識できないものをスキップします。デザインシステムはすでにこの方法で運ばれ、`design-systems.json`とそのユーザーアセットとして含まれます。

まだ運ばれないデータのために、予約されている名前が2つあります。

- **`tokens.json`**は、グループ、セット、テーマを備えた[W3C DTCG](https://tr.designtokens.org/format/)デザイントークンのドキュメント全体を運びます。これは[Penpotがインポートおよびエクスポートする](https://help.penpot.app/user-guide/design-systems/design-tokens/)形式です。ユーザー自身のブランドトークンは、すでに`assets.json`内の`user/tokens/brand`アセットとして運ばれ、デザインシステムのトークンは、そのレコードとともに運ばれます。
- **`penpot/`**は、取り込まれたPenpotファイル、またはそのうちLollyに関係する部分を、ツールとして表面化するために予約されています。

今日のリーダーは、どちらの名前もまだ知りません。上記のパート以外の他のものと同様に、どちらも未知のパートとして扱われ、そのまま手を付けられず、`skipped`で数えられます。

## 履歴パート

2つの履歴パートは任意で、それぞれ独自のバージョンを持ちます。ほとんどのリーダーは、この節を読み飛ばせます。

::: details 作品の履歴 (v3)
作品の履歴を持つWebインストールからの手動バックアップには、独自の`{ version: 1, documents, revisions, recoveries }`スキーマを持つ`revision-history.json`が含まれます。保持されたID、正規の入力スナップショット、バージョンスタンプ、ラスターのプレビュー、別のライターのドラフトを運びます。履歴アダプターは、現在のセッションとそのヘッドを1回の読み取りトランザクションで取得し、`sessions.json`は古いリーダー向けに同じ現在のスナップショットを使います。

復元は、アーカイブを1つのトランザクションで確定する前に、ペイロードのSHA-256とバイト数、一意なID、ドキュメントとヘッドの関係、系譜、タイムスタンプ、プレビューの種類と制限を検査します。圧縮された親参照は、欠けていることがあります。既存の現在の作業が黙って置き換えられることはありません。作品が両側にある場合、現在のものとして残らなかった側が保護されたドラフトになります。

アーカイブの384 MiBの転送上限は明示的に検査され、ストレージの制限は保持されたチェックポイントを切り詰めずに適用されます。書き出しは、`revision-history.json`と`sessions.json`を、1回の`JSON.stringify`が返すのと同じバイト列で分割して書くため、ファイルのテキスト全体が保持されることはありません。上限を超えることになる履歴ファイルは、超えた時点で破棄され、そこから先は数えるだけになります。その後、アーカイブは最も古い自動チェックポイントを除いて作り直され、書き出しの要約はそれらを`checkpointsLeftOut`として数えるか、アーカイブ全体が拒否されます。

この機能を持たないシェルは、通常のセッションを復元し、履歴パートをスキップとして報告します。ネイティブのファイルシステム履歴は、そのアダプターが耐久性のある履歴トランザクションを提供するまで、非対応のままです。プライベートコラボのゲストには、耐久性のある履歴も復旧用アーカイブもありません。

個人用のスナップショット同期は、作品の履歴を含めません。スナップショットを履歴のあるローカルドキュメントに適用すると、以前の作業状態が別の復旧ドラフトとして保持され、開いているエディターの書き込みトークンは無効になります。変更不可のチェックポイントは、デバイス上に残ります。これはスナップショットの置き換え中にローカルの履歴を守るものであり、同時に存在する複数のデバイスの履歴をマージするものではありません。

過去のアセット参照は保持されますが、レンダリングは引き続き、移行先の既存のライブラリを通してアセットを解決します。このアーカイブは、古いアセットの正確なバイト列や、古いツールのレンダリングをまだ保証しません。アセットバージョンとファイル結果のバイト列は、独自のバックアップパートで運ばれます。
:::

::: details 保存済みバージョンとファイル結果 (v2)
任意の履歴パートは`{ version: 2, assetVersions: [...], operations: [...], batches: [...] }`を保持し、リーダーはバッチのない以前のhistory-v1の形も受け付けます。各スナップショットは、安定したアセットIDと正確なバージョン、保存時刻、バイト長、16進のSHA-256に加え、`_file`と任意の`_credentialFile`がバイナリパートを指すアセットレコードを持ちます。操作は、元のファイルの事実、リクエスト、レポート、タイムスタンプ、任意の結果`_file`を運びます。ストレージのバックエンド名、OPFSのハンドル、実行リースは運ばれません。history v1しか知らないリーダーは、バッチのメンバーを黙って落とすのではなく、インポートの前に新しい履歴バージョンを拒否します。

バッチのマニフェストは、処理の前に、選択されたすべてのソースを記録します。読み込まれなかったファイル、キャンセルされたメンバー、結果の領域を確保できなかった失敗、中断された作業を含みます。各メンバーには、安定した操作ID、ソースの参照と事実、要求された出力名、最終レポートがあります。読み込まれなかったソースには、作り物のダイジェストではなく、宣言された事実があります。インポートは、メンバーのIDと、保持されている操作レポートとの整合性を検証します。個々の結果が削除されてもバッチのレポートは残りますが、受領記録があることは、その出力のバイト列がまだ保存されていることを意味しません。

- **まず検証。** 既知のすべての履歴レコード、レポート、参照されるファイルは、プロフィールやアセットのインポートが何かを書き込む前に検証されます。欠けているバイト列とSHA-256の不一致は、エンベロープに整合性マップがなくても失敗します。抽出されたクレデンシャルは、数値キーのオブジェクトとしてシリアライズした古いライターからのインポートを含め、バイト配列のままです。
- **実行中の作業。** 実行中の操作は、バックアップでは中断されたレコードになり、説明付きの失敗レポートが付き、結果はありません。復元がバックグラウンドの作業を再開することも、アクティブなリースをインポートすることもありません。再試行するには、元のファイルをもう一度選び、可能な場合は記録されたSHA-256と照合します。
- **ストレージ。** 復元された結果は、バイト列とメタデータをIndexedDBに一緒に確定します。通常の新しい結果は、利用できる場合はOPFSを使い、IndexedDBへのフォールバックがあります。既存の実行中の操作が、インポートで置き換えられることはありません。
- **バックアップの制限。** 書き出しはこれらのバイト列をアーカイブにストリーミングしますが、復元は今もバックアップ全体をメモリ内で展開するため、制限は残ります。**履歴ペイロード256 MiB**、**履歴メタデータ4 MiB**、最大**100件の操作**、**100件のバッチ**、**2,000件のスナップショット**です。書き出しは、大きすぎる、または不完全な履歴を明示的に拒否し、黙って省くことはありません。古いローカルのコピーを削除する前に、重要なバージョンと結果を1つずつダウンロードしてください。これらの制限は、スマートフォンでの実測のピークメモリの保証ではありません。
- **ローカルの予算。** ローカルの結果履歴には512 MiBの予算と100件の上限があります。アセットのスナップショットには別の512 MiBの予算と、アセットあたり最大20の過去バージョンがあり、抽出されたクレデンシャルのバイト列もその予算に数えられます。復元はこれらの制限を守り、既存のユーザーデータを黙って追い出すことはありません。
- **バッチのメタデータ。** ローカルのバッチのメタデータには、別の4 MiBの予算、最大100のマニフェスト、バッチあたり20のメンバーがあります。保留中のメンバーはメタデータの容量を確保し、メンバーあたりのレポートの上限は32 KiBです。これは論理的な予算であり、ブラウザのディスク容量の保証ではありません。実際のクォータの失敗は表示され、メモリ内のレポートはダウンロード可能なままです。バッチのメンバーを再試行すると、古いレポートを上書きせずに新しいバッチが作られます。バッチのレコードを削除しても、個々の結果のバイト列やライブラリのアセットは削除されません。
- **ライブラリ内の結果。** 変換結果は、正規化や再エンコードなしに、ソースと出力のハッシュ、操作の関係を付けてライブラリに追加できます。繰り返し追加しても、変更されていないコピーは再利用され、編集されたコピーが上書きされることはありません。ラスター画像は、現在のライブラリのアセットIDを使う新しいDesignドキュメントを始められます。DesignのランタイムとURL経路全体で正確なバージョンの固定を徹底するのは、別の作業です。SVG、HTML、PDF、ZIPの結果は、信頼されたインタラクティブなコンテンツやベクターに昇格されることなく、不透明なファイルアセットとして保持されます。
- **人に見える場所。** **Convert → Recent file operations**には、履歴の使用量、レポート、ダウンロード、バージョンマネージャーが表示され、削除されたライブラリアセットの以前のバージョンも見つかります。スナップショットを復元すると新しい現在のバージョンが作られ、選択したスナップショットは保持されます。**Settings → Preferences → Storage**は、結果とバージョンを、使い捨てのキャッシュとは別に数えます。
- **クリーンアップ。** 明示的な一時ファイルのクリーンアップは、操作が所有し、参照されていないバイト列だけを削除します。現在のレコードはそのファイルを守り、最近のOPFSファイルには1時間の猶予があります。保存した結果とアセットのスナップショットが、自動的に消去されることはありません。

古いリーダーも、v2のエンベロープ(`minReader: 1`)を受け付け、知っているパートを復元し、非対応の履歴パートをスキップとして数えます。履歴の完全な復旧には、`fileHistory`アダプターを持つシェルが必要で、これはシェルの内部の接点であり、ツール向けの新しい`HostV1`ケイパビリティではありません。実際の2台のデバイス間の復元はローカルのChromiumゲートで検証されており、インストール済みのデスクトップ、iOS、Androidアプリでの復旧は、別途受け入れを行う予定です。
:::

## リファレンス

- モジュール: `shells/web/src/data-transfer.ts`(`exportBackup`、`importBackup`、`BACKUP_FORMAT`、`BACKUP_FORMAT_VERSION`、`BACKUP_READER_VERSION`。`backupFilename()`による命名は内部用です)。
- 契約テスト: `tests/data-transfer.test.ts`。往復、マージ、整合性、前方互換性、リーダーの判定を扱います。
- 履歴の契約テスト: `tests/file-history-backup.test.ts`、`tests/file-batch-history.test.ts`、`tests/file-result-library.test.ts`。ブラウザでの受け入れ: `tests/file-history.browser.test.ts`、`tests/file-batch-history.browser.test.ts`、`tests/file-result-reuse.browser.test.ts`。
- 使用するブリッジの面: `host.profile`、`host.state`、`host.assets`。[Host API](/info/host-api.html)をご覧ください。
