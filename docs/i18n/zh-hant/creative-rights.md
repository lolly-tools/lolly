# 創作權利與署名

你應該能使用別人製作的好作品，而不必成為授權專家，也不必默默省略創作者。因此，Lolly 會保留它繪製的每件作品的來源、讀取記錄的授權、判斷該授權對你實際用途的要求、完成程式能做的部分，並告訴你哪些部分只有你能做。

::: note 這些都不是法律建議
也不是對你專案的裁定。Lolly 記錄事實，套用從授權法律條文本身讀取的一小組規則，並顯示判斷過程。附有條件的授權是正常且允許的選擇。它絕不會被視為有問題的素材。
:::

## 你會在哪裡遇到這些情況

表情符號集是日常例子。Twemoji 採用 CC BY 4.0，因此含有表情符號的標題在匯出時，會附上圖稿的來源署名。兩套 OpenMoji 都採用 CC BY-SA 4.0，因此用品牌風格重新為其中一個字符上色屬於改作，分享該改作時會要求你選擇一次相容的授權。Fluent（MIT）、Noto 與 Blobmoji（兩者皆為 Apache 2.0）也已登錄，各自依照經審閱的授權處理。

選擇符號集從不會受阻，選擇控制項也會在你選擇時顯示授權。同樣的規則適用於目錄插圖、LUT、字型與其他任何已記錄的作品。

## 三項事實，分開記錄

「CC BY 4.0」、「這項用途需要署名」與「署名已放在你剛下載的檔案裡」是三種不同的陳述，Lolly 會將它們分開處理：

- **證據**是來源所宣告的內容，依找到時的原貌記錄，並附上宣告者與讀取位置。後續匯入絕不會覆寫先前的記錄。
- **義務**是經審閱的規則針對一項用途、一條交付路徑與一群受眾，依據該證據判定的要求。
- **交付**是成品位元組實際包含的內容，透過回讀確認。只有在讀取器於交付的檔案中找到署名之後，Lolly 才會表示已包含署名。

## 你會看到什麼，以及該怎麼做

匯出面板、Lolly Verify、命令列與供機器讀取的結果都使用相同的用語，以下大致依你遇到的頻率排列。

| 你看到的內容 | 意義 |
|---|---|
| 將包含來源署名。 | 署名已準備好，交付路徑也能攜帶署名。尚未寫入任何內容，因此這不是成功訊息。 |
| 此檔案的中繼資料已包含署名。 | 已回讀交付的位元組、驗證憑證，並在憑證中找到所有必要來源。 |
| 署名與憑證位於下載套件中。 | 署名會以附帶檔案的形式隨成品傳遞。轉交時請將它們放在一起。 |
| 若要分享這份改作，需要相容的授權。 | 採用 ShareAlike 的來源已經變更，成果將用於私人使用以外的用途。只需選擇一次，不會每放置一次就跳出對話框。 |
| 請將這段署名加入貼文說明。 | 選定的路徑既不攜帶憑證，也不攜帶可讀的署名，因此需要你貼上署名文字。 |
| 根據已記錄的 CC0 宣告，無須署名。 | 該宣告沒有任何要求。仍會提供致意署名。 |
| 未記錄來源授權。 | 這個來源沒有任何記錄。這是需要補齊的資訊缺口，不是對作品不利的判定。它絕不代表作品可以任意轉交。 |
| 已記錄條件，尚未解讀。 | 已識別授權識別碼並列出其條件，但這裡沒有規則解讀這些條件。不會自動放行，也不會自動禁止。 |
| 兩項授權宣告不一致。 | 兩筆記錄列出不同的授權，尚未選定適用哪項授權許可。 |
| 交付的檔案中沒有署名。 | 原本承諾附上署名，但回讀時未找到，檔案仍屬於你。請重新匯出，或手動使用署名文字。 |

Lolly 絕不會告訴你某件作品沒有權利爭議，或在法律上可放心使用，產品中也沒有任何統一的綠色授權標章。沒有程式能查明這兩件事。

## 哪些仍由你決定

- **授權由你選擇。** 聲明檔案權利時，會將過去混為一談的三種狀態分開：未宣告公開授權、明確的保留所有權利聲明，以及實際授予公開授權。Lolly 只會為後兩者寫入權利聲明，絕不會從你的個人資料產生。
- **不會替你的作品重新授權。** 來源條款與你自己的輸出宣告是分開的記錄。ShareAlike 條件適用於它所規範的改作，不會自動套用到你製作的所有其他內容。
- **私人作品仍可使用。** 適用於分享時的條件，會在準備分享時提出。這裡不會因此禁止匯入，也不會要求你先填授權問卷才能使用自己的檔案。
- **決定會連同其依據的事實記錄。** 你記錄的每項選擇都會附上指紋，對應做出選擇時的作品、用途、路徑與受眾。更換符號集、處理方式、格式或受眾，就會再次詢問。沒有全面「忽略授權」的開關，因為關閉警告無法交付署名，也無法授予許可。
- **你的詳細資料與第三方署名分開處理。** 移除你自己的個人中繼資料，不會移除已署名的藝術家；必要署名也絕不是匯出你聯絡資料的理由。

## Lolly 在各處的處理方式

- **在目錄中。** 作品資訊頁會顯示來源與創作者、正式授權名稱（下方保留原始標籤）、已記錄且可複製的署名，以及一行使用要求。卡片只會說明要求，絕不會宣稱已完成匯出。
- **在匯出面板中。** 渲染一旦使用已記錄的作品，Content protection 內就會出現 Source credits 卡片，位於你為自身匯出選擇的 Licence 旁邊。它顯示狀態、Details 裡的署名文字、Copy credit 按鈕，以及需要做決定時的內嵌卡片。決定絕不會以阻擋操作的對話框呈現：即使還有待辦動作，下載仍會繼續。
- **在檔案中。** 匯出若放置了已記錄的作品，會為每件不同作品寫入一項 Content Credentials 來源素材，繫結至其公開位址的原始位元組，並附上創作者、授權及其連結、來源、修訂版本與變更。Lolly 簽署的是它觀察到的事實。它絕不會代表上游藝術家簽署聲明，Lolly Verify 也會說明是哪一種情況。
- **在套件中。** 無法容納憑證的下載，例如 `.lottie` 動畫，會將署名以 `CREDITS.txt` 與 `credits.json` 放入套件。寫入後會回讀這些檔案，且不會宣稱它們具有已簽署的憑證。
- **寫入之後。** 在任何地方表示已包含署名之前，都會回讀交付的位元組。未通過驗證的憑證不算已交付署名。
- **在可編輯的 `.lolly` 檔案中。** 經審閱的授權記錄了轉交來源的許可、資料列附有擁有者自己的條款，或完全沒有記錄作品權利資訊時，位元組會隨檔案傳遞；最後一種情況是沒有授權、沒有權利記錄，也沒有署名。在最後一種情況下，傳送者會看到哪些作品在沒有授權記錄的情況下隨檔傳遞，`CREDITS.txt` 也會要求開啟檔案的人在重複使用前查核其條款。已記錄但尚未解讀的授權會導致作品被保留；已記錄權利人但沒有授權的作品，或無法讀取目錄記錄的作品，也會被保留。你仍可刻意納入被保留的內容，署名檔案會記錄這是你的選擇。套件的 `CREDITS.txt` 會列出哪些內容隨檔傳遞、依據哪項授權，以及哪些內容被保留與原因。
- **在 Lolly Verify 中。** Sources 面板會列出檔案記錄的每個來源，附有計算得出的摘要、署名、Copy credit 按鈕、只有在你要求時才會開啟的 Open source 連結，以及檢查範圍的限制說明。只有當你選擇用途時，才會出現 Check for this use 問題，且不會為了回答而擷取任何資料。
- **移除中繼資料時。** 清除作業會告訴你檔案不再攜帶多少項來源署名、提供署名文字，並提供一份乾淨檔案與獨立的署名檔案。清除過的位元組絕不會重新加註。

**擁有者自己的標誌。** 擁有者很少會以開放授權發布標誌。若資料列的權利記錄標示為 `own-work`，且附有擁有者與條款，就能隨 `.lolly` 檔案及[品牌頁面](/info/brand-page.html#publish-your-own-marks)傳遞。它會標示為「擁有者發布，非開放授權」，條款則放在檔案旁。這只是讀取目錄的陳述。Lolly 不會查核標誌的所有權。沒有擁有者、條款空白或沒有宣告的記錄仍會被保留，沒有這類記錄的他人標誌也一樣。

::: details Lolly 已審閱的授權
規則版本 `rights-rules-2026-11-05.1`。每項規則都來自授權本身的法律條文，其依據的章節會在這裡及 `engine/src/rights-profiles.ts` 中的規則旁標明。版本與司法管轄區版本都依記錄保留：CC BY 3.0 宣告會保留自己的版本，不會因為應用程式的選擇器偏好 4.0 就被回報為 4.0。

| 授權 | 對 Lolly 可執行用途的要求 | 依據 |
|---|---|---|
| CC BY 4.0 | 創作者、標題、著作權聲明、授權名稱與連結、來源連結及變更標示，來源有提供的項目都須附上。不排除任何用途，包含商業使用。 | [法律條文](https://creativecommons.org/licenses/by/4.0/legalcode.en)，第 2(a)(1) 與 3(a) 節 |
| CC BY-SA 4.0 | 相同的署名要求。此外，若分享改作，必須採用相容授權發布：CC BY-SA 4.0、Free Art License 1.3，或僅單向相容的 GPL-3.0-or-later。這三項以資料形式取自 Creative Commons 清單，絕不以名稱比對。 | [法律條文](https://creativecommons.org/licenses/by-sa/4.0/legalcode.en)，第 3(a) 與 3(b) 節；[相容授權清單](https://creativecommons.org/compatible-licenses/) |
| CC0 1.0 | 沒有要求。該宣告不附帶條件，因此 Lolly 會提供致意署名，但絕不將它列為必要。 | [宣告](https://creativecommons.org/publicdomain/zero/1.0/legalcode.en)，第 2 與 3 節；[CC 常見問題](https://creativecommons.org/faq/)中關於署名的說明 |
| CC-PDDC | 沒有要求。記錄的是聲明本身及聲明者，因為認證是單方陳述，而非證明。 | [宣告與認證](https://creativecommons.org/licenses/publicdomain/)段落 |
| Apache License 2.0 | 來源的聲明與 NOTICE 檔案中的署名文字會隨散布的作品傳遞。執行時使用沒有要求。若授權要求聲明文字，但作品沒有附上，就會回報為資訊缺口。 | [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0)，第 4 節，條件 1 至 4 |
| MIT | 著作權聲明與許可聲明會隨副本及實質部分傳遞。執行時與參照用途沒有要求。 | [MIT](https://opensource.org/license/mit)，許可聲明條件 |
| ISC | 與 MIT 相同，但文字更簡短：著作權聲明與許可聲明會隨副本傳遞。執行時與參照用途沒有要求。 | [ISC](https://opensource.org/license/isc-license-txt)，許可聲明條件 |
| SIL OFL 1.1 | 使用字型渲染文字，不會對文字附加任何要求。轉交字型檔案時，須附上授權、著作權聲明與保留名稱規則。 | [OFL 1.1](https://openfontlicense.org/open-font-license-official-text/)，條件 2、3 與 5；[OFL 常見問題](https://openfontlicense.org/ofl-faq/)中關於文件的說明 |

**已記錄，未解讀。** CC BY-NC、CC BY-ND，以及 NC-SA 與 NC-ND 組合都可識別，其條件會列出，但這裡沒有規則解讀它們。它們會回報 `licence.unknown`，並附上一行列出條件的文字。無法從價格或帳號判斷是否屬於商業情境，而每份組合授權條文都必須各自經過審閱，才能由規則解讀。

另有三種如實回覆，都不代表許可：

- `LicenseRef-` 識別碼會原樣傳回。它指向已儲存的定義，絕不會因為拼寫方式就被判定為專有授權。
- 無法識別的宣告會以未解析的狀態傳回，並保留原始文字。
- `A OR B` 是權利人提供的選擇，因此會傳回每個選項，不會選定任何一個。`A AND B` 表示條件累加，這些規則只會記錄它，不會將兩份授權設定一起解讀。
:::

::: details 在命令列與 MCP 中
當評估結果有必要署名或問題時，渲染會在標準錯誤輸出中列印 `Rights:` 區塊。它包含狀態、每個問題各一行的 `code - summary`、回讀交付檔案的結果，以及供貼上的署名文字。

```
Rights: actions-required
  licence.adaptation-choice - If you share this adaptation, it needs a compatible licence.
  Credential intact. It records 1 source. The exporter recorded it; the source did not sign a credential of its own.
  Credits included in this file's metadata.
  "water wave (OpenMoji Color 17.0.0)" by Vanessa Boutzikoudi (OpenMoji), CC BY-SA 4.0 https://creativecommons.org/licenses/by-sa/4.0/, source https://raw.githubusercontent.com/hfg-gmuend/openmoji/f9fc506a3f913be9897ab0181d611d4c910a4104/color/svg/1F30A.svg, changes: recoloured.
```

在這裡，署名已在檔案中，但分享檔案之前仍需做出授權決定。

| 狀態 | 意義 | 結束碼 |
|---|---|---|
| `ready` | 沒有任何事項等待人員處理。 | 0 |
| `actions-required` | 分享檔案之前仍需做出決定。檔案仍會寫入。 | 4 |
| `use-not-covered` | 經審閱的規則指出，授權不涵蓋這項用途。 | 4 |
| `unknown` | 問題僅為資訊缺口：未記錄授權，或未解讀條件。 | 0 |
| `delivery-failed` | 由回條設定，絕非由評估設定：在交付的位元組中找不到原本承諾附上的署名。匯出面板會顯示此狀態；CLI 則在回讀結果行回報相同事實。 | 不列印 |

當保護性檢查拒絕執行時，這個 CLI 原本就會傳回結束碼 4。不是代表「在另一個執行器重試」的 3，因為無論在哪個執行器，授權決定都仍待處理。

`--rights=private` 表示這次渲染不會交付給任何人。區塊仍會列印，署名也仍可複製；暫不套用的是分享時適用的條件，且不會記錄交付聲明。沒有用來忽略條件的旗標：`--rights=ignore` 是用法錯誤。

問題代碼固定且可供機器讀取，不受翻譯文字影響：`attribution.source-missing`、`attribution.delivery-missing`、`licence.adaptation-choice`、`licence.use-not-covered`、`licence.grant-conflict`、`licence.unknown`、`source.redistribution-unknown`、`credential.ingredient-missing`。

透過 MCP，`lolly_verify` 會傳回 `rights` 資料，包含摘要、每個已記錄來源各一列的資料，以及限制說明。不需瀏覽器的 `lolly_render` 會傳回 `status`、`issues`、`credits`、`fingerprint`，以及透過回讀位元組判定的 `creditsInFile` 旗標。
:::

::: details 規則位於何處
五個引擎模組，全都是純模組：不使用網路、時鐘或檔案系統。規則資料有版本記錄且存放於儲存庫中，絕不另行擷取。

| 模組 | 內容 |
|---|---|
| `engine/src/rights-profiles.ts` | 識別碼表、精簡的 SPDX 運算式讀取器、附有出處的已審閱授權設定，以及署名可列印連結的唯一規則。 |
| `engine/src/rights-evaluate.ts` | 分類、問題、署名計畫與指紋。結果固定：相同事實即使順序不同，也會得到相同答案。 |
| `engine/src/rights-attribution.ts` | 可讀的署名、附帶檔案、來源素材，以及寫入後實際檢查產生的回條。 |
| `engine/src/rights-companion.ts` | 套件署名的回讀（ZIP 下載內的 `CREDITS.txt` 與 `credits.json`），確認署名但不宣稱具有已簽署的憑證。 |
| `engine/src/rights-report.ts` | 將已驗證的憑證回讀為 Lolly Verify 所詢問的三個問題。 |

`tests/fixtures/rights/` 中的預期結果檔案依據授權條文撰寫，而非依據評估器的輸出；其 README 引用了每項預期結果所依據的章節。
:::

## 目前尚未做到的事

- **不會確認任何目的地。** Lolly 會準備說明文字。連接器接受請求，不代表署名已送達讀者，這裡也不保證後續上傳、截圖或轉碼會保留隱藏的中繼資料。
- **不會依計畫寫入原生中繼資料署名欄位。** 署名透過 Content Credentials 與可讀文字傳遞。目前尚未依署名計畫填入 IPTC 與 XMP 的個別來源署名欄位。
- **尚未建置更正與撤回功能。** 沒有介面可為已記錄的作品補上缺漏的創作者、加入本機更正，或撤回記錄。
- **尚未建置供應商連接功能。** 購買的圖庫素材、自訂許可與供應商帳號都沒有匯入路徑，因此其授權許可只能記錄為你自己的聲明。
