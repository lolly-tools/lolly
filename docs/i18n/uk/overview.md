# Архітектура Lolly

![Значок Lolly - велика зелено-біла цукерка на паличці](/info/icon.svg)

Ця сторінка для тих, хто змінює код Lolly: як поєднуються рушій, оболонки та пакети інструментів, де кожен із них міститься в репозиторії та які зобов'язання обмежують кожну зміну. Щоб дізнатися, що робить Lolly та хто ним користується, спершу прочитайте [Як працює Lolly](/info/how-lolly-works.html).

[`engine/README.md`](https://github.com/lolly-tools/lolly/blob/main/engine/README.md) описує рушій за модулями та генерується з коду. [Модель загроз і межі довіри](/info/threat-model.html) розглядає ту саму архітектуру через межі довіри та пояснює, що рушій вважає недовіреним.

<!--i:eti-layers-->
## Загальна картина

На верхньому рівні інструменти — це дані. Рушій посередині нічого не знає про жодну платформу. Оболонки внизу реалізують один контракт, а каталоги постачають вміст.

![Інструменти передають маніфест, шаблон і хуки до спільного рушія. Вебоболонка, оболонки Tauri й термінала реалізують міст можливостей HostV1 і читають інструменти та ресурси з каталогів.](/info/diagrams/concepts/platform-layers.svg)

Усе, що можна описати чистими даними та Handlebars, належить до **рушія**. Усе, що звертається до DOM, файлової системи, мережі чи будь-якого API браузера або операційної системи, належить до **хоста**, тобто боку оболонки в мосту. Рушій має відкритий вихідний код. Ніщо, що знає про конкретний бренд, не потрапляє до рушія.

## Структура репозиторію

Lolly — це один репозиторій. Кожен наведений нижче каталог є звичайним каталогом, окрім `brands/suse`: це **приватний** підмодуль git із пакетом інструментів і каталогом SUSE, який публічний клон не завантажує. Профіль вмісту (`profiles.json`) визначає, які пакети читає збірка. Кожен процес визначає власний профіль, і глобального перемикача немає. [Посібник зі збирання](/info/build-guide.html) містить команду клонування та пояснює, як закомітити зміну всередині приватного пакета.

| Каталог | Що містить |
|---|---|
| `engine/` | Незалежне від платформи ядро: завантажувач, середовище виконання, вхідні дані, шаблони, режим URL, одиниці виміру та модулі форматів |
| `shells/` | Вебзастосунок, настільні й мобільні застосунки Tauri, CLI, TUI та розширення браузера |
| `packages/` | Зокрема SDK для авторів інструментів (`@lolly-tools/core`), спільні частини оболонки Node та рендерер документації |
| `community/` | Інструменти, не прив'язані до бренду, та спільні пакети емодзі |
| `brands/` | Пакети брендів: `lolly-demo` (Lolly Demo, дизайн-система, яку використовує lolly.tools), `lolly-start` (порожня основа для початку) та приватний `suse` |
| `services/` | Необов'язкові сервіси MCP, сертифікатів і Penpot та спільний для них серверний код |
| `schemas/` | JSON Schema для маніфестів інструментів, записів ресурсів і посилань на ресурси |
| `scripts/`, `tests/`, `docs/`, `api/` | Скрипти збирання й каталогів, набір тестів рушія, ця документація та згенеровані безсерверні пакети |

::: details Файли рушія та оболонок, з якими ви познайомитеся першими
```
engine/src/
  index.ts          public surface: loader, runtime, template, inputs, url-mode
  loader.ts         fetches and validates tool files
  runtime.ts        orchestrates one mounted tool, from load to export
  template.ts       Handlebars hydration and annotateTemplate
  inputs.ts         manifest to runtime input model
  url-mode.ts       URL to input state and back
  validate.ts       JSON Schema validation of manifests
  compose.ts        nested tool renders (composes)
  embed.ts          portable lolly.tools embed URLs
  bridge/host-v1.ts type re-export of the @lolly-tools/core contract

shells/web/src/
  main.ts           boot and routing
  bridge/           the web implementations of the host APIs
  catalog/sync.ts   boot-time catalog sync and offline cache
  views/            the gallery, tool, projects, free canvas and the other views
  pro/              Batch (#/batch)

shells/cli/         bin/lolly.ts (entry), src/run.ts (headless render), src/bridge.ts
shells/tui/         src/main.tsx (the full-screen app), src/bridge.ts
```
:::

::: note У корені репозиторію немає каталогів `tools/` або `catalog/`
`packages/node-shell/src/content-roots.ts` відповідає на запитання «де міститься інструмент `<id>`» і «де каталог» за даними з `profiles.json`. Справжня пара `tools/` і `catalog/` записується лише до результату збірки, як-от `dist/`, вмісту пакета RPM чи образу контейнера, бо браузер завантажує ці два шляхи через HTTP.
:::

## Де працює Lolly

Кожен інтерфейс використовує той самий рушій і ті самі файли інструментів.

- **Вебзастосунок.** Прогресивний вебзастосунок. Він працює офлайн, щойно його сервіс-воркер закешує інструменти та ресурси. Обліковий запис не потрібен, а стан зберігається в IndexedDB на кожному пристрої. Один адаптивний макет підходить і для комп'ютера, і для телефона. На телефоні елементи керування переходять на висувну панель, а елементи керування експортом відкриваються з плавучої пігулки.
- **Настільні та мобільні застосунки.** Пакети Tauri з тим самим вебзастосунком, із системними файловими діалогами, станом у файловій системі та повноцінною роботою офлайн.
- **CLI.** `lolly <tool-id> --input=value --output=file.png` завантажує той самий рушій у DOM без графічного інтерфейсу та записує файл. Це режим URL через інший транспорт. Див. [CLI](/info/cli.html).
- **TUI.** Повноекранний термінальний застосунок, орієнтований на клавіатуру. Він повторно використовує міст CLI та тримає збережені сеанси на диску: у папці настільного застосунку, якщо його встановлено, інакше в `~/.lolly`. Він запускає браузер без графічного інтерфейсу з обмеженою областю дії лише тоді, коли цього потребує формат. Див. [TUI](/info/tui.html).

Вебзастосунок також містить **Batch** (`#/batch`, `shells/web/src/pro/`), сітку на зразок електронної таблиці, яка рендерить багато рядків одночасно в одному чи кількох інструментах. Див. [Batch і Lolly Multi-edit](/info/batch.html#make-many-versions-of-one-design). **Налаштування → Capabilities** перелічує все, що платформа заявляє як свої можливості.

## Архітектурні зобов'язання

Ці рішення вже ухвалено. Від них залежить кожне інше рішення в кодовій базі, тому зміна будь-якого з них — масштабна справа.

### 1. Декларативні інструменти з можливістю використати імперативний код

Інструмент — це маніфест (`tool.json`), шаблон (`template.html`) і необов'язковий `hooks.js`. **Маніфест оголошує вхідні дані**. Вхідні дані ніколи не визначаються за токенами Handlebars у шаблоні. Більшість інструментів складається лише з маніфесту та шаблону, тож їх можуть створювати й не розробники.

![Стек елементів керування Street Map: випадний список міст, вибір теми, повзунки товщини та тригери кольору, кожен із яких створено з рядка маніфесту](/t/url-shot?url=%2F%23%2Ftool%2Fstreet-map%3Fcity%3Damsterdam&width=1440&height=900&dpi=192&waitMs=2400&walker=1&format=svg&css=%23tool-canvas%7Bdisplay%3Anone%7D&cropSelector=%23tool-inputs&dark=1&filename=ov2-street-map-controls)

Інструменти, які обчислюють значення, як-от кодування QR чи побудова діаграм, додають хуки: іменовані функції життєвого циклу, які середовище виконання викликає з переданим мостом можливостей. Хуки — це контракт переносності, а не захисна пісочниця. Вони працюють у межах відведеного часу. Інструменти, чиї хуки перевірено на відсутність залежностей від глобальних об'єктів сторінки, мають `isolate: true` і працюють у Worker. [Хуки інструментів](/info/tool-hooks.html) описує життєвий цикл і часові ліміти. [Модель загроз](/info/threat-model.html) пояснює, що обмежує виконавець на сторінці, а що ні.

### 2. Інструменти та ресурси — це дані, а не код у складі застосунку

Вебзастосунок і застосунки Tauri завантажують каталоги інструментів і ресурсів під час запуску, кешують їх і працюють із кешованим вмістом. Новий інструмент чи ресурс не потребує нового випуску застосунку. Байти ресурсів перевіряються за контрольними сумами SHA-256. `id` і `version` ресурсу визначають скидання кешу.

### 3. Міст можливостей — єдиний API, доступний інструментам

Інструменти ніколи не звертаються до DOM поза своїм шаблоном, не викликають `fetch` напряму та не читають файлову систему. Вони викликають версійовані методи `host.*`. Контракт визначено в `packages/core/src/host-v1.ts`, у SDK для авторів інструментів `@lolly-tools/core`. Сторонній розробник може використовувати SDK без залежності від рушія. `engine/src/bridge/host-v1.ts` повторно експортує його типи.

| Обов'язковий API | Що робить |
|---|---|
| `host.profile` | Дані користувача; попередньо заповнює вхідні поля через `bindToProfile` |
| `host.assets` | Запити до каталогу, визначення ресурсів і вибірник хоста |
| `host.state` | Збереження та завантаження слотів вхідних даних: IndexedDB у вебзастосунку, файлова система в Tauri, пам'ять у CLI |
| `host.clipboard` | Запис тексту чи зображення до буфера обміну з резервними варіантами для різних платформ |
| `host.export` | Растеризація чи серіалізація об'єкта рендерингу та шлях перетворення файлів на пристрої |
| `host.log` | Запис до журналу хоста з рівнями важливості |

Усі інші API необов'язкові та доповнюють основні: `tokens`, `text`, `color`, `geom`, `pdf`, `compose`, `media`, `recorder` та багато інших. `requires` у маніфесті перелічує необов'язкові API, які його хуки викликають без попередньої перевірки. Хост, у якого бракує хоча б одного, відмовляється підключати інструмент. Наявність решти хуки перевіряють під час роботи. Деякі, як-от `recorder`, також потребують можливості пристрою, яку оголошує інструмент. `packages/core/src/host-v1/apis.ts` перелічує їх усі, а [API хоста](/info/host-api.html) описує кожен. Додавання методу — це мінорна версія. Видалення чи зміна методу — мажорна версія, а v1 продовжує працювати після випуску v2.

### 4. Ідентифікатори ресурсів — назавжди

`lolly/logo/primary` — це контракт. Після публікації ідентифікатор ніколи не змінюється й не використовується повторно. Зміна байтів підвищує `version` у записі ресурсу. Заміна встановлює `deprecated: true` і, за потреби, `replacedBy`. Наявні посилання завжди знаходять ресурс, тож збережені сеанси та поширені посилання працюють роками.

### 5. Режим URL — повноцінний спосіб роботи

Кожне вхідне значення можна виразити параметром URL, тож посилання — це готовий файл:

```
https://lolly.tools/t/qr-code?url=https://example.com&ecl=H
```

![Саме це посилання, без жодних доповнень, — готовий файл](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Fexample.com%26ecl%3DH%26full&width=760&height=760&dpi=192&waitMs=2000&walker=1&format=svg&dark=1&filename=aud-url-mode-qr)

Змініть параметр — і отримаєте інший файл. Ця палітра — один початковий колір, гармонія та кількість кроків:

![Дев'ять кроків у чотирьох колірних тонах, усі з одного початкового кольору, переданого в посиланні](/t/url-shot?url=%2F%23%2Ftool%2Fcolor-palette%3Fseed%3De0521a%26harmony%3Dtetrad-4%26steps%3D9%26full&width=1440&height=900&dpi=192&waitMs=2000&walker=1&format=svg&cropSelector=%23tool-canvas&dark=1&filename=ov2-url-palette)

CLI будує той самий стан URL зі своїх аргументів і запускає той самий конвеєр, тож CLI не може розійтися із застосунком. `engine/src/url-mode.ts` розбирає та серіалізує стан URL. Зарезервовані назви (`format`, `width`, `dpi`, `c2pa`, `z` та інші) ніколи не передаються інструменту. [Зарезервовані параметри URL](/info/url-parameters.html) перелічує їх усі. Вхідні ресурси передаються за `id` і визначаються через `host.assets.get()` до заповнення шаблону.

### 6. Зберігання працює через міст

Вебзастосунок використовує IndexedDB, Tauri — файлову систему, а CLI — пам'ять. Інструменти бачать лише `host.state.save(slot, data)` і `host.state.load(slot)`, ніколи `localStorage`. Користувачі можуть зберігати кілька іменованих сеансів для кожного інструмента без облікового запису. Оскільки міст — єдина точка взаємодії, цей стан також переносний. `shells/web/src/data-transfer.ts` експортує стан як один файл `lolly-backup`, який можна імпортувати в будь-яку іншу інсталяцію ([Перенесення даних](/info/data-transfer.html)). [Синхронізація](/info/sync.html) надсилає той самий пакет до сховища, вибраного користувачем.

### 7. Позначки зрілості вказують, що являє собою інструмент

Кожен інструмент оголошує `status: official | community | experimental`. Галерея сортує за статусом. Експериментальні інструменти типово додають водяний знак до експорту: середовище виконання вмикає його, якщо викликач не передав `watermark: false`. Інструменти, що працюють на пристрої, звільнені від цього. Власний процес ведення каталогу команди доповнює ці позначки.

### 8. Типи вхідних даних визначено в маніфесті

Вхідне поле оголошує `type`: `text`, `longtext`, `number`, `boolean`, `color`, `select`, `asset`, `date`, `time`, `datetime-local`, `url`, `blocks`, `vector`, `table` або `file`. Хост рендерить елемент керування для кожного типу, тож інструментам не потрібен код елементів керування. Будь-яке вхідне поле може мати `bindToProfile`. Найважливіші три типи:

- **`asset`**, з `filter` і `allowUpload`, — це міст до системи ресурсів. `allowUpload: false` обмежує слот ресурсами бібліотеки. Завантажені користувачем файли мають ту саму структуру `AssetRef`, що й ресурси бібліотеки.
- **`blocks`** — це група повторюваних полів, яку редагують на бічній панелі та використовують Meeting Planner, Wayfinding, Diagrams та інші. Клацання відрендереного блока фокусує його рядок.
- **`file`** тримає власний файл користувача в пам'яті для утиліт, що працюють на пристрої, як-от Lolly Strip Hidden Data та Compress, а **`vector`** об'єднує фіксований набір чисел в один елемент керування.

### 9. Шаблони не містять логіки

Шаблони написано на Handlebars, тож їх можуть створювати й не розробники. `{{x}}` екранує, а `{{{x}}}` явно дозволяє вивід без екранування. Логіка міститься в `hooks.js`, де її можна перевірити. Багато шаблонів використовують `{{{` для розмітки, обчисленої хуком, тож кожен хук має екранувати те, що передає. Допоміжні функції — `default`, `upper`, `lower`, `eq`, `markdown`, `asset`, `framing` і `media`, а також `icsStamp`, `rfcText`, `csvCell` і `arrow` для супутніх шаблонів `.ics`, `.vcf` і `.csv`. Їх описано в [Шаблони та рендеринг](/info/tool-rendering.html).

### 10. Інструменти компонують інструменти

Інструмент може вбудувати рендер іншого інструмента без імпортів між інструментами. Рушій опрацьовує композицію. Маніфест може оголосити `composes: [{ id, tool, inputs }]` і розмістити дочірній елемент за допомогою `{{asset <id>}}`. Переносна URL-адреса вбудовування (`https://lolly.tools/tool/<id>.svg?…`) рендерить дочірній елемент локально; саме так Lolly Design розміщує живий QR-код або діаграму. Дочірній SVG залишається вектором у батьківському SVG чи PDF. Дочірні елементи є проміжними результатами, тому до них ніколи не додають водяних знаків чи позначок походження. Оболонка, яка не може відрендерити дочірній елемент, залишає слот порожнім, а батьківський елемент усе одно рендериться. Подробиці наведено в [Композиція та накладки бренду](/info/tool-composition.html).

## Від чого ми вирішили відмовитися

- **Без довільного JavaScript у шаблонах.** Логіка міститься в `hooks.js`.
- **Без обов'язкового сервера ресурсів.** Користувачі додають власні файли до Ресурсів у застосунку та передають роботу як сеанс: посилання для спільного доступу до вхідних даних і налаштувань, файл `.lolly`, якщо треба передати й завантажені файли. Спільний сеанс може стати шаблоном у вибірнику інструмента. Організація, якій потрібен керований каталог, може використовувати каталог, затвердження та політики Lolly Work або керувати пакетом бренду в git і перевіряти зміни там.
- **Без примусового контролю доступу.** Відкритий застосунок типово загальнодоступний. Позначки зрілості та водяні знаки позначають ризик для бренду. Вхід до організації, ролі та політику надає Lolly Work, коли команда цього потребує.
- **Без центральної бази даних.** Стан користувача зберігається на кожному пристрої, а необов'язкова синхронізація копіює його до вибраного користувачем сховища, ніколи до бази даних Lolly.
- **Без спільного шляху виконання коду між інструментами та рушієм.** Рушій та інструменти спільноти мають відкритий вихідний код. Пакет бренду, як-от приватний `brands/suse/`, містить власні інструменти й каталог на власних умовах. Жоден інструмент не імпортує з `engine/`, тож поділ залишається чітким.

## Життєвий цикл одного рендеру

Хтось відкриває `https://lolly.tools/t/qr-code?url=https://example.com&ecl=H`:

1. **Запуск.** Вебзастосунок відкриває IndexedDB, будує міст можливостей і синхронізує каталоги інструментів та ресурсів або завантажує їх із кешу під час роботи офлайн.
2. **Маршрутизація.** Шлях вибирає вигляд інструмента `qr-code`, а параметри запиту стають його початковими значеннями.
3. **Завантаження.** `loadTool` завантажує `tool.json`, перевіряє його за схемою та завантажує шаблон, стилі й хуки.
4. **Розбір посилання.** `parseUrlState` перетворює параметри на вхідні значення. Посилання на ресурс, як-от `?logo=lolly/logo/primary`, стає ще не визначеним `{ id }`.
5. **Запуск середовища виконання.** `createRuntime(tool, host, initialValues)` будує модель вхідних даних із даних профілю, типових значень і посилання, визначає ресурси за посиланнями, завантажує хуки та викликає `onInit`.
6. **Рендеринг.** Оболонка підписується на середовище виконання, малює елементи керування за моделлю та записує заповнений шаблон у `#tool-canvas`.
7. **Взаємодія.** Введення тексту викликає `runtime.setInput`, що застосовує обмеження, викликає `onInput`, знову заповнює шаблон і перемальовує його.
8. **Експорт.** **Завантажити** викликає `runtime.export(node, format)`, а `host.export` оболонки створює файл: растр, вектор за результатом обходу DOM, PDF, документ чи один з інших форматів у `schemas/tool.schema.json`. Фізичні одиниці перетворюються відповідно до формату. Метадані та Content Credentials вбудовуються там, де формат може їх містити. Експериментальні інструменти отримують водяний знак від хоста, а не від самого інструмента. [Шаблони та рендеринг](/info/tool-rendering.html) і [Експорт файлу](/info/exporting.html) описують крок експорту.

![Панель експорту, яку відкриває ?options: пара з імені файлу та формату, розмір виводу й елементи керування, що записують файл](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26options&width=1440&height=900&dpi=192&waitMs=2200&cropSelector=.export-popup&walker=1&format=svg&dark=1&filename=aud-export-popup)

Той самий життєвий цикл працює в Tauri та в CLI з DOM без графічного інтерфейсу, де результат записується до файлу або stdout.
