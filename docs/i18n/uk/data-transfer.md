# Передача даних: пакет `lolly-backup`

Пакет резервної копії переносить особисту бібліотеку, яку Lolly зберігає на пристрої: експортуйте її з одного встановлення, перенесіть файл (USB, AirDrop, листом собі чи через мережевий ресурс) та імпортуйте в інше. Експорт та імпорт не потребують сервера, а цільовий пристрій може бути офлайн.

Це специфікація формату для тих, хто створює оболонки, інструменти чи скрипти для роботи з резервними копіями. Щоб перенести власну роботу, прочитайте [Перенесення роботи на інший пристрій](/info/find-your-work.html#move-your-work-to-another-device).

![Дві кнопки, що переносять усю інсталяцію: Export my data записує один zip, Import data зчитує його назад](/t/url-shot?url=%2F%23%2Fsettings%3Ffocus%3Dstorage-section&width=1440&height=1800&dpi=192&waitMs=2400&css=.store-move%3Ediv%3Anth-of-type%282%29%2C.store-move%3Ep%3Alast-of-type%7Bdisplay%3Anone%7D&waitSelector=%5Bdata-store-group%3Dmove%5D&drive=click%3A%5Bdata-store-group%3Dmove%5D%3Esummary&walker=1&format=svg&cropSelector=%5Bdata-store-group%3Dmove%5D&dark=1&filename=pd-transfer-controls)

::: note Обсяг
Пакет містить *дані користувача*, а не інструменти каталогу. Інструменти й ресурси каталогу синхронізуються окремо та вважаються наявними на цільовому пристрої, у найгіршому разі у вищій версії. Інструменти, створені користувачем, передаються всередині `profile.json`. Імпорт ніколи не встановлює й не оновлює інструмент каталогу.
:::

## Цілі

- <!--i:box--> **Один формат для всіх оболонок.** Вебзастосунок, настільні й мобільні застосунки та майбутні оболонки використовують однакову зовнішню структуру й схеми частин. Необов'язкові частини залежать від можливостей кожної оболонки, а про непідтримувані частини повідомляється. Кожен міст можливостей надає свій адаптер сховища.
- <!--i:shieldcheck--> **Витримує перенесення.** Пакет, пошкоджений чи обрізаний під час передачі, відхиляється під час імпорту з помилкою й ніколи не відновлюється наполовину.
- <!--i:clock--> **Переживає цю версію.** Старіший застосунок імпортує ті частини новішого пакета, які розпізнає. Несумісний формат коректно відхиляється.
- <!--i:check--> **Безпечне об'єднання.** Імпорт у встановлення, яке вже використовується, ніколи не стирає нічого, чого не було в пакеті.

## Зовнішня структура

Пакет є звичайним `.zip`. Він зберігається цілим за будь-якого способу передачі, а його вміст може перевірити будь-який засіб розпакування ZIP.

Завантажений файл називається за його власником: `LollyTools-<First>-<Last>-<YYYY-MM-DD>-<n>.zip`, наприклад `LollyTools-Ada-Lovelace-2026-06-26-1.zip`. Ім'я та прізвище беруться з профілю й пропускаються, якщо не задані: без профілю виходить `LollyTools-2026-06-26-1.zip`, а лише з ім'ям — `LollyTools-Ada-2026-06-26-1.zip`. Кожне ім'я стає безпечним для назви файлу токеном (літери й цифри Unicode зберігаються, пробіли та пунктуація видаляються, щонайбільше 32 символи). `<n>` є послідовністю для кожного дня й пристрою, тож повторні експорти протягом дня не конфліктують і зберігають порядок. `backupFilename()` у `data-transfer.ts` формує назву. Назва не змінює вміст ZIP.

| Шлях | Обов'язковість | Вміст |
|---|---|---|
| `manifest.json` | так | Ідентифікатор формату, версії, кількості та цілісність кожної частини. Засіб читання читає цей файл першим. |
| `profile.json` | якщо задано | Запис користувача `me`: ім'я, контакт, посилання на портрет і прапорці, а також папки, Кошик, заготовки проєктів, шаблони користувача й створені ним інструменти, обране, приховані інструменти, мова та вибір емодзі. Читається через `host.profile`. |
| `sessions.json` | так | Кожен збережений сеанс: слот, ідентифікатор і версія інструмента, мітка, мініатюра (data URL) і повні вхідні дані. Читається через `host.state`. |
| `assets.json` | так | Метадані кожного завантаженого ресурсу (зображення, шрифти, токени бренду, логотипи, збережені копії завантажень), кожен указує на свої байти в `assets/blobs/`. |
| `assets/blobs/<n>.<ext>` | для кожного ресурсу | Необроблені байти ресурсу, збережені без стиснення, бо більшість уже мають стиснені формати. Розширення є косметичним; визначальним є тип MIME в `assets.json`. |
| `assets/blobs/<n>.c2pa` | за наявності | Витягнуті Content Credentials як точні двійкові байти, на які посилається `_credentialFile` у записі ресурсу. Це не ключі підпису пристрою. |
| `design-systems.json` | за наявності | Дизайн-системи, створені чи додані в цьому встановленні, як `{ active, records }`. Див. [Правила імпорту](#import-rules). |
| `file-history.json` | необов'язково | Знімки ресурсів із версіями, звіти про завершені файлові операції та повні маніфести пакетів, із власною версією. Надається внутрішнім адаптером резервного копіювання `fileHistory` оболонки. |
| `revision-history.json` | необов'язково, ручні резервні копії | Стабільні ідентифікатори творів, збережені контрольні точки, мініатюри та постійно оновлювані чернетки відновлення. Надається через `host.state.history.backup`, де підтримується. |
| `file-history/versions/` | для кожного знімка | Попередні байти ресурсів і витягнуті посвідчення, незалежно від того, чи існує поточний ресурс. |
| `file-history/results/` | для кожної завершеної операції | Точні вихідні байти. Жоден оригінальний файл, вибраний для конвертації, не зберігається й не включається. |
| `prefs.json` | так | Локальні налаштування користувача: `theme`, `sidebarWidth` і лічильник активності `ct-metrics`. |
| `lolly.txt` | так | Зрозумілий підсумок пакета (кількості, профіль, назва файлу) для всіх, хто відкриває ZIP без Lolly. Створюється заново під час кожного експорту й розпізнається під час імпорту, тож ніколи не рахується як пропущена частина. Записується після карти цілісності, тож карта не охоплює цей файл. |

::: details Як експорт записує ZIP
Експорт записує ZIP по одній частині за раз (`shells/web/src/lib/zip-stream.ts`). Завантаження, збережені результати й збережені версії ресурсів читаються порціями по 4 MiB, ніколи цілком. Збережені результати й версії спершу перевіряються за записаними SHA-256. Потім кожен файл читається для обчислення контрольної суми й дайджесту цілісності, а ZIP посилається на файл у його поточному розташуванні.

Нічого не перекодовується. Кожна частина зберігає точні байти й дайджест, тож файл із Content Credentials зберігає байти, які охоплює його підпис. Для тих самих частин і часу ZIP ідентичний результату попереднього засобу запису в пам'яті, за винятком того, що файл історії понад 16 MiB стискається частинами. `tests/backup-streaming.test.ts` перевіряє це за записаними еталонними дайджестами.

Для синтетичної бібліотеки розміром 192 MiB, за вимірами в Node, завершення резервного копіювання потребувало приблизно від 125 до 150 MiB понад саму бібліотеку, порівняно з приблизно 850 MiB для засобу запису в пам'яті (`node scripts/bench-backup-finalise.ts`). Імпорт і далі читає весь ZIP у пам'ять.
:::

## `manifest.json`

```json
{
  "format": "lolly-backup",
  "formatVersion": 3,
  "minReader": 1,
  "app": "lolly",
  "exportedAt": "2026-06-22T09:30:00.000Z",
  "counts": { "profile": true, "sessions": 2, "userAssets": 4, "prefs": 3, "assetVersions": 1, "fileOperations": 1 },
  "integrity": {
    "profile.json": "sha256-…",
    "sessions.json": "sha256-…",
    "assets.json": "sha256-…",
    "assets/blobs/0.bin": "sha256-…",
    "file-history.json": "sha256-…",
    "file-history/versions/0.bin": "sha256-…",
    "file-history/results/0.bin": "sha256-…",
    "prefs.json": "sha256-…"
  }
}
```

| Поле | Значення |
|---|---|
| `format` | Завжди `lolly-backup`. Файл без нього відхиляється як "не резервна копія Lolly". |
| `formatVersion` | Структура, з якою цей пакет було **записано**. Збільшується за будь-якої зміни набору чи структури частин. Засоби читання **не** визначають сумісність за цим полем. |
| `minReader` | Мінімальна версія засобу читання, що може **безпечно** імпортувати цей пакет. Саме за цим полем засоби читання визначають сумісність. |
| `app` | Ідентифікатор застосунку, що створив пакет, для діагностики. |
| `exportedAt` | Позначка часу створення пакета у форматі ISO. |
| `counts` | Що засіб запису включив, для показу й перевірки узгодженості. |
| `integrity` | Необов'язкове. Зіставляє кожну частину, крім `manifest.json`, із дайджестом `sha256-<base64>` у стилі SRI її **нестиснених** байтів. |

## Політика версій

Два номери версій дають формату розвиватися, не залишаючи старіші встановлення без підтримки.

![Зміна формату пакета або доповнює його, і старі засоби читання можуть її ігнорувати, або порушує сумісність, коли хибний імпорт пошкоджує дані. Доповнення збільшує formatVersion і зберігає minReader; несумісна зміна збільшує formatVersion і підвищує minReader. Засіб читання імпортує, коли minReader не перевищує його власної версії.](/info/diagrams/concepts/backup-version-gate.svg)

- Засіб читання імпортує пакет, коли `manifest.minReader` не перевищує його власної версії. Він відмовляє з повідомленням "потрібна новіша версія застосунку", лише коли пакет вимагає новішого засобу читання.
- **Доповнювальна** зміна, наприклад нова необов'язкова частина чи нове необов'язкове поле маніфесту, збільшує `formatVersion` і залишає `minReader` без змін. Старіші застосунки й далі імпортують кожну частину, яку розпізнають, а про нерозпізнані частини повідомляють як про пропущені, не відкидаючи їх мовчки.
- **Несумісна** зміна, коли хибний імпорт частини пошкоджує дані або необов'язкова частина стає обов'язковою, підвищує `minReader`. Тоді старіші застосунки коректно відмовляють замість того, щоб імпортувати те, з чим не можуть працювати. Тоді старіші застосунки коректно відхиляють пакет.
- Якщо майбутній пакет задає `formatVersion`, але пропускає `minReader`, засоби читання визначають сумісність за `formatVersion` і вважають зміну несумісною.

::: note Практичне правило для авторів
Якщо кожен наявний засіб читання й далі працюватиме правильно, ігноруючи ваше доповнення, зміна є доповнювальною: збільште `formatVersion` і залиште `minReader`. Інакше підвищте `minReader`.
:::

## Цілісність

Коли `manifest.integrity` наявне, засіб читання перевіряє SHA-256 кожної переліченої частини **до будь-якого запису**. Невідповідність ("не пройдено перевірку цілісності") чи відсутня частина ("неповний") зупиняє імпорт, тож часткового відновлення не відбувається. Це виявляє пошкодження під час передачі: обрізане передавання AirDrop, поштовий шлюз, що перекодував вкладення, пошкоджений сектор USB.

Цілісність забезпечується за можливості. Вона записується лише там, де доступне Web Crypto (кожен безпечний контекст браузера й сучасний Node), і перевіряється лише за наявності і карти, і Web Crypto. Пакет без карти, наприклад створений до появи перевірки цілісності, імпортується без змін: "неможливо перевірити" ніколи не вважається "пошкоджено".

Маніфест не перелічує ні себе, ні заново створений `lolly.txt`.

## Правила імпорту

Імпорт виконується в одному з двох режимів.

- **Merge** — це те, що виконують **Import data…** і перше приєднання до синхронізації, **Bring it to this device**. Дані на цільовому пристрої залишаються, і нічого поза пакетом не змінюється.
- **Replace** використовується синхронізацією пристроїв, щоб підтримувати їх узгодженість. Він бере запис профілю, налаштування, сеанси, зображення та вибір активної дизайн-системи із синхронізованої копії. Він видаляє лише елементи, які інший пристрій видалив після останньої синхронізації. Відновлення попередньої копії спершу зберігає дані пристрою, потім приводить пристрій у відповідність до цієї копії та видаляє все, чого копія не містить. [Синхронізація пристроїв](/info/sync.html) описує те, що бачить людина.

Об'єднання обробляє кожен вид даних так:

| Дані | Уже на цільовому пристрої | Лише в пакеті |
|---|---|---|
| Сеанси (за слотом) і завантажені зображення (за ідентифікатором) | Зберігається копія, збережена пізніше, тож старіша резервна копія ніколи не перезаписує новішої роботи. За однакового чи невідомого часу зберігається копія цільового пристрою. | Додаються |
| Папки | Зберігаються назва й батьківська папка цільового пристрою, а до папки додаються відсутні в ній елементи пакета. Сеанс, розміщений у папці на цільовому пристрої, залишається в ній. | Додаються |
| Обране (інструменти, ресурси каталогу та елементи Проєктів) | Об'єднується | Додається |
| Шаблони, шаблони Проєктів та інструменти користувача (за ідентифікатором) | Зберігається запис цільового пристрою. | Додаються |
| Записи Кошика | Зберігається запис цільового пристрою. | Додаються, тож елемент, який можна було відновити в будь-якому встановленні, і далі можна відновити. Запис, папка якого знову використовується на цільовому пристрої або слот Кошика якого цільовий пристрій уже використовує, пропускається. |
| Інші поля профілю (ім'я, контактні дані, мова, прапорці функцій, приховані інструменти та інші налаштування) | Зберігається значення цільового пристрою. | Беруться, якщо поле цільового пристрою порожнє |
| Налаштування (`prefs.json`) | Зберігається значення цільового пристрою. | Записуються, якщо на цільовому пристрої їх немає |
| Дизайн-системи (за ідентифікатором) | Запис пакета замінює запис цільового пристрою. | Додаються. Активний вибір пакета застосовується лише тоді, коли цільовий пристрій не має власної дизайн-системи. |
| Історія творів | Пізніше збережена копія залишається поточною, а інша зберігається як захищена чернетка. | Додається |

**Збережені сеанси автоматично відновлюють зв'язки зі своїми зображеннями.** Посилання на ресурси зберігаються за ідентифікатором. Міст повторно визначає їх після відновлення зображень, бо URL `blob:` не зберігаються після перезавантаження.

**Записи історії ніколи не змінюються після запису.** Повторний імпорт версій ресурсів та ідентифікаторів операцій нічого не додає, а ідентифікатор, що вже позначає інші байти чи історію, відхиляється, а не перезаписується. Повторний імпорт ідентичного поточного ресурсу зберігає його версію, а змінений поточний ресурс має містити іншу версію.

**Історія творів має ще кілька правил.** Твір, слот якого цільовий пристрій використовує для іншого твору, додається як окремий твір, а твір у Кошику цільового пристрою залишається там. Якщо ідентифікатор контрольної точки позначає інший вміст на цільовому пристрої, зберігається вміст цільового пристрою. Архів, що не проходить власних перевірок, зупиняє імпорт до будь-яких змін профілю, сеансів, ресурсів чи налаштувань, а ідентичний повторний імпорт не займає додаткового місця.

**Підсумок повідомляє, що відбулося.** Кожен імпорт повертає `profile`, `sessions`, `userAssets`, `prefs`, `skipped` і `failedAssets`.

- `failedAssets` рахує завантажені ресурси, які не вдалося відновити, наприклад через заповнене сховище пристрою.
- `skipped` рахує частини від новішого засобу запису, яких ця збірка не розпізнала. Застосунок показує кількість ("… · Пропущено N новіших елементів").
- За наявності історії файлів підсумок додає `assetVersions`, `fileOperations`, `fileBatches` і `failedHistory`. Вичерпання сховища або конфлікт незмінних ідентифікаторів може спричинити часткове відновлення, і тоді застосунок радить людині зберегти вихідну резервну копію.
- За наявності історії творів він додає `revisions` і `recoveryDrafts`, рахуючи лише те, що додав цей імпорт, а також `added`, `kept`, `replaced`, `copies` і `hidden` для способу об'єднання кожного твору. `skippedCheckpoints` рахує контрольні точки, ідентифікатор яких позначає інший вміст на цільовому пристрої, а `historyLeftOut` рахує старіші контрольні точки й чернетки, що не вмістилися у відведений для історії простір пристрою.
- Імпорт із заміною додає `removed` і `failedRemovals`.

Відновлення не є єдиною транзакцією для сховищ профілю, сеансів, ресурсів та історії. Хмарна синхронізація **не** оновлює номер застосованої ревізії після часткового чи непідтримуваного відновлення, тож копія залишається доступною для повторної спроби.

## Що не переноситься

- **Кеші каталогу** (завантажені метадані ресурсів і двійкові об'єкти, індекс інструментів), які цільовий пристрій синхронізує заново.
- **Інструменти й ресурси каталогу**, які вважаються наявними на цільовому пристрої. Токени бренду, шрифти й логотипи, додані користувачем, є користувацькими ресурсами й переносяться.
- **`blob:` та об'єктні URL**, які міст створює заново під час завантаження.
- **Оригінали для конвертації, активні оренди виконання й локальні секрети доступу або підписування.** Це не переносна історія. Збережений результат є копією. Це не означає, що резервну копію оригіналу було створено.
- **Лічильник послідовності експорту**, щоденний лічильник для іменування завантажень у `localStorage` (`lolly-export-seq`). Його не включено до `PREF_KEYS`, тож він ніколи не переноситься в пакеті.

Індикатор сховища показує той самий поділ. Збережені сеанси, Мої зображення та Результати файлів і версії входять до пакета. Кеш ресурсів, попередні перегляди інструментів і закріплення для офлайну можна відтворити, тому вони залишаються на пристрої.

## Дані організації з Lolly Work

Цей пакет є резервною копією особистої бібліотеки пристрою. Пакет не є резервною копією екземпляра **Lolly Work**. Облікові записи організації, політики доступу, спільні проєкти, версії каталогу, погодження, завдання рендерингу й записи аудиту зберігаються в цьому сервісі. Підключіться знову й увійдіть, щоб відновити доступ до спільної роботи. Імпорт особистого пакета не надає такого доступу.

Оператори створюють резервні копії, зберігають і стирають серверні дані за власними посібниками Lolly Work: [Резервне копіювання й відновлення](/info/work-operations.html#backup-and-restore) та [Сховище Lolly Work і життєвий цикл даних](/info/work-data-lifecycle.html). Очищення чи експорт даних пристрою не виконує жодної з цих серверних операцій.

## У різних оболонках

`data-transfer.ts` читає й записує лише через міст можливостей (`host.profile`, `host.state`, `host.assets`) і спільні налаштування `localStorage`. Той самий модуль читає й записує спільну оболонку формату у вебі та в настільних і мобільних застосунках, використовуючи IndexedDB або файлову систему. Необов'язкові частини історії з'являються лише там, де доступний їхній адаптер. Імпорт позначає непідтримувану частину як пропущену. Набір тестів без графічного інтерфейсу перевіряє спільні частини через міст у пам'яті, а транзакції історії також мають тести в справжньому браузері.

Ця гарантія не поширюється на дві оболонки:

- **CLI для одноразового запуску** не має що переносити: його стан зберігається в пам'яті й існує протягом одного виклику.
- **TUI** зберігає стан у `~/.lolly` (сеанси, папки, профіль). Його подання Profile записує власний простіший архів резервної копії: `saved-state/<slot>.json` для кожного сеансу плюс `profile.json` і `folders.json`, без маніфесту, без `formatVersion` чи `minReader` і без карти цілісності. Читач цього формату відхиляє такий архів як «не резервну копію Lolly», хоча назви схожі (`lolly-backup-<stamp>.zip`). Узгодження цих двох форматів є відомим невирішеним питанням.

## Ще не переноситься

Нові види переносних даних можуть згодом додаватися як додаткові частини (новий `formatVersion`, той самий `minReader`). Дизайн-системи вже переносяться так: як `design-systems.json` разом зі своїми користувацькими ресурсами.

Дві назви зарезервовано для даних, які ще не переносяться:

- **`tokens.json`** мав би містити документ токенів дизайну [W3C DTCG](https://tr.designtokens.org/format/) з його групами, наборами й темами, у форматі, який [імпортує та експортує Penpot](https://help.penpot.app/user-guide/design-systems/design-tokens/). Власні токени бренду користувача вже переносяться як ресурс `user/tokens/brand` у `assets.json`, а токени дизайн-системи переносяться разом з її записом.
- **`penpot/`** зарезервовано для прийнятого файлу Penpot або його частини, що стосується Lolly, представленої як інструмент.

## Частини історії

Обидві частини історії необов'язкові й мають власні версії.

::: details Історія створення (v3)
Ручні резервні копії з вебінсталяції з історією створення містять `revision-history.json` із власною схемою `{ version: 1, documents, revisions, recoveries }`. Він переносить збережені ID, канонічні знімки вхідних даних, позначки версій, растрові попередні перегляди й окремі чернетки авторів. Адаптер історії фіксує поточні сеанси та їхні головні ревізії в одній транзакції читання, а `sessions.json` використовує ті самі поточні знімки для старіших читачів.

Відновлення перевіряє SHA-256 і кількість байтів вмісту, унікальність ідентифікаторів, зв'язки документів і головних ревізій, ланцюжки предків, часові позначки, типи попереднього перегляду й ліміти, перш ніж зафіксувати архів однією транзакцією. Посилання на батьківські ревізії, видалені під час ущільнення, можуть бути відсутні. Наявна поточна робота ніколи не замінюється без повідомлення: коли твір є з обох боків, та сторона, що не залишається поточною, стає захищеною чернеткою.

Архів має ліміт перенесення 384 MiB. Ліміти сховища застосовуються без обрізання збережених контрольних точок. Експорт записує `revision-history.json` і `sessions.json` частинами, з тими самими байтами, які дає один виклик `JSON.stringify`, тож текст файлу ніколи не утримується цілком. Файл історії, який перевищив би ліміт, відкидається в момент перевищення, і відтоді лише підраховується його розмір. Потім архів створюється знову без найстаріших автоматичних контрольних точок, які підсумок експорту рахує як `checkpointsLeftOut`, або створення архіву відхиляється.

Оболонка без цієї можливості відновлює звичайні сеанси й повідомляє, що частину історії пропущено. Історія в нативній файловій системі не підтримується, доки її адаптер не забезпечить стійкі транзакції історії. Гості в приватній співпраці не мають стійкої історії чи архіву відновлення.

Синхронізація особистих знімків не включає історію створення. Застосування знімка до локального документа з історією зберігає його попередній робочий стан як окрему чернетку відновлення й анулює токен запису кожного відкритого редактора. Його незмінні контрольні точки залишаються на пристрої. Це захищає локальну історію під час заміни знімком. Це не об'єднує паралельні історії пристроїв.

Історичні посилання на ресурси зберігаються, а рендеринг і далі знаходить ресурси через наявну бібліотеку цільового пристрою. Цей архів ще не гарантує точних старих байтів ресурсів чи старих рендерів інструментів. Байти версій ресурсів і результатів файлів переносяться у власній частині резервної копії.
:::

::: details Збережені версії та результати файлів (v2)
Необов'язкова частина історії містить `{ version: 2, assetVersions: [...], operations: [...], batches: [...] }`, а читачі також приймають попередню структуру history-v1 без пакетів. Кожен знімок містить сталий ID ресурсу й точну версію, час збереження, довжину в байтах і шістнадцятковий SHA-256, а також запис ресурсу, чиї `_file` та необов'язковий `_credentialFile` вказують на двійкові частини. Операції переносять відомості про оригінальний файл, запит, звіт, часові позначки й необов'язковий `_file` результату. Назви серверних частин сховища, дескриптори OPFS та оренди виконання не переносяться. Читачі, які знають лише історію v1, відхиляють нову версію історії до імпорту, тож належність до пакетів ніколи не втрачається без повідомлення.

Маніфести пакетів фіксують кожне вибране джерело до обробки, зокрема непрочитані файли, скасовані елементи, невдалі спроби зарезервувати місце для результату й перервану роботу. Кожен елемент має сталий ID операції, посилання на джерело та відомості про нього, запитану назву виводу й остаточний звіт. Непрочитане джерело має заявлені відомості, а не вигаданий хеш. Імпорт перевіряє ідентичність елемента та узгодженість із кожним перенесеним звітом операції. Звіти Lolly Batch залишаються доступними після видалення окремих результатів, але квитанція не означає, що байти її виводу ще зберігаються.

- **Спочатку перевірка.** Кожен відомий запис історії, звіт і файл за посиланням перевіряється до будь-якого запису під час імпорту профілю чи ресурсів. Відсутні байти й невідповідність SHA-256 спричиняють помилку, навіть якщо оболонка формату не має карти цілісності. Витягнуті облікові дані залишаються масивами байтів, зокрема під час імпорту зі старіших засобів запису, які серіалізували їх як об'єкти з числовими ключами.
- **Поточна робота.** Виконувані операції стають у резервній копії записами про переривання, зі звітом про збій і без результату. Відновлення ніколи не перезапускає фонову роботу й не імпортує активну оренду. Для повторної спроби потрібно знову вибрати оригінальний файл, який перевіряється за записаним SHA-256, якщо він є.
- **Сховище.** Відновлені результати фіксують свої байти й метадані разом в IndexedDB. Звичайні нові результати використовують OPFS, де доступно, із запасним варіантом в IndexedDB. Імпорт ніколи не замінює наявну активну операцію.
- **Ліміти резервної копії.** Експорт потоково записує ці байти в архів, але відновлення все ще розпаковує всю резервну копію в пам'яті, тому ліміти залишаються: **256 MiB вмісту історії**, **4 MiB метаданих історії**, щонайбільше **100 операцій**, **100 пакетів** і **2,000 знімків**. Експорт явно відхиляє завелику чи неповну історію й ніколи не пропускає її без повідомлення. Завантажте важливі версії й результати по одному, перш ніж видаляти старіші локальні копії. Ці ліміти не є виміряною гарантією пікового використання пам'яті на телефонах.
- **Локальні обмеження.** Локальна історія результатів має ліміт 512 MiB і 100 записів. Знімки ресурсів мають окремий ліміт 512 MiB і щонайбільше 20 історичних версій на ресурс, а байти витягнутих облікових даних враховуються в цьому ліміті. Відновлення дотримується цих лімітів і ніколи не витісняє наявні дані користувача без повідомлення.
- **Метадані пакетів.** Локальні метадані пакетів мають окремий ліміт 4 MiB, щонайбільше 100 маніфестів і 20 елементів на пакет. Елементи в очікуванні резервують місткість для метаданих із межею 32 KiB для звіту кожного елемента. Це логічний ліміт, а не гарантія дискового простору браузера: реальна помилка квоти показується, а звіт у пам'яті залишається доступним для завантаження. Повторна спроба для елемента пакета створює новий пакет, не перезаписуючи старий звіт. Видалення запису пакета не видаляє байти окремих результатів чи ресурси бібліотеки.
- **Результати в бібліотеці.** Конвертовані результати можна додати до бібліотеки без нормалізації чи перекодування, з прикріпленими хешами джерела й виводу та зв'язком з операцією. Повторні додавання використовують незмінену копію, а відредагована копія ніколи не перезаписується. Растрові зображення можуть започаткувати новий документ Lolly Design, який використовує поточний ID ресурсу бібліотеки. Забезпечення точного закріплення версій у всьому середовищі виконання Lolly Design і шляху URL є окремою роботою. Результати SVG, HTML, PDF і ZIP зберігаються як непрозорі файлові ресурси, без надання їм статусу довіреного інтерактивного чи векторного вмісту.
- **Де це видно.** **Convert → Recent file operations** показує використання історії, звіти, завантаження й менеджер версій, який також знаходить попередні версії видалених ресурсів бібліотеки. Відновлення знімка створює нову поточну версію й зберігає вибраний знімок. **Налаштування → Preferences → Storage** рахує результати й версії окремо від кешів, які можна видалити.
- **Очищення.** Явне очищення тимчасових файлів видаляє лише байти, що належать операціям і на які немає посилань. Поточні записи захищають свої файли, а нові файли OPFS мають годинний пільговий період. Збережені результати й знімки ресурсів не очищуються автоматично.

Старіші читачі й далі приймають оболонку формату v2 (`minReader: 1`) і відновлюють відомі їм частини, рахуючи непідтримувані частини історії як пропущені. Для повного відновлення історії потрібна оболонка з адаптером `fileHistory`, внутрішнім інтерфейсом оболонки, а не можливістю `HostV1`, доступною інструментам. Справжнє відновлення між двома пристроями охоплює локальна контрольна перевірка Chromium. Відновлення у встановлених настільних застосунках і застосунках iOS та Android ще потребує окремого приймального тестування.
:::
