# 데이터 전송 - `lolly-backup` 번들

Lolly 사용자가 쌓아온 모든 것은 **기기에** 있어요 - 계정도 없고 클라우드도 없어요. 데이터 전송 번들은 그 가치를 옮기는 방법이에요. 한 설치본에서 내보내고, 파일을 어떤 수단으로든(USB, AirDrop, 자신에게 보내는 이메일, 네트워크 공유) 옮긴 뒤, 다른 설치본에서 가져와요. 파일 자체가 전송 수단이에요. 대상은 오프라인이든 온라인이든 상관없어요. 서버와는 아무것도 통신하지 않으니까요.

![The two buttons that move a whole install: Export my data writes one zip, Import data reads it back](/t/url-shot?url=%2F%23%2Fsettings%3Ffocus%3Dstorage-section&width=1440&height=1800&dpi=192&waitMs=2400&css=.store-manages%7Bdisplay%3Anone%7D&walker=1&format=svg&cropSelector=%23storage-section%20.storage-subsection&dark=1&filename=pd-transfer-controls)

이 페이지는 형식 명세예요. 최종 사용자용 안내는 [작업 찾기 및 복구 → 다른 기기로 작업 옮기기](/info/find-your-work.html#move-your-work-to-another-device)를 참고하세요. 구현체는 [`shells/web/src/data-transfer.ts`](../shells/web/src/data-transfer.ts)이고, [`tests/data-transfer.test.ts`](../tests/data-transfer.test.ts)가 왕복 계약을 고정해요.

> **범위.** 번들은 *사용자 데이터*를 담을 뿐 카탈로그 도구는 담지 않아요. 도구와 카탈로그 자산은 별도로 동기화되며 대상에 이미 존재한다고 가정해요(최악의 경우 더 높은 버전으로); 사용자가 직접 만든 도구는 `profile.json` 안에 담겨 이동해요. 가져오기는 절대 카탈로그 도구를 설치하거나 업그레이드하지 않아요.

## 목표

- <!--i:box--> **하나의 형식, 모든 셸.** 웹 PWA, Tauri 데스크톱/모바일 앱, 그리고 앞으로 나올 셸들은 모두 같은 봉투와 지원되는 부분 스키마를 공유해요. 선택적 부분은 각 셸의 캐퍼빌리티에 달려 있으며, 지원하지 않는 부분은 보고돼요. 각 캐퍼빌리티 브리지가 그 뒤에 있는 저장소 어댑터를 제공해요.
- <!--i:shieldcheck--> **이동을 견뎌요.** 전송 중 손상되거나 잘린 번들은 가져오기 시 크게 실패할 뿐, 절대 절반만 복원되지 않아요.
- <!--i:clock--> **이번 버전보다 오래 살아남아요.** 구버전 앱도 신버전 번들 중 자신이 인식하는 부분은 가져올 수 있어요. 진짜로 호환되지 않는 형식은 깔끔하게 거부돼요.
- <!--i:check--> **병합해도 안전해요.** 이미 사용 중인 설치본에 가져오기를 해도 번들에 없던 항목은 절대 지워지지 않아요.

## 봉투(envelope)

번들은 평범한 `.zip`이에요. 다운로드 파일명은 소유자 이름을 따라요 - `LollyTools-<First>-<Last>-<YYYY-MM-DD>-<n>.zip`(예: `LollyTools-Ada-Lovelace-2026-06-26-1.zip`) - 그래서 백업이 쌓인 다운로드 폴더도 알아보기 쉬워요. 이름과 성 부분은 프로필에서 가져오며 설정되지 않으면 생략돼요. 프로필이 없으면 `LollyTools-2026-06-26-1.zip`이 되고, 이름만 있으면 `LollyTools-Ada-2026-06-26-1.zip`이 돼요. 각 부분은 파일명에 안전한 토큰으로 정제돼요(유니코드 문자/숫자는 유지하고 공백/구두점은 제거하며 최대 32자로 제한). `<n>`은 일별, 기기별 시퀀스라 같은 날 반복 내보내기도 충돌 없이 순서를 유지해요. [`shells/web/src/data-transfer.ts`](../shells/web/src/data-transfer.ts)의 `backupFilename()`이 이름을 만들어요. zip의 내용물은 이름과 무관하게 동일해요. 내부 구성:

| 경로 | 필수 여부 | 내용 |
|---|---|---|
| `manifest.json` | 예 | 형식 id, 버전, 개수, 부분별 무결성 정보. 리더가 가장 먼저 보는 것. |
| `profile.json` | 설정된 경우 | 사용자의 `me` 레코드 전체: 이름, 연락처, 헤드샷 참조, 플래그에 더해 폴더, 휴지통, 프로젝트 청사진, 사용자 템플릿과 사용자가 만든 도구, 즐겨찾기, 숨긴 도구, 언어와 이모지 선택. `host.profile`로 읽음. |
| `sessions.json` | 예 | 저장된 모든 세션: 슬롯, 도구 id/버전, 라벨, 썸네일(data-URL), 전체 입력 데이터. `host.state`로 읽음. |
| `assets.json` | 예 | 업로드된 각 자산(이미지, 폰트, 브랜드 토큰, 로고, 다운로드 저장 사본)의 메타데이터. 각각 `assets/blobs/` 아래의 바이트를 가리킴. |
| `assets/blobs/<n>.<ext>` | 자산별 | 원본 자산 바이트(이미지와 폰트 파일). 이미 압축된 형식이라 압축하지 않고 저장. 확장자는 겉모습일 뿐. `assets.json`의 MIME이 신뢰 정보. |
| `assets/blobs/<n>.c2pa` | 존재하는 경우 | 추출된 Content Credentials를 정확한 바이너리 바이트로 저장한 것. 자산 레코드의 `_credentialFile`이 참조함. 이는 기기 서명 키가 아님. |
| `design-systems.json` | 존재하는 경우 | 이 설치본에서 만들거나 추가한 디자인 시스템을 `{ active, records }`로 저장. 가져올 때 id로 병합되며, 번들의 활성 선택은 대상에 자체 디자인 시스템이 없을 때만 적용됨. |
| `file-history.json` | 선택 | 버전 관리되는 자산 스냅숏, 완료된 파일 작업 보고서, 완전한 배치 매니페스트. 이 히스토리 부분은 자체 버전을 가지며, 셸 내부의 `fileHistory` 백업 어댑터가 제공함. |
| `revision-history.json` | 선택, 수동 백업 | 안정적인 창작물 ID, 보존된 체크포인트, 썸네일, 계속 갱신되는 복구 초안. 지원되는 경우 `host.state.history.backup`이 제공함. |
| `file-history/versions/` | 스냅숏별 | 이전 자산 바이트와 추출된 크리덴셜. 현재 자산이 여전히 존재하는지와는 무관함. |
| `file-history/results/` | 완료된 작업별 | 정확한 출력 바이트. 변환 대상으로 선택된 원본 파일은 보존도, 포함도 되지 않음. |
| `prefs.json` | 예 | 사용자 소유의 로컬 환경설정: `theme`, `sidebarWidth`, `ct-metrics` 활동 집계. |
| `lolly.txt` | 예 | Lolly 없이 zip을 여는 사람을 위한 번들의 사람이 읽기 쉬운 요약(개수, 프로필, 파일명). 내보낼 때마다 다시 생성되고 가져올 때 인식되므로, 건너뛴 부분으로 취급되지 않음. 무결성 맵 *이후에* 작성되므로 그 맵의 대상에서는 제외됨. |

번들을 평범한 zip으로 만든 건 의도적이에요. 어떤 전송 수단을 거쳐도 손상 없이 살아남고, 어떤 압축 해제 도구로도 내용을 살펴볼 수 있으니까요.

`profile.json`은 가장 작은 부분이면서 앱에서 리더가 가장 먼저 보게 되는 부분이에요. 작성자가 한 번 채워 넣는 정보와, 도구가 그 정보를 사용하도록 허용하는 옵트인이에요.

## `manifest.json`

```json
{
  "format": "lolly-backup",
  "formatVersion": 3,
  "minReader": 1,
  "app": "lolly",
  "exportedAt": "2026-06-22T09:30:00.000Z",
  "counts": { "profile": true, "sessions": 2, "userAssets": 4, "prefs": 3, "assetVersions": 1, "fileOperations": 1 },
  "integrity": {
    "profile.json": "sha256-…",
    "sessions.json": "sha256-…",
    "assets.json": "sha256-…",
    "assets/blobs/0.bin": "sha256-…",
    "file-history.json": "sha256-…",
    "file-history/versions/0.bin": "sha256-…",
    "file-history/results/0.bin": "sha256-…",
    "prefs.json": "sha256-…"
  }
}
```

| 필드 | 의미 |
|---|---|
| `format` | 항상 `lolly-backup`. 이 값이 없는 파일은 "Lolly 백업이 아님"으로 거부됨. |
| `formatVersion` | 이 번들이 **작성될 때** 사용한 레이아웃. 구성 요소나 형태가 바뀌면 올라감. 리더는 이 값으로 판단하지 **않음**. |
| `minReader` | 이 번들을 **안전하게** 가져오는 데 필요한 최소 리더 버전. 리더가 실제로 판단 기준으로 삼는 필드. |
| `app` | 생성한 앱 id, 진단용. |
| `exportedAt` | 번들이 생성된 ISO 타임스탬프. |
| `counts` | 작성자가 무엇을 담았는지, 표시와 정합성 확인용. |
| `integrity` | 선택 사항. `manifest.json`을 제외한 모든 부분을 그 **압축 해제된** 바이트의 SRI 형식 `sha256-<base64>` 다이제스트에 매핑. |

## 버전 정책(하위 호환성)

`formatVersion`과 `minReader`를 분리한 덕분에 구버전 설치본을 소외시키지 않고도 형식을 확장할 수 있어요.

- 리더는 `manifest.minReader ≤` 자신의 리더 버전일 때 번들을 가져와요. 번들이 명시적으로 더 새로운 리더를 요구할 때만("앱의 최신 버전이 필요합니다"라며) 거부해요.
- **추가적인** 변경 - 새로운 *선택적* 부분, 또는 새로운 선택적 매니페스트 필드 - 은 `formatVersion`을 올리지만 `minReader`는 그대로 둬요. 구버전 앱도 자신이 인식하는 모든 부분은 여전히 가져와요. 인식하지 못하는 부분은 (아래 참고) 조용히 버려지는 게 아니라 건너뛰어져요.
- **호환성을 깨는** 변경 - 부분을 잘못 가져오면 데이터가 손상되거나, 이전엔 선택적이던 부분이 필수가 되는 경우 - 은 `minReader`를 올려요. 구버전 앱은 처리할 수 없는 것을 가져오려 시도하는 대신 깔끔하게 거부해요.
- 미래의 번들이 `formatVersion`은 설정하되 `minReader`를 생략하면, 리더는 보수적으로 `formatVersion` 기준으로 판단해요(변경을 호환성을 깨는 것으로 취급).

> **작성자를 위한 경험칙:** 기존의 모든 리더가 여러분의 추가 사항을 무시하고도 여전히 올바르게 동작한다면 그건 추가적인 변경이에요 - `formatVersion`을 올리고 `minReader`는 그대로 두세요. 그렇지 않다면 `minReader`를 올리세요.

## 무결성

`manifest.integrity`가 있으면 리더는 **아무것도 쓰기 전에** 나열된 각 부분의 SHA-256을 검증해요. 불일치("무결성 검사 실패")나 누락된 부분("불완전")이 있으면 가져오기 전체가 중단돼요 - 부분 복원은 없어요. 이는 파일 전송 과정에서 생길 수 있는 손상을 잡아내요(잘린 AirDrop 전송, 첨부파일을 다시 인코딩한 이메일 게이트웨이, 불량 USB 섹터 등).

무결성 검증은 설계상 최선을 다하는 방식이에요. Web Crypto를 사용할 수 있는 곳(모든 보안 브라우저 컨텍스트와 최신 Node)에서만 작성되고, 맵과 Web Crypto가 둘 다 있을 때만 검증돼요. 맵이 없는 번들 - 예를 들어 무결성 기능이 생기기 전의 번들 - 은 그대로 가져와져요. "검증할 수 없음"은 절대 "손상됨"으로 취급되지 않아요.

매니페스트는 자기 자신도, 다시 생성되는 `lolly.txt` README도 나열하지 않아요. 다이제스트는 매니페스트가 보증하는 부분만 다뤄요.

## 가져오기 의미론

가져오기는 **병합 후 덮어쓰기**이며, 전체 교체가 절대 아니에요.

- 대상에 있는 기존 데이터는 그대로 남아요.
- 충돌하는 키 - 프로필, 세션 슬롯, 업로드된 이미지 id - 는 가져온 사본으로 교체돼요.
- 프로필은 하나의 레코드라서 통째로 교체돼요: 대상의 폴더, 휴지통, 템플릿, 즐겨찾기, 숨긴 도구는 번들의 것이 돼요. 대상에는 있었지만 번들에는 없던 세션은 정리되지 않은 채로 프로젝트 최상위에 남아요.
- 과거 자산 버전과 작업 ID는 불변의 예외예요: 반복 가져오기는 멱등적이며, 이미 다른 바이트/히스토리를 가리키는 ID는 덮어쓰지 않고 거부돼요. 동일한 현재 자산을 다시 가져와도 버전은 그대로 유지돼요. 변경된 현재 자산은 반드시 다른 버전을 가져야 해요.
- 창작 히스토리도 예외예요: 충돌하는 현재 문서나 리비전 정체성이 있으면 프로필, 자산, 환경설정이 바뀌기 전에 그 복원이 먼저 중단돼요. 동일한 내용을 다시 가져와도 저장 공간은 늘지 않아요. 충돌하는 아카이브는 별도의 설치본에서 복원해 내용을 확인하고 복사하세요.
- 번들에 없던 것은 아무것도 건드리지 않아요. 대상에는 있었지만 번들에는 없던 세션은 가져오기 이후에도 살아남아요.

저장된 세션은 이미지와 자동으로 다시 연결돼요. 자산 참조는 id로 유지되며, 업로드된 이미지가 복원된 뒤 브리지가 이를 다시 해석해요(어차피 그렇게 해야 해요. `blob:` URL은 새로고침을 견디지 못하니까요).

가져오기 요약은 `{ profile, sessions, userAssets, prefs, skipped, failedAssets }`를 보고해요. `failedAssets`는 복원하지 못한 업로드 자산의 수예요(예를 들어 기기 저장 공간이 가득 찬 경우). 이는 `skipped`와 다른데, `skipped`는 이 빌드가 인식하지 못한, 하위 호환성을 위해 남겨둔 더 새로운 작성자의 부분 개수를 세는 거예요. UI는 `skipped`를 그대로 보여줘요("… · N개의 최신 항목을 건너뜀"), 그래서 복원 결과가 무엇을 남겼는지 정직하게 알려줘요.

파일 히스토리가 있으면 요약에는 `assetVersions`, `fileOperations`, `failedHistory`도 함께 담겨요. 저장 공간 고갈이나 불변 ID 충돌은 부분 복원을 일으킬 수 있으며, UI는 사용자에게 원본 백업을 보관해 두라고 알려줘요. 클라우드 동기화는 부분적이거나 지원되지 않는 복원 이후 적용된 리비전을 앞으로 진행시키지 **않으므로**, 스냅숏은 재시도를 위해 계속 사용할 수 있는 상태로 남아요. 복원은 프로필/세션/자산/히스토리 저장소 전체에 걸친 단일 트랜잭션이 아니에요.

## 창작 히스토리(v3)

히스토리를 지원하는 웹 호스트의 수동 백업에는 자체 `{ version: 1, documents, revisions, recoveries }` 스키마를 가진 `revision-history.json`이 포함돼요. 여기에는 보존된 ID, 표준화된 입력 스냅숏, 버전 스탬프, 래스터 미리보기, 그리고 작성자별로 분리된 초안이 담겨요. 히스토리 어댑터는 현재 세션과 그 head를 하나의 읽기 트랜잭션으로 가져와요; `sessions.json`은 더 오래된 리더를 위해 같은 현재 스냅숏을 사용해요.

복원은 아카이브를 하나의 트랜잭션으로 커밋하기 전에 페이로드 SHA-256과 바이트 수, 고유 정체성, 문서/head 관계, 계보, 타임스탬프, 미리보기 유형과 한도를 확인해요. 압축된 부모 참조는 없을 수 있어요. 기존 현재 작업물은 가져오는 문서와 일치해야 하며, 충돌은 조용히 대체하지 않고 거부돼요. 아카이브의 384MiB 전송 한도는 명시적으로 확인되며, 저장 공간 한도는 보존된 체크포인트를 잘라내지 않으면서 적용돼요. 전체 백업은 여전히 메모리 내 ZIP 구현을 사용하며, 스트리밍 방식의 아카이브가 아니에요.

요약에는 `revisions`와 `recoveryDrafts`가 추가돼요. 이 기능이 없는 셸은 일반 세션만 복원하고 히스토리 부분은 건너뛴 것으로 보고해요. 네이티브 파일시스템 히스토리는 해당 어댑터가 지속적인 히스토리 트랜잭션을 제공하기 전까지는 지원되지 않아요. P2P 게스트 상태에는 지속적인 히스토리도, 복구 아카이브도 없어요.

개인 스냅숏 동기화는 창작 히스토리를 명시적으로 제외해요. 히스토리를 가진 로컬 문서에 스냅숏을 적용하면 그 이전 작업 상태는 별도의 복구 초안으로 보존되고, 열려 있는 에디터의 쓰기 토큰은 모두 무효화돼요. 불변 체크포인트는 기기에 그대로 남아요. 이는 스냅숏 교체 중에 로컬 히스토리를 보호하기 위한 것이며, 여러 기기의 히스토리를 병합하지는 않아요.

과거 자산 참조는 유지되지만, 렌더링은 여전히 대상의 기존 라이브러리를 통해 자산을 해석해요. 이 아카이브는 아직 예전 자산 바이트나 예전 도구의 렌더링 결과를 정확히 보장하지 않아요. 자산 버전과 파일 결과 바이트는 계속해서 기존의 별도 백업 부분을 통해 이동해요.

## 저장된 버전과 파일 결과(v2)

선택적인 히스토리 부분에는 `{ version: 2, assetVersions: [...], operations: [...], batches: [...] }`가 담겨요; 리더는 batches가 없는 이전 history-v1 형태도 받아들여요. 각 스냅숏은 안정적인 자산 ID와 정확한 버전, 저장 시각, 바이트 길이, 16진수 SHA-256을 식별하고, 여기에 `_file`과 선택적인 `_credentialFile`이 바이너리 부분을 가리키는 자산 레코드가 더해져요. 작업은 원본 파일의 사실 정보, 요청, 보고서, 타임스탬프, 선택적인 결과 `_file`을 담지만, 저장소 백엔드 이름, OPFS 핸들, 실행 리스는 이동하지 않아요. history-v1만 지원하는 오래된 리더는 배치 소속 정보를 조용히 누락시키는 대신, 가져오기 전에 새 히스토리 버전을 거부해요.

배치 매니페스트는 한 번도 읽히지 않은 파일, 취소된 구성원, 결과 저장 공간 확보에 실패한 경우, 중단된 작업을 포함해 처리 전에 선택된 모든 소스를 기록해요. 각 구성원은 안정적인 작업 ID, 소스 참조/사실 정보, 요청된 출력 이름, 확정된 보고서를 가져요. 읽히지 않은 소스는 지어낸 다이제스트가 아니라 선언된 사실 정보를 가져요. 가져오기는 구성원의 정체성과, 함께 전달된 작업 보고서와의 일관성을 검증해요. 개별 결과가 명시적으로 제거된 뒤에도 배치 보고서는 계속 사용할 수 있지만, 그 영수증이 출력 바이트가 여전히 저장되어 있음을 의미하지는 않아요.

- 알려진 모든 히스토리 레코드, 보고서, 참조된 파일은 프로필이나 자산 가져오기 쓰기가 일어나기 전에 검증돼요. 봉투에 무결성 맵이 없더라도 누락된 바이트와 불일치하는 SHA-256은 실패로 처리돼요. 추출된 크리덴셜은, 이를 숫자 키 객체로 JSON 직렬화했던 오래된 작성자로부터의 가져오기를 포함해, 여전히 바이트 배열로 유지돼요.
- 실행 중이던 작업은 백업 안에서 설명이 담긴 실패 보고서와 함께, 결과 없이 중단된 레코드가 돼요. 복원이 백그라운드 작업을 다시 시작하거나 활성 실행 리스를 가져오는 일은 절대 없어요. 재시도하려면 원본 파일을 다시 선택해야 하며, 기록된 SHA-256이 있으면 그것과 대조해요.
- 복원된 결과는 바이트와 메타데이터를 함께 IndexedDB에 커밋해요. 일반적인 새 결과는 가능한 경우 OPFS를 사용하고, IndexedDB로 폴백해요. 기존에 실행 중인 작업이 가져오기로 대체되는 일은 절대 없어요.
- 히스토리 ZIP 조립은 여전히 메모리에서 이뤄져요: 현재 한도는 **히스토리 페이로드 256MiB**, **히스토리 메타데이터 4MiB**, 최대 **작업 100개**, **배치 100개**, **스냅숏 2,000개**예요. 내보내기는 크기를 초과하거나 불완전한 히스토리를 명시적으로 거부하며, 조용히 생략하는 일은 절대 없어요. 오래된 로컬 사본을 지우기 전에 중요한 버전/결과는 개별적으로 다운로드하세요. 이 한도들은 휴대폰의 최대 메모리 사용량을 측정해 보장하는 것이 아니에요.
- 로컬 결과 히스토리는 512MiB 예산과 100개 레코드 상한을 가져요. 자산 스냅숏은 별도로 512MiB 예산을 가지며 자산당 최대 20개의 과거 버전까지예요; 추출된 크리덴셜 바이트는 그 스냅숏 예산에 포함돼요. 복원은 이 한도를 존중하며 기존 사용자 데이터를 조용히 몰아내는 일은 절대 없어요.
- 로컬 배치 메타데이터는 별도로 4MiB 예산을 가지며, 최대 100개의 매니페스트와 배치당 20개의 구성원까지예요. 대기 중인 구성원은 메타데이터 용량을 예약하며, 구성원별 보고서에는 32KiB 상한이 있어요. 이는 논리적인 예산이지 브라우저 디스크 공간을 보장하는 것이 아니에요; 실제 할당량 실패는 그대로 드러나며 메모리상의 보고서는 계속 다운로드할 수 있어요. 배치 구성원을 재시도하면 오래된 보고서를 덮어쓰지 않고 새 배치가 만들어져요. 배치 레코드를 지워도 개별 결과 바이트나 라이브러리 자산은 지워지지 않아요.
- 변환된 결과는 정규화나 재인코딩 없이 명시적으로 라이브러리에 추가할 수 있어요. 소스/출력 해시와 작업 관계가 그 자산에 함께 따라와요. 반복해서 추가해도 변경되지 않은 사본은 재사용되며, 편집된 사본이 덮어써지는 일은 절대 없어요. 래스터 이미지는 새 Design 문서를 시작할 수 있어요. 그 문서는 현재 라이브러리 자산 ID를 사용해요: Design의 런타임과 URL 경로 전체에 걸쳐 정확한 버전 고정을 강제하는 일은 아직 별도의 작업으로 남아 있어요. SVG/HTML/PDF/ZIP 결과는 이 인계 과정에서 불투명한 파일 자산으로 유지되며, 신뢰할 수 있는 인터랙티브/벡터 콘텐츠로 승격되지 않아요.
- **Convert → Recent file operations**는 히스토리 사용량, 보고서, 다운로드, 버전 관리자를 보여줘요. 이 관리자는 삭제된 라이브러리 자산의 이전 버전도 찾아줘요. 스냅숏을 복원하면 선택한 스냅숏은 그대로 둔 채 새로운 현재 버전이 만들어져요. **설정 → 저장 공간**은 일회성 캐시와는 별도로 결과와 버전을 집계해요.
- 명시적인 임시 파일 정리는 작업이 소유하고 어디서도 참조되지 않는 바이트만 지워요. 현재 레코드는 자신의 파일을 보호하며, 최근 OPFS 파일에는 1시간의 유예 기간이 있어요. 저장된 결과와 자산 스냅숏은 자동으로 지워지지 않아요.

이전 리더도 여전히 v2 봉투(`minReader: 1`)를 받아들여 익숙한 부분들을 복원하고, 지원하지 않는 히스토리 부분은 건너뛴 것으로 셈해요. 완전한 히스토리 복구에는 `fileHistory` 어댑터를 갖춘 셸이 필요해요; 이는 셸 내부의 접합부이지, 도구를 향한 새로운 `HostV1` 캐퍼빌리티가 아니에요. 실제 기기 두 대 간 복원은 로컬 Chromium 게이트로 검증돼요; 설치된 Tauri/iOS/Android의 복구 승인 테스트는 별도로 진행돼요.

## 이동하지 않는 것

- **카탈로그 캐시**(다운로드된 자산 메타데이터와 blob, 도구 인덱스) - 대상에서 무료로 다시 동기화됨.
- **카탈로그 도구와 카탈로그 자산** - 범위 밖이며, 대상에 이미 있다고 가정함. 사용자가 추가한 브랜드 토큰, 폰트, 로고는 사용자 자산이라 함께 이동함.
- **`blob:` / 객체 URL** - 로드 시 브리지가 다시 생성함.
- **변환 원본, 실행 중인 실행 리스, 그리고 기기 로컬 접근/서명 비밀 정보** - 이동 가능한 히스토리 페이로드가 아님. 저장된 결과는 사본일 뿐, 원본 소스가 백업되었다는 보장은 아님.
- **내보내기 시퀀스 카운터** - 일별 다운로드 이름 붙이기용 카운터(`localStorage` 키 `lolly-export-seq`)는 로컬 전용 편의 기능이라 `PREF_KEYS`에서 제외돼 있어 번들에 절대 실리지 않음.

저장 공간 미터는 같은 구분을 항목별로 보여줘요. 저장된 세션, 내 이미지, 그리고 파일 결과 및 버전은 번들에 실려요. 그 아래의 자산 캐시, 도구 미리보기, 오프라인 고정 항목은 모두 다시 만들어낼 수 있어서 남겨져요.

## 셸 간 보장

`data-transfer.ts`는 오직 캐퍼빌리티 브리지(`host.profile`, `host.state`, `host.assets`)와 공유 `localStorage` 환경설정만을 통해 읽고 써요. 같은 모듈이 IndexedDB나 파일시스템 저장소를 거쳐 웹과 Tauri 모두에서 공통의 봉투를 읽고 써요. 선택적인 히스토리 부분은 해당 어댑터를 사용할 수 있는 곳에서만 나타나며, 지원하지 않는 부분은 가져올 때 건너뛴 것으로 보고돼요. 헤드리스 테스트 스위트는 인메모리 브리지를 대상으로 공통 부분을 검증하고, 히스토리 트랜잭션은 실제 브라우저 테스트도 별도로 있어요.

두 셸은 서로 다른 이유로 이 보장 밖에 있습니다:

- **원샷 CLI**는 유지할 것이 없습니다 - 상태는 호출마다 메모리에만 존재하고 사라집니다.
- **TUI**는 실제로 상태(`~/.lolly`: 세션, 폴더, 프로필)를 유지하며 Profile 화면에서 백업도 가능하지만, 자체적으로 더 *단순한* 아카이브를 씁니다: 세션별 `saved-state/<slot>.json`에 `profile.json`과 `folders.json`을 더한 형태로, 매니페스트도 `formatVersion`/`minReader`도 무결성 맵도 없습니다. 이 형식으로는 **가져올 수 없으며** - 리더는 이를 "Lolly 백업이 아님"으로 거부합니다 - 게다가 이름까지 비슷해(`lolly-backup-<stamp>.zip`) 혼동을 줍니다. 둘을 통합하는 것은 알려진 과제입니다.

## 예약된 확장 지점

봉투(envelope)는 설계상 매니페스트와 이름 붙은 파트들의 집합이므로, 나중에 새로운 종류의 이동 가능한 데이터도 **호환성을 깨지 않고** 실릴 수 있습니다. 이들은 추가되는 파트로 들어오며(새 `formatVersion`, 동일한 `minReader`), 오늘의 리더는 알아보지 못하는 것을 건너뜁니다. 이들은 아직 구현되지 않았습니다. 이름을 여기서 미리 예약해 두어, 이들이 도입될 때 형식이 일관되게 유지되도록 합니다.

- **`tokens.json` - 디자인 토큰.** [W3C DTCG](https://tr.designtokens.org/format/) 디자인 토큰 문서입니다([Penpot이 가져오고 내보내는](https://help.penpot.app/user-guide/design-systems/design-tokens/) 형식으로, `$value`/`$type`/`$description`을 가진 토큰들이 그룹, 세트, 테마로 구성됩니다). 번들 안의 토큰 세트를 이용하면 사용자가 세션과 함께 브랜드 기본값을 설치 간에 옮길 수 있습니다. (사용자 자신의 브랜드 토큰은 오늘날에도 이미 `assets.json`의 `user/tokens/brand` 자산으로 이동하고 있습니다. 이 부분은 세트와 테마를 포함한 DTCG 문서 전체를 담게 됩니다.) 장기적으로는, 가져온 토큰 세트가 도구와 팔레트 애셋이 참조하는 일급 소스가 됩니다.
- **`penpot/` - 가져온 Penpot 파일.** Penpot 파일(또는 그 안에서 추출한, Lolly와 관련된 부분집합)을 가져와 *도구로서* 노출하기 위한 예약 디렉터리입니다. 번들은 가져온 정의를 담아, 사용자의 다른 데이터와 함께 이동합니다.

이 예약된 이름들과 위의 파트들을 벗어난 것은 리더 입장에서 알 수 없는 파트이며, 손대지 않고 `skipped`에 집계됩니다.
