# Lolly for DAM vendors and implementation partners

**Lolly can extend a digital asset management system into governed content production.** Customers keep the DAM as their source of record and make permitted variants of its exposed assets in Lolly tools. Lolly Work adds organisation-controlled access, shared projects, review and delivery.

A partner can help customers use their approved library in more everyday production. [Content sovereignty](/info/content-sovereignty.html) describes the customer's control over that arrangement, including the choice to keep or change systems.

<!--i:eti-users-->
## A joint customer workflow

A designer creates an event-card layout and chooses which fields other people may change. The DAM administrator curates the source imagery and logos. A marketer selects an exposed asset, enters the event details and makes the required variants. A configured delivery can then submit the exact finished file for approval before sending it to an organisation destination.

Template constraints, source access, use rights and output approval each need their own check. [The worked production sequence](/info/dam-production.html) shows how to evaluate them together.

## Agree responsibilities before connecting

| Responsibility | What a joint implementation should establish |
|---|---|
| Source authority | Which DAM records and files are authoritative, with supported approval and availability mappings |
| Member access | The audience exposed through a shared source credential, tested across listings, previews and originals |
| Production rules | Who maintains the design system, templates and editable inputs |
| Review | Who approves source use, catalog admission and finished delivery, as separate decisions |
| Writes and retries | Supported destinations, separate write credentials and reconciliation after an uncertain result |
| Operations | Hosting, support ownership, release compatibility, refresh expectations and recovery |
| Portability | What the customer can keep or move, with source licences and missing history made explicit |

## What can be offered today?

Lolly and Lolly Work are open source under MPL-2.0. A partner can evaluate and operate them with a customer's design system and supported catalog sources. Hosting, integration work, maintenance and support still need an agreed owner and budget.

The [provider directory](/info/work-provider-guides.html) lists implemented sources and open live checks. Supported sources are normally read-only. [Organisation delivery](/info/work-delivery.html) has separate adapters.

::: note A provider entry is not an endorsement
Nor is it a certification or an announced commercial partnership.
:::

SUSE reports successful use of Brandfolder in the [deployment account](/info/suse-brandfolder.html). That evidence does not qualify unrelated tenants or operations.

## Evaluate one recurring task

Choose a real customer task and a small set of permitted assets. Before you start, agree how to observe success. For example, a marketer produces the required variants without a manual file handoff, and an administrator can withdraw further access.

Run the [source qualification checks](/info/work-provider-tenant-check.html), demonstrate the workflow and record unresolved limitations. Measure approved-asset reuse, completed outputs, correction work and administrator effort only where the deployment's privacy and telemetry choices permit. Compare the results with the customer's existing process.

## Does the customer have to stay with the DAM?

The customer chooses. The integration can stay in place. Supported migration paths exist for a later move. Portability is part of the product's purpose, so cover it in the integration agreement. Do not assume that read access grants permission to copy or redistribute every source.

Start with [Use Lolly with your existing DAM](/info/use-with-dam.html). For technical evaluation, continue to [Lolly Work architecture](/info/work-overview.html) and [What Lolly Work does today](/info/work-status.html).
