# How SUSE connected Brandfolder to Lolly

**SUSE successfully connected Brandfolder to Lolly and used that connection to introduce Lolly alongside an existing content library and approval practices.** The integration supported change management for administrators responsible for different content approvals before a planned move away from Brandfolder.

This account records the Lolly maintainer's deployment experience, reported on **31 October 2026**. The migration target is the end of December 2026. The connection is in use. Migration is planned, not reported complete.

<!--i:eti-users-->
## Start from the system people already administer

A new creative platform brings decisions about who curates assets, which content needs approval and where people make the next version. An existing DAM has both files and established administrative responsibilities.

At SUSE, the Brandfolder integration helped Lolly inherit that existing system during adoption. While the connection gave continuity and access to the library, administrators had time to work through changes to their content-approval responsibilities.

## What the connector provides

The public [Brandfolder source guide](/info/work-provider-brandfolder.html) describes the implementation. Assets enter the Lolly Work catalog as references, selected by exposure rules. Brandfolder remains the source of record while connected. Current attachments keep their file identities when selected in Lolly.

The guide does not establish which optional field or action the SUSE deployment exercised. The maintainer's account confirms successful use and its role in adoption. The two Brandfolder availability-field mappings still need the separate live check in the guide. Outbound Brandfolder delivery is a different adapter with its own qualification requirements.

## How another organisation can apply the approach

Identify the administrators and approval responsibilities before connecting the library. Introduce one bounded production workflow, retain the existing source authority and test access and withdrawal. Use the adoption period to decide which responsibilities should stay with the DAM and which belong with production or delivery.

Keeping the DAM is a supported outcome. Moving later is another choice, with its own checks for originals, metadata, permissions, history and recovery. The SUSE experience supports connecting first and allowing time for organisational change. It does not promise that another tenant will have the same mappings or migration requirements.
