# Експорт і формати

Як отримати готовий файл з інструмента - вибір потрібного формату, налаштування розміру виводу і що робить кожна опція. Як і все інше, **експорт відбувається на вашому пристрої**; нічого не завантажується на сервер.

## Як працює експорт

Попередній перегляд *і є* файлом. Коли ви експортуєте, хост рендерить це полотно у вибраний формат і видає завантаження (або кладе результат у буфер обміну). Інструмент пропонує лише ті формати, які задекларував його автор, а селектор приховує будь-які, які ваш браузер не може створити (див. [Video](#video)).

Файл створюють три шляхи. Більшість інструментів **рендерять полотно** у вибраний формат. Текстові та формати даних (HTML, MD, TXT, JSON, CSV, ICS, VCF) натомість **генеруються з вмісту інструмента**, а не растеризуються із зображення. А утиліти конфіденційності (напр., *Strip Hidden Data*) використовують третій шлях: файл, який вибираєте *ви*, трансформується побайтово на пристрої і повертається без змін - без полотна, без водяного знака і без доданих метаданих походження, бо це вже ваш власний файл.

Дії в елементах керування експортом:

- <!--i:download--> **Download** - зберегти файл (основна дія).
- <!--i:photos--> **Copy** - помістити зображення в буфер обміну, щоб одразу вставити в Slack, лист, документ. Там, де браузер не може копіювати зображення, натомість відбувається завантаження з відповідним повідомленням.
- <!--i:folder--> **Save** - зберегти поточний дизайн як сеанс інструмента у вашій бібліотеці.
- <!--i:link--> **Share** - відкриває **діалог Share**: копійовне посилання, яке відтворює дизайн, перемикачі на момент переходу (повноекранний режим, панель експорту, завантаження або копіювання при відкритті) та опційний **Shortest link**, який пакує весь стан у компактний токен (див. [URL Mode](/info/url-mode.html)).

(Які саме з цих дій з'являються, вибирає автор інструмента; типовий набір - Copy, Download і Save.)

### Рендер багатьох за один раз

Один експорт - це один файл, але можна відрендерити **багато** за один прохід - кожен доставляється як один `.zip`:

- <!--i:folder--> **Projects → Render folder** експортує кожен збережений сеанс у папці (та її підпапках) як один вкладений zip; **Render selection** робить те саме для будь-якого множинного вибору; один збережений сеанс рендериться просто у власний файл. Batch/Pro не потрібні - див. [Using Lolly → Projects](/info/using.html).
- <!--i:layers--> **Batch (Pro)** рендерить сітку наборів вхідних даних - усі варіанти одного шаблону за раз.

Збережений сеанс також можна повторно поширити як посилання на інструмент із Projects (воно відновлює URL інструмента зі збережених вхідних даних), тож посилання відкриває його з точно тими самими налаштуваннями.

## Вибір формату

Поле імені файлу і селектор формату розташовані вгорі панелі як одна пара `name.format`, і селектор перелічує лише формати, задекларовані автором цього інструмента.

![The filename field fused to the format picker, so the export reads as one name.format pair](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26options&width=1440&height=900&dpi=192&waitMs=2000&format=svg&cropSelector=.filename-extension&walker=1&dark=1&filename=exp-format-picker)

| Що вам потрібно… | Формат | Чому |
|---|---|---|
| Чіткі логотипи / зображення, що масштабуються | **SVG** | Вектор - безмежно масштабується, малий розмір, редагований |
| Вектор для Office / застосунків Windows | **EMF** | Вставляється як редагований вектор у PowerPoint / Word; текст залишається живим і редагованим, а Google Drive відкриває його в Google Drawings для Slides |
| Вектор для друку / дизайнерських застосунків | **EPS**, або **EPS (CMYK)** | Вектор PostScript для Illustrator / друкарських процесів |
| Вектор для різальних / CAD-верстатів | **DXF** | Лазерні різаки, вінілові плотери, ЧПУ - контурні шляхи в міліметрах |
| Редагована презентація | **PowerPoint** (PPTX) | Рідний редагований текст + фігури, зображення та вектори залишаються придатними для вилучення |
| Курс, який можна імпортувати в LMS | **SCORM** (LMS) | Zip-архів із маніфестом, стартовою сторінкою, слайдами та озвученим відео з субтитрами - з презентації Design |
| Редагований текстовий документ | **Word** (DOCX) або **OpenDocument** (ODT) | Справжні абзаци та заголовки, які текстовий редактор може й далі редагувати (Doc Studio) |
| Фотографія або зображення загального призначення | **PNG** (без втрат) або **JPG** (менший розмір) | Універсальний растр |
| Менші сучасні зображення | **WebP** / **AVIF** | Краще стиснення, альфа-канал |
| Друк | **PDF**, або **Print PDF** (CMYK) | Справжній розмір сторінки; CMYK для друкарського процесу |
| Растр для друкарського преса | **Print TIFF** (CMYK) | Пікселі DeviceCMYK для RIP |
| Анімація для вебу | **GIF** | Працює всюди, більші файли |
| Анімація з повним кольором + справжньою альфою | **APNG** | Анімований PNG - без обмеження палітри, справжня прозорість |
| Анімація, найменший файл | **Animated WebP** | Повний колір + альфа, краще стиснення, ніж у GIF або APNG |
| Анімований вектор, що масштабується | **Animated SVG** | Самодостатній; циклічно відтворюється в браузері або `<img>`, без кодека, будь-якого розміру |
| Відео для соцмереж / поширення | **MP4** або **WebM** | Найкраща якість на байт (див. нижче) |
| Форматований текст / підпис електронної пошти | **HTML** | Вставляється відформатованим у поштові клієнти |
| Простий вміст | **MD** / **TXT** | Лише текст |
| Подія календаря | **ICS** | Імпортується в будь-який застосунок календаря |
| Візитка контакту | **VCF** | Імпортується в Контакти / адресні книги |
| Структуровані дані для повторного імпорту | **JSON** / **CSV** | Дає змогу відтворити вміст інструмента без втрат |
| Фавікон | **ICO** | Іконка сайту кількох розмірів (**ZIP** об'єднує кілька форматів) |

Перший рядок - це поширений випадок. Логотип-напис, набраний вашим брендовим шрифтом, експортується як SVG, де кожна літера - це обведений контур, а не піксель, тож він лишається чітким і на розмірі візитівки, і на розмірі обгортки будівлі з того самого файлу.

## Розмір і одиниці друку

За замовчуванням експорт використовує рідний піксельний розмір інструмента. Там, де інструмент відкриває **розміри**, ви можете задати ширину × висоту і **одиницю**:

- **px** (за замовчуванням) - точні пікселі.
- **mm · cm · in · pt · pc** - фізичні/друкарські розміри. З фізичною одиницею ви також задаєте **DPI** (за замовчуванням **300** для друку); рушій конвертує коректно для кожного формату - **PDF** стає справжньою сторінкою такого розміру, **растр** рендериться з правильною кількістю пікселів для DPI (і вбудовує роздільну здатність), **SVG** зберігає фізичну одиницю з viewBox у пікселях.

Щоб отримати растр вищої роздільної здатності, введіть більшу ширину/висоту або виберіть фізичну одиницю й підвищте DPI (пікселі = розмір × DPI). Перемикача масштабу в один клік немає.

Приклад: ширина `210`, висота `297`, одиниця `mm` → сторінка A4.

## Стоп-кадри з композиції з часовою шкалою

**Композиція з часовою прив'язкою** - таймлайн [Sequence](/info/using.html#timeline-sequence) у Design, або будь-який артборд, керований таймлайном, - це рухома річ, тож статичний експорт має відповісти на питання «який саме момент?». Правило очевидне: **кадр у позиції повзунка відтворення**. Поставте повзунок там, де потрібне зображення, і експортуйте; що бачите, те й отримаєте.

Коли потрібен не один момент, поле **Frames** з'являється поряд із розміром виводу (лише для композиції з часовою шкалою і лише для формату стоп-кадру - PNG, JPG, WebP, SVG чи PDF). Залиште `1` для кадру плейхеда. Підвищте значення - і отримаєте стільки стоп-кадрів, вибраних із рівними інтервалами по всій послідовності:

- **Растр і SVG** повертаються одним **zip** - `<name>-01.png`, `-02.png` і так далі.
- **PDF** повертається **одним документом з такою кількістю сторінок**.

Корисно для розкадровки, аркуша мініатюр, контрольного аркуша для перегляду чи соціальної каруселі, вирізаної просто з відеомонтажу.

Вибірка береться в **середній точці** кожного інтервалу, а не на межах, тому що перша мить послідовності часто є переходом входу, який ще не встиг проявитися, а остання - станом після завершення всіх кліпів; вибірка з країв витратила б два кадри на майже порожні. Кількість обмежена **64** (контрольний аркуш призначений для читання людиною), а будь-яке безглузде значення, введене в поле, відкочується до `1`, а не завершує експорт помилкою. Кожен кадр - звичайний стоп-кадр, тож Content Credentials, imprint, фізичні одиниці і DPI поводяться точно так само, як і при одиночному експорті.

Поле **Frames** - це сьогоднішній спосіб отримати аркуш. Рушій резервує відповідний параметр URL `cuts`, але жодна оболонка ще не читає його з посилання, тож поширене посилання завжди відкривається на кадрі плейхеда - див. [URL Mode](/info/url-mode.html#contact-sheets-cuts).

## Багатосторінковий PDF

Деякі інструменти створюють **багатосторінковий PDF-документ** замість одного зображення - обкладинку, вміст, що переливається на стільки сторінок, скільки потрібно, і задню сторінку, все в одному файлі (див. інструмент *Booklet*). Кожна сторінка - це **справжня сторінка PDF** розміром під бокс цієї сторінки, тож читачі та принтери отримують справжні сторінки, а не одне довге зображення.

- **Сторінки з вмісту.** Додавайте блоки тексту й зображень; нові сторінки створюються автоматично в міру заповнення блоків, і ви можете примусити будь-який блок почати нову сторінку.
- **Справжні розміри сторінок.** Виберіть A4, US Letter або A5 (книжкова орієнтація - двоколонковий макет розрахований саме на неї) - кожна сторінка та експортований PDF рендериться точно в цьому розмірі.

Багатосторінкові PDF - це RGB-документи, і вони не несуть міток обрізки/випуску під обріз - ті належать шляху **Print PDF** для однієї сторінки вище. Вони несуть ті самі **метадані PDF/X-4**, що й кожен експорт PDF (бокси сторінки, XMP, ідентифікатор документа, вихідний намір sRGB із вбудованим профілем), і пропонують **Content Credentials** (нижче) - в інструменті *Booklet* цей параметр вибрано заздалегідь.

## Створення багатьох речей одночасно

У Lolly є три різні способи роботи з великими обсягами, і вони розв'язують різні задачі - пакетне редагування є повноцінною можливістю платформи, а не тим, що кожен інструмент вигадує заново:

- <!--i:document--> **Один дизайн × таблиця рядків → один багатосторінковий документ.** Інструменти з вхідними даними `table` (як-от *Battlecards*) автоматично перетворюють кожен рядок на сторінку - вставте таблицю з вашої таблиці даних, отримайте PDF розміру презентації. Ваш справжній пакетний редактор лишається таблицею даних: виправте десять рядків там, вставте знову. Сам інструмент ніколи не керує сторінками.
- <!--i:layers--> **Один дизайн × файл даних → багато окремих файлів.** Пакетна сітка `/pro` бере CSV і рендерить один експорт *на рядок* - бейджі з іменами, сертифікати, по одному файлу кожен.
- <!--i:sliders--> **Багато різних активів, що редагуються поряд.** *Multi-edit* відкриває кілька збережених сеансів в одному перегляді для скоординованих правок у різних дизайнах.

Правило: рядки одного дизайну, яким місце в **одному документі** → інструмент на основі таблиці; рядки, які мають вийти як **окремі файли** → `/pro`; **різні дизайни**, яким потрібна та сама правка → multi-edit. (Запланована опція рендеру «combine media» з'єднає перші два - об'єднуючи експорти того самого формату в один PDF, одне відео чи контрольний аркуш для перевірки.)

## PowerPoint (PPTX)

Design, Markdown Slides, Booklet, Doc Studio, Chart і Diagrams можуть експортувати **презентацію PowerPoint** - один слайд на сторінку. Мета не в тому, щоб отримати піксель-у-піксель точний знімок екрана, а в тому, щоб передати колезі презентацію, яку той справді зможе **редагувати і з якої зможе вилучати елементи**. Тому кожна сторінка розкладається на рідні об'єкти:

- <!--i:font--> **Текст** стає справжніми, **редагованими текстовими полями PowerPoint** - з розміром шрифту, кольором, накресленням, курсивом і вирівнюванням з макета - тож ви можете виправити одруківку чи змінити стиль просто в PowerPoint.
- <!--i:pentool--> **Вектори** (логотипи, іконки, знак SUSE) вбудовуються як **справжні SVG-зображення** - вони лишаються чіткими за будь-якого розміру, і PowerPoint навіть може застосувати до них *Convert to Shape*.
- <!--i:photos--> **Зображення** передаються у власній роздільній здатності як окремі зображення, які можна витягти (герой-зображення з обрізкою `cover` зберігає повне зображення позаду обрізки, тож ви можете переобрамити його), з будь-якою обробкою на зображенні (фільтри, змішування), точно збереженою.
- <!--i:layers--> **Фони, рамки та лінії** стають справжніми формами прямокутників/ліній.

![Панель експорту з вибраним PowerPoint: один слайд на сторінку, текст і фігури залишаються редагованими](/t/url-shot?url=%2F%23%2Ftool%2Fdeck-studio%3Foptions&width=1440&height=900&dpi=192&waitMs=2500&drive=click%3A%5Bdata-fmt-trigger%5D%3Bwait%3A400%3Bclick%3A%5Bdata-fmt%3D%22pptx%22%5D%3Bwait%3A800&cropSelector=.export-popup&walker=1&format=svg&dark=1&filename=exp-pptx)

Макет є приблизним за задумом - мета полягає у точному, придатному для повторного використання **вмісті**, а не в закріпленому знімку екрана. Усе, що walker не може виразити нативно (складна відфільтрована чи замаскована ділянка), вбудовується як зображення, тож нічого не втрачається. Презентація має єдиний розмір слайда, взятий з першої сторінки.

PowerPoint - це також спосіб **потрапити всередину**. Перетягніть `.pptx` на будь-яку поверхню завантаження і виберіть потрібні слайди - кожен стає активом, який можна розмістити, доопрацювати колірно або розвинути далі. **Markdown Slides** створює нову презентацію з Markdown (і видає фірмовий шаблон `.pptx`), а утиліта **Rebrand** перетемлює наявну презентацію на місці - палітру теми, жорстко задані кольори та шрифти - не торкаючись її діаграм, SmartArt чи анімацій, і повертає `.pptx`. Див. [Імпорт дизайну → Презентації та документи](/info/design-import.html#decks-and-documents).

## Penpot

Будь-який інструмент, що вміє експортувати SVG, може також експортувати **файл Penpot** (`.penpot`) - документ, готовий до подальшого редагування в Penpot, а не лише для перегляду.

- <!--i:layout--> З **Design** кожен фрейм стає Penpot **board**, кожен бокс на ньому переноситься як власна редагована фігура - прямокутник, еліпс, текст, зображення або контур, - а результат потрапляє як придатний до повторного використання **component** у панелі Assets, готовий знову витягнути перетягуванням.
- <!--i:pentool--> З інструмента, чий рендер - **проста геометрія** - векторні інструменти на кшталт QR Code, Street Map, Wordmark і Palette Lab, - кожен контур, прямокутник, текстовий рядок і градієнт переноситься так само, як власна редагована фігура.
- <!--i:font--> З інструмента, що вибудовує свій рендер у **HTML**, **текст залишається текстом** - один редагований текстовий об'єкт Penpot на рядок, а не контур і не плоска картинка. Елемент оформлення, для якого в Penpot немає конструкції - складна ілюстрація, живий canvas, - переноситься окремо як зображення, тож текст і бокси навколо нього ніколи не сплощуються. Ціла компоновка, яку Penpot не може точно розділити, все одно може перейти як одне зображення з повною точністю, тож нічого ніколи не втрачається.
- <!--i:palette--> Колір або шрифт, який фігура **успадковує від токена бренду**, залишається **пов'язаним** із цим токеном у файлі: змініть токен у панелі Tokens в Penpot - і кожна фігура, що його успадковує, перефарбується разом, тоді як одноразовий буквальний колір залишається точно таким, яким був. Кольори та типографіка бренду також потрапляють у панель **Assets**, а повний набір токенів дизайну - у панель **Tokens** - той самий набір токенів DTCG, який використовує власна палітра Lolly. Далі Penpot зберігає власну копію: правка, внесена в його панелі Tokens, повертається в бренд через [імпорт Brand Studio](/info/design-import.html), а не сама собою.

| Що ви створили | У Penpot |
|---|---|
| Текст | Редаговані текстові об'єкти - виправте одруківку або перестилізуйте |
| Фігури, контури, градієнти, зображення | Власні редаговані векторні фігури |
| Колір або шрифт із токена бренду | Живе посилання на токен - змініть токен, і кожна фігура, що його успадковує, підхопить зміну |

## SCORM (пакети курсів)

- <!--i:layout--> **Слайди**, по одному зображенню на артборд, у векторному вигляді там, де артборд це дозволяє, і в растрі лише там, де ні.

## DXF (файли для різання)

Векторні інструменти (Brand Lockup, QR Code, Street Map, Wayfinding Signage, Pose Geeko, зв’язки логотипів, Diagram Builder) можуть експортувати у **DXF** - формат обміну AutoCAD R12, який читають лазерні різаки, вінілові плотери й ПЗ ЧПК/САПР. Геометрія записується як контурні **шляхи в міліметрах** (криві сплощені з тонким допуском), текст перетворюється на контури-шляхи, а колір зіставляється з найближчим індексом кольору AutoCAD (який зазвичай визначає інструмент/операцію на різаку). DXF - це лише лінійна графіка - фотографічна чи фільтрована область не має форми шляху різання і відкидається (Lolly попереджає), тож використовуйте SVG/PDF, коли потрібно зберегти растровий вміст.

Street Map - найпростіший приклад: увесь дизайн вже складається зі штрихів, тож кожна дорога і канал стають шляхом для різання без нічого зайвого.

## Анімований SVG

Інструменти анімації (Animated Ad, Lottie Ad) можуть експортувати **Animated SVG** - самодостатню *векторну* анімацію. На відміну від GIF/APNG/WebP (які растеризують кожен кадр у пікселі), анімований SVG складає векторні знімки з вбудованими CSS keyframes, тож він **масштабується до будь-якого розміру без кодека і без зовнішнього середовища виконання** - він циклічно відтворюється у вкладці браузера чи в `<img>`. Текст лишається контурним, тож рендериться будь-де. Він поділяє з анімованими форматами елементи керування **тривалістю** / частотою кадрів, і (будучи важчим на кадр, ніж растр) використовує нижчу типову частоту кадрів.

## Прозорість

Інструменти, що підтримують це, пропонують перемикач **прозорого фону** (наприклад, *No BG*). Прозорість зберігається у PNG, WebP, AVIF, SVG (статичному й анімованому), APNG і Animated WebP. JPG і PDF завжди непрозорі, а TIFF зводиться на білий фон (на чорний - на шляху HDR, див. нижче).

## Кольорові простори

Два різні питання, які варто розрізняти: у яких кольорових просторах Lolly вміє **читати й мислити**, і у які вона **записує**.

**Читання.** Скрізь, де записано колір - у таблиці стилів інструменту, у заливці імпортованого SVG, у значенні дизайн-токена, у тіні чи градієнті всередині CSS-скорочення - Lolly читає повний словник **CSS Color 4**: `#hex`, `rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, іменовані кольори CSS та `color()` у визначених просторах - `srgb`, `srgb-linear`, `display-p3`, `a98-rgb`, `prophoto-rgb`, `rec2020`, `xyz-d50`, `xyz-d65` - включно з компонентами, записаними як ключове слово `none`. Один парсер робить це для всієї платформи, тож браузер і кожен walker експорту однаково розуміють, що означає рядок кольору.

Це важливіше, ніж здається, бо браузер перетворює сучасний CSS у сучасний CSS. Напишіть `color-mix(in oklab, …)`, і Chrome обчислить `oklab(…)`; використайте брендовий токен, збережений як `oklch()`, і це буквальне значення, яке побачить walker експорту. Кольори в таких формах читаються коректно, а не відкидаються - на відміну від walker, який розумів лише `rgb()`, експортуючи брендований текст чорним, втрачаючи забарвлені панелі та лінії таблиць і сприймаючи `oklch(0.7 0.1 200) 0px 2px 4px` як зсув тіні 0.7 на 0.1.

**Мислення.** Колірна математика відбувається перцептивно, а не в сирих каналах. Виведення палітри, рампи, гармонії та контраст працюють у **OKLCH/OKLab**, а колір поза гамою повертається в діапазон власним алгоритмом зіставлення гами CSS Color 4 - зменшенням насиченості з перевіркою перцептивної відстані - а не обрізанням каналів, тому яскравий колір осідає на найближчому кольорі, який ви б справді прийняли, а не на сплощеному. Градієнти інтерполюються в просторі, який ви вибираєте (OKLab за замовчуванням, або `oklch`, `lab`, `lch`, `srgb`, `srgb-linear`, `hsl`, з напрямком руху відтінку для полярних), а змішування **попередньо помножене**, тому перехід у прозорість зберігає правильний колір замість того, щоб темніти в бік чорного по дорозі. Один інтерполятор обслуговує і попередній перегляд, і обхідники експорту - саме це зупинило конічний градієнт від того, щоб змішуватися по-одному на екрані й по-іншому в експортованому файлі.

**Запис.** Вихід свідомо вужчий за вхід, бо файл має бути прочитним будь-чим, що його відкриє, а простір лише тоді *заявляється* на виході, коли числа справді були в нього перетворені. Екранні та веб-формати записуються як **sRGB** і позначаються відповідно; поліграфічні формати записуються як **CMYK** відносно названої умови друку (нижче); а шлях HDR - це **Rec.2100 PQ** (вище). Колір широкого гамута, що доходить до експорту, мапується в sRGB, а не позначається неправильно - перенесення `color(display-p3 …)` у векторний файл є запланованим розширенням, а не тим, що сьогоднішні експорти заявляють, ніби роблять. Градієнт, створений в OKLab, на виході *випікається* у звичайні sRGB-стопи, з додатковими стопами, вставленими лише там, де sRGB помітно відхилявся б від перцептивної кривої, бо `<linearGradient>` SVG і осьове затінення PDF не мають параметра простору інтерполяції, щоб передати задум. Одне авторське значення, три рендерери, жодного розходження.

## Кольорові профілі

Щоб кольори точно відтворювалися в застосунках з керуванням кольором (друкарнях, Photoshop, браузерах), експорти **позначаються кольоровим профілем**:

- **PNG / JPG** несуть вбудований ICC-профіль **sRGB** - кольоровий простір, у якому справді рендериться попередній перегляд - тож здогадуватися не доводиться. (Лише позначення; пікселі не перекодовуються.)
- **Print PDF (CMYK)** заявляє цільову **умову друку** у своєму *OutputIntent* (типово *Coated FOGRA39*), повідомляючи RIP/друкарні, як слід читати її фарби CMYK. Брендові зразки з виміряними значеннями фарби конвертуються точно; інші кольори використовують стандартну апаратну конверсію. Ця заява - це *назва*: жоден профіль CMYK не постачається з Lolly, а PDF/X-4 вимагає вбудованого профілю, тож названа умова записує output intent, не заявляючи відповідність PDF/X-4. Завантажте власний профіль CMYK і оберіть його рядок **Embed** у елементі керування кольоровим профілем - і він буде вбудований як *DestOutputProfile* файлу - і тоді PDF справді може бути PDF/X-4, і заявляє про це, коли решта файлу це дозволяє. Три речі утримують цю заяву, зберігаючи output intent (RIP усе одно його потребує): RGB-графіка, яку прохід CMYK не зміг конвертувати, текст підпису поля перевірки `prov` (намальований стандартним шрифтом, який не вбудовується, і X-4 не робить винятку для таких) і пароль **Strong**, оскільки X-4 забороняє шифрування. Умова, яку файл заявляє, тоді зчитується з цього профілю: зареєстрована назва - там, де профіль її підтверджує, `Custom` під власною назвою профілю - там, де ні, тож файл ніколи не може називати одну умову друку, несучи виміри іншої.
- **Print TIFF (CMYK)** записує непозначені пікселі **DeviceCMYK** і фіксує ту саму умову друку як провенанс у метаданих TIFF (*ImageDescription*), а не вбудовує профіль. Той самий елемент керування кольоровим профілем керує обома форматами CMYK - TIFF узагалі не може вбудувати профіль друку, тож рядок **Embed** записує туди лише власну назву профілю і нічого більше.
- **TIFF (RGB)** - це простий, нестиснений sRGB-варіант - растр без втрат при обраному DPI для архіву чи циклу редагування, з провенансом, записаним у тих самих метаданих TIFF. Будь-яка прозорість зводиться на білий (цей профіль не несе альфа-канал). Як і CMYK TIFF, він лише для настільних платформ, оскільки браузери не можуть показати попередній перегляд TIFF, а мобільні завантаження заходять у глухий кут.
- **SVG**, **EMF**, **EPS** і **DXF** - незалежні від роздільної здатності й профілю вектори без вбудованого профілю - кольори SVG прості sRGB, кольори EMF та EPS - апаратний RGB (а **EPS (CMYK)** записує наївний DeviceCMYK), а **DXF** несе найближчий AutoCAD Color Index. (SVG, EPS і DXF, як і PDF, перетворюють будь-який текст на векторні контури, тож результат рендериться навіть там, де шрифт не встановлено. EMF натомість зберігає текст ЖИВИМ за замовчуванням - справжні записи тексту метафайлу, які лишаються редагованими у Office та Google Slides, повертаючись до контурів лише для рядків, які формат не може виразити; опція панелі експорту "Outline fonts" примусово застосовує контури всюди.) **SVG** також відтворює CSS `box-shadow` з HTML - кожна зовнішня тінь малюється позаду блока, зі зсувом/розтягненням і гаусовим розмиттям, що відповідають браузеру, а внутрішні тіні малюються всередині так само.

Це автоматично - жодного налаштування підлаштовувати не потрібно. Мініатюри та попередні перегляди пропускають позначку, щоб лишатися компактними. Один профіль *дійсно* є вибором, бо він змінює пікселі, а не просто позначає їх - див. **HDR** нижче.

## HDR (яскраві кольори)

Звичайні експорти - це sRGB: білий є білим, а насичений брендовий колір настільки ж яскравий, як звичайний білий екрана. На дисплеї з підтримкою HDR над цим є значний запас яскравості, і картка **HDR** у панелі експорту використовує його - ваші брендові кольори та білий текст підсилюються до пікової яскравості, тож вони справді *світяться*, тоді як темні ділянки лишаються темними і надають цьому світінню контрасту.

![Картка HDR у панелі експорту, увімкнена, з відкритими під нею регуляторами White / Reach / Dark lift / Focus](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpng%26hdr%3D1%26options&width=1440&height=900&dpi=192&waitMs=2000&format=svg&cropSelector=.export-hdr&walker=1&dark=1&filename=exp-hdr-card)

- **Формати.** Растрові формати, що мають куди нести сигнал: **PNG**, **JPG**, **AVIF** і **TIFF**. (Не WebP - він 8-бітний і не має робочого шляху декодування HDR, тож PQ WebP просто виглядав би темним. Вектори і PDF взагалі не мають моделі HDR.)
- **Вимкнено за замовчуванням**, на відміну від кольорового тегування - це змінює пікселі, тож є опцією, яку треба ввімкнути свідомо. Позначте картку або передайте `hdr=1` у посиланні для спільного доступу.
- **Що насправді записується.** Пікселі перекодовуються в **Rec.2100 PQ** - первинні кольори BT.2020 із кривою передачі SMPTE ST 2084 (PQ) - і контейнер несе відповідний сигнал, щоб застосунок із керуванням кольором знав, що читати їх саме так: згенерований **профіль ICC v4 із тегом `cicp`** (JPG, TIFF), **фрагмент `cICP`** (PNG) або переписаний бокс `colr` (AVIF). Посилення прив'язане до **перцептивної (OKLab) яскравості**, тож середні й вищі кольори підтягуються до піку, а темні радше заспокоюються, ніж «вибиваються», і зберігається відтінок - фірмовий зелений стає яскравішим, а не м'ятним.
- **Регулятори.** Чотири, з'являються, коли картка ввімкнена: **White** (стеля пікової яскравості, 400-2000 ніт), **Reach** (наскільки глибоко в тони поширюється сяйво), **Dark lift** (наскільки освітлюються темні тони - `0` залишає їх темними) і **Focus** (наскільки насиченим залишається колір після посилення). Вони передаються в тому самому параметрі, що й компактне налаштоване значення - `hdr=1600-60-0-50` означає White 1600, Reach 60, Dark lift 0, Focus 50, - тож налаштований вигляд відтворюваний із посилання.
- **Де ви це побачите.** У переглядачах із керуванням кольором на HDR-дисплеї: Preview / Quick Look / Safari на пристроях Apple, Chrome на HDR-моніторі. На звичайному SDR-екрані файл усе одно виглядатиме як звичайне зображення.
- **Що варто знати перед публікацією.** Багато платформ **перекодовують** те, що ви завантажуєте, і знімають сигнал HDR - соціальні мережі, месенджери, деякі CMS, - через що зображення може виглядати темним або вицвілим. Використовуйте HDR там, де ви контролюєте призначення (сайт, який ви створюєте, відеостіна, презентація на яскравій панелі), а не як типовий варіант для всього.
- **Прозорість.** PNG і AVIF зберігають альфа-канал; JPG, як завжди, непрозорий. Шлях **TIFF** сплющується на **чорний** колір, а не на білий, як шлях SDR, - у PQ білий - це код на 10 000 ніт, тож сплющення на нього обвело б кожен край засліплюючим ореолом.
- **Ті самі байти з термінала.** `--hdr=1` разом з `--export=png` або `--export=jpg` записує 16-бітний PNG у Rec.2100 PQ і JPEG із gain-картою ISO 21496-1 також у [CLI](/info/cli.html), з тих самих кодерів рушія, а не з браузера, - тож інструмент, рідний для `<svg>`, видає файл HDR без жодного Chromium у всьому шляху, і PNG байт-у-байт ідентичний тому, що видає веб-оболонка. AVIF і TIFF поки залишаються експортами лише з веб-оболонки.

## Відео

Анімовані інструменти експортують рух як **MP4**, **WebM** або **GIF** - а там, де пропонується, - **APNG**, **Animated WebP** або векторний **Animated SVG** (вище). Який відеоконтейнер ви побачите, залежить від вашого браузера - список показує лише те, що він справді може записати:

| Браузер | Показує |
|---|---|
| Safari / iOS | **MP4** |
| Firefox | **WebM** |
| Chrome / Edge 126+ / Android | **MP4 і WebM** |
| Старіший Chrome | **WebM** |

GIF працює всюди (чудово для чату/пошти; більший і з меншою кількістю кольорів, ніж відео). Анімовані інструменти також пропонують **Wait** (секунди, щоб дати анімації встановитися перед записом) і **Duration** (тривалість кліпа).

> Спільне посилання `?format=…`, що вимагає контейнер, який ваш браузер не може записати, плавно повертається до іншого і відповідно називає файл.

**Звук.** Відеоекспорти не безмовні. Інструмент може підкласти під кліп **музичну підкладку** - аудіоактив із каталогу, зациклений чи обрізаний до довжини кліпа, з плавним входом/виходом, гучністю й автоматичним приглушенням під власний звук відзнятого матеріалу - а інструменти запису передають живий звук свого відзнятого матеріалу прямо у файл. **MP4** і **WebM** зберігають зведену доріжку; GIF та анімовані формати зображень (APNG, Animated WebP, Animated SVG) безмовні за своєю природою.

## Аудіо

Деякі інструменти експортують **аудіо окремо**, а не лише як відеодоріжку. **Voice Recorder** записує дубль із мікрофона з живим індикатором рівня та м'яким коучингом, потім зберігає його як **MP3** (типово, перекодовано у вашому браузері) або в його власному контейнері - **M4A** (AAC), **OGG** чи **WebM** (Opus), залежно від того, що записав ваш браузер. Як і все інше, кодування відбувається на вашому пристрої - нічого не завантажується.

Аудіо, яке ви *приносите* самі, настільки ж широке. Засіб вибору активів приймає **MP3**, **WAV**, **OGG**/**Opus**, **M4A**/**AAC** і **FLAC** (зберігаються побайтово і декодуються на пристрої), **MIDI** (`.mid` - конвертується при імпорті в крихітну доріжку синтезатора на пристрої) і **трекерні модулі** - **MOD**, **XM**, **IT**, **S3M**, **STM**, **MTM** (декодуються на пристрої вбудованим плеєром, кілька кілобайтів даних пісні). Будь-що з цього може стати **музичною підкладкою** під відеоекспорт або відтворюватися в атмосферному плеєрі Neurospicy Mode.

Аудіо *дійсно* є частиною конвеєра `format=` / `--export=` нижче: `wav`, `mp3`, `m4a` і `opus` - звичайні ідентифікатори формату, тож аудіоекспорт настільки ж придатний для спільного доступу й скриптування, як PNG. На виході - лише звук, без зображення.

## Провенанс і водяний знак

Там, де формат це підтримує, експорти несуть **метадані провенансу** - ПЗ, джерело, назву інструменту та рядок вашого профілю - вбудовані нативно (PNG iTXt, JPEG EXIF, PDF info, SVG `<metadata>`, коментар GIF). Це лише авторство; нічого не завантажується. **Експериментальні** інструменти додатково проставляють видимий водяний знак, застосований хостом, тож його не можна прибрати редагуванням інструменту.

**Lolly Imprint.** Растрові експорти також несуть власний **невидимий піксельний водяний знак** Lolly - *Lolly Imprint* - **увімкнений за замовчуванням**, так само як Content Credentials. Там, де облікові дані та метадані провенансу подорожують *поряд* із пікселями і втрачаються при повторному збереженні, знімку екрана чи знятті метаданих, Imprint живе *всередині* пікселів і переживає повторне стиснення - тож копію зображення можна пізніше все одно розпізнати як створену в Lolly. Це стійка підказка, а не криптографічна гарантія, і вона лише вказує на присутність (не несе персональних даних). Вона їде в **PNG, JPG, WebP, AVIF, TIFF і BMP**, а також у растрах, відрендерених Lolly і скомпонованих у **PDF або PPTX** - ніколи в зображенні, яке вбудували *ви*, лише в тому, що рендерить сама Lolly. Зніміть позначку з картки **Lolly Imprint** у панелі експорту, щоб пропустити це, або передайте `imprint=0` у посиланні для спільного доступу. (Виживання AVIF при перекодуванні ще не відкалібровано; виявлення PDF/PPTX охоплює вбудовані растри Lolly.) [/verify](/verify) виявляє це на пристрої - див. [Ідентичність Content Credentials](/info/content-credentials-identity.html#the-lolly-imprint).

**Стійкий обліковий запис.** Поряд з Imprint є друга, важча позначка: **Durable credential**, яка використовує нейронну модель на пристрої (формат TrustMark), щоб записати ідентифікатор Lolly *в* пікселі, тож зв'язок "створено в Lolly" переживає зняття метаданих, повторне кодування і повторне зчитування інструментами, обізнаними з TrustMark, а також власними інструментами Lolly. Вона **вимкнена за замовчуванням** - на відміну від чистого JavaScript-Imprint, вона коштує нейронного проходу на кожен експорт плюс одноразове завантаження моделі, тож це свідома згода, а не тихий податок. Лише растр (**PNG, JPG, WebP, AVIF, TIFF**), позначається в панелі експорту або передається як `durable=1` у посиланні для спільного доступу. У настільних і мобільних застосунках картка повністю прихована, а не показана як недіюча, бо офлайн немає джерела, звідки завантажити модель.

**Захист вмісту.** У панелі експорту *Password protect*, **C2PA Credentials**, **Lolly Imprint** і **Durable credential** згортаються в одну згорнуту, залежну від формату групу **Content protection**, тож параметри провенансу та захисту файлу живуть в одному місці - група показує лише ті картки, які застосовні до обраного формату, і повністю ховається, якщо жодна з них не застосовна. Позначки друку свідомо *не* входять до неї: це геометрія поліграфічного виробництва, а не захист, тож **Print marks & bleed** - вимір випуску під обріз у міліметрах плюс Crop, Registration, Bleed, Colour bars і Stamp details - зберігає власну картку верхнього рівня на поліграфічних форматах.

![Група Content protection, відкрита для експорту PNG, показує лише застосовні до нього картки](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpng%26imprint%3D1%26options&width=1440&height=900&dpi=192&waitMs=2000&walker=1&format=svg&cropSelector=.export-protection&dark=1&filename=exp-content-protection)

**Перед експортом (поліграфічний preflight).** Увімкніть **Print preflight** (`export-preflight`) у прапорцях функцій свого профілю - він **вимкнений за замовчуванням**, тож людину, яка експортує PNG для повідомлення в чаті, ніколи не заскочать зненацька результати перевірки поліграфії, а панель керування розгортанням ([lolly.work](https://lolly.work)) може ввімкнути його за замовчуванням для своїх учасників - і картка **Before you export** з'являється внизу панелі, безпосередньо над кнопками, щоразу, коли правилам друку є що сказати про завдання: формат, розмір і випуск під обріз, потім зони обрізу й випуску, покриття фарбою, кількість пластин і сторінок, із вердиктом поряд із заголовком. Вона розташована під кожним налаштуванням, бо є твердженням *про* ці налаштування, а не ще одним із них - і вона ніколи не блокує експорт. Вона повідомляє, що зараз побачить друкарня.

**Вартість, розрахована з вашого прайс-листа.** Під preflight - останньою з усіх, усе ще над кнопками - розташована картка, що перетворює ті самі підрахунки на гроші, і лише з цін, які хтось справді надав. Вона зчитує все, що підрахував прохід preflight, незалежно від того, чи ввімкнена сама картка preflight, і потребує виконання двох умов: у завданні є щось, що прайс-лист узагалі може оцінити (пластини, аркуші, площа, сторінки, рядки варіантів чи вихідні файли - тож простий логотип у PNG ніколи цього не показує), **і** присутній **прайс-лист**. Прайс-лист - це JSON-список цін від вашої друкарні. Типова збірка не містить жодного і не має способу завантажити його всередині застосунку: він потрапляє або як актив каталогу, що постачає розгортання, або через опційне розширення прайс-листа, яке вмикає самостійний хостинг чи панель керування. Без прайс-листа нічого не показується - ні підказки, ні порожньої таблиці.

Правило, навколо якого побудовано все це, полягає в тому, що **воно ніколи не вигадує гроші**. Кожна цифра - це тариф, який ви надали, помножений на кількість, яку підрахувала Lolly - `4 пластини × €35.00` - а сума називає власне джерело в тому самому реченні, що й цифра: видавця, якого називає прайс-лист, і дату, якою прайс-лист датує свої тарифи. Немає типової валюти, немає заповнювача і немає нуля, що заміняв би відсутню ціну. Те, що файл каже про себе, лишається переказаним мовленням: *"Файл каже: … Lolly цього не перевіряла."*

А коли чесно порахувати неможливо, робоча таблиця **зникає**, а не деградує до сірої чи заповненої довільно цифри:

- Рядки, які прайс-лист не оцінює, означають **відсутність суми взагалі** - лише заголовок, що повідомляє, скільки з них не оцінено. Часткова сума - не менша відповідь, а неправильна.
- Кількість, що є верхньою межею, а не точним підрахунком, несе позначку **"до"** аж до своєї проміжної суми, тож межа ніколи не видається за точну цифру.
- Тарифи, термін дії яких минув, показують **лише кількості**, доки ви не натиснете *Use these rates anyway* - і тоді дата закінчення терміну дії йде разом із цифрою, тож застарілу суму не можна прочитати як актуальну.
- Відкрито через **посилання** - гроші лишаються прихованими, доки ви не запитаєте їх на цьому пристрої. Ані картка, ані це розкриття ніколи не подорожують у URL - та сама причина, з якої CLI приймає `--rate-card=<file.json>` як прапорець локального файлу, а не як параметр посилання.

Картка - це хром, ніколи не вміст: вона видаляється з кожного етапу експорту, тож не може зрушити жодного пікселя завантажуваного вами файлу. І це арифметика, а не комерційна пропозиція - лише ваша друкарня може її вам надати.

**Складені рендери.** Коли інструмент вбудовує вихід іншого інструменту (наприклад, *Event Name Badge*, що вбудовує *QR Code*), вкладений рендер вбудовується в експорт батьківського - він лишається **справжнім вектором** у SVG і PDF та чітко растеризується у PNG/JPG/WebP. Вбудований дочірній елемент - це проміжний результат: він не отримує *жодного* водяного знака і *жодного* власного провенансу; лише готовий батьківський актив отримує їх. (Композиція охоплює SVG і растрові формати; HTML/MD/TXT не можна компонувати.)

## Захист паролем

Два незалежні типи блокування, обидва повністю на пристрої.

**PDF-пароль на відкриття** - картка *Password protect* на панелі експорту пропонує два рівні:

![Розгорнута картка Password protect під час експорту PDF, з полем пароля та двома рівнями блокування](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpdf%26password%3Ddemo%26options&width=1440&height=900&dpi=192&waitMs=2000&walker=1&format=svg&cropSelector=.export-pdfpass&dark=1&filename=exp-pdf-password)

- **Standard** - базове 40-бітне блокування (RC4). Воно відкривається в *будь-якому* PDF-застосунку, і - будучи легким стримувальним засобом, а не справжнім захистом - може передаватись у посиланні для спільного доступу (у відкритому вигляді, за задумом). Лише RGB `pdf`.
- **Strong** - AES-256 (PDF 2.0). Пароль вводиться під час експорту і **ніколи** не потрапляє в посилання; файл відкривається лише в новіших PDF-застосунках (Acrobat / Preview приблизно з 2018 року), а старіші застосунки можуть повідомляти про пошкодження файлу. Strong також застосовується до **PDF для друку / CMYK** і до **кожного PDF усередині пакетного zip-архіву** (діалог підтвердження пакету збирає пароль). Оскільки PDF/X-4 забороняє шифрування, PDF для друку з блокуванням Strong зберігає CMYK, мітки та вихідні наміри, але втрачає заявку на відповідність PDF/X-4.

Обидва рівні взаємовиключні з Content Credentials (зашифрований PDF не може отримати облікові дані).

**Заблоковані завантаження (весь zip-архів + додаткові рівні захисту)** - експорт у **ZIP** (формат *ZIP* на панелі експорту, який об'єднує кілька форматів інструмента), завантаження **папки** (Projects → Download) або **пакетна сітка** можуть заблокувати весь архів одним паролем на двох рівнях:

- **Standard** - традиційний **ZipCrypto**: відкривається в *будь-якому* засобі розпакування, включно з вбудованим видобуванням Провідника Windows, але слабкий (стримувальний засіб). Його пароль може передаватись у посиланні `?password=`.
- **Strong** - **AES-256** (WinZip AE-2): надійний, але **не** відкривається вбудованим видобуванням Провідника Windows - отримувачу потрібен 7-Zip / WinZip / Keka / macOS. Вводиться під час експорту, ніколи не потрапляє в посилання.

Та сама картка *Password protect* на панелі експорту керує і блокуванням PDF, і блокуванням ZIP, змінюючи формулювання залежно від обраного формату. Один пароль захищає **кожен** елемент - зображення, SVG, усе, включно з PDF (тільки zip-контейнер може захистити файли, що не є PDF, оскільки вони не мають власного блокування). І це **додатковий рівень захисту**: будь-який PDF усередині *також* окремо заблокований AES-256 з тим самим паролем, тому PDF залишається заблокованим навіть після розпакування архіву. Запит з'являється, коли ви починаєте завантаження; порожній пароль означає відсутність блокування.

**Посилання для спільного доступу із захистом паролем** - будь-яке посилання для спільного доступу можна зашифрувати так, щоб відкриття вимагало пароль від отримувача. Весь стан посилання зашифровано AES-256 під ключем, отриманим із пароля (PBKDF2); передається лише шифротекст, тому **пароль ніколи не міститься в посиланні**, а розшифрування відбувається **в браузері отримувача** - сервер, що обслуговує посилання, бачить у URL лише шифротекст, ніколи не пароль і ніколи розшифрований дизайн. Увімкніть це в діалозі **Share**. Зашифроване посилання можна лише *відкрити* в Lolly (його не можна вбудувати як зображення, оскільки цей шлях не може запитати пароль). Див. [URL Mode → Encrypted links](/info/url-mode.html).

## Content Credentials (C2PA)

Експорти можуть містити **Content Credentials** - підписаний маніфест [C2PA](https://c2pa.org), вбудований у файл, що фіксує, у спосіб, стійкий до підробки, що файл створено в Lolly і не змінено відтоді. Це стандартизована версія наведених вище метаданих походження: криптографічна заява (що створило файл, коли, ким і де), прив'язана до хешу байтів файлу, тому будь-яке подальше редагування виявляється переглядачем, що підтримує C2PA. Стандарт курує [Content Authenticity Initiative](https://contentauthenticity.org) (Adobe, BBC, Microsoft, Nikon та інші), тому ті самі облікові дані, які записує Lolly, - це ті самі, що їх упроваджують камери, редакції новин і творчі пакети.

![Картка C2PA Credentials, попередньо позначена, з терміном дії облікових даних поруч](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpng%26c2pa%3D30%26options&width=1440&height=900&dpi=192&waitMs=2000&format=svg&cropSelector=.export-c2pa%5Bdata-c2pa-only%5D&walker=1&dark=1&filename=exp-c2pa-card)

- **Формати.** Кожен контейнер із вбудовуванням C2PA: **PDF** (і RGB, і для друку), **PNG / Animated PNG**, **JPG**, **GIF**, **SVG**, **TIFF** (RGB і для друку), **WebP** (статичний і анімований), **AVIF**, **MP4**, **WebM** і аудіоконтейнери **MP3**, **WAV**, **M4A** і **OGG/Opus** - тож записаний або синтезований голосовий кліп постачається з тими самими обліковими даними, що й зображення. Пакет **ZIP** проставляє їх у кожному підтримуваному елементі окремо, і саме так їх отримує **Animated SVG** (за суттю це звичайний документ SVG; прямий експорт Animated SVG не пропонує власної картки). MP4, AVIF і M4A використовують прив'язку BMFF зі специфікації, а MP3 - зіставлення ID3v2, тому `c2patool` та інші переглядачі, що підтримують C2PA, можуть їх перевірити; **WebM** і **OGG/Opus** ще не мають стандартизованого зіставлення C2PA, тому Lolly переносить маніфест як вкладення Matroska та поле OpusTags відповідно, і саме це перевіряє власний верифікатор Lolly (і CLI). (`ico`, `eps`, `emf`, `dxf`, `bmp`, `pptx`, формати Office та текстові/дата-формати не мають контейнера C2PA.)
- **Увімкнено за замовчуванням.** Картка **C2PA Credentials** на панелі експорту попередньо обрана майже для кожного інструмента - зніміть позначку, щоб пропустити облікові дані для окремого експорту (або передайте `c2pa=off` у посиланні для спільного доступу). Інструмент може повністю відмовитись від цього у своєму маніфесті.
- **Що записується.** Інструмент і застосунок, що створили файл, час підписання, поверхня експорту (сімейство браузерного рушія + сімейство ОС - навмисно грубо, ніколи не відбиток) і - лише коли увімкнено *Profile → Use my details* - ваше ім'я та email як автора роботи.
- **Що бачать отримувачі.** Інструменти перегляду облікових даних вмісту (застосунки Adobe, `c2patool`, contentcredentials.org/verify) прочитають маніфест і покажуть заяву. Оскільки Lolly підписує ключем, згенерованим **на вашому пристрої** - а не сертифікатом зі списку довіри - переглядачі повідомляють про неї як про *непідтверджені* облікові дані. Структура та стійкість до підробки - справжні; особа підписувача просто не підтверджена жодним органом. Щоб покращити це, можна зареєструвати **підтверджену особу** (Profile → Content Credentials): короткостроковий сертифікат від Lolly CA прив'язує ваш email до ваших експортів, тоді як ключ підписування все одно ніколи не покидає ваш пристрій - див. [Content Credentials Identity](/info/content-credentials-identity.html).
- **Перевірка файлу.** Lolly також перевіряє власні облікові дані: перетягніть будь-який файл на [/verify](/verify) (або запустіть `lolly validate <file>` у CLI), щоб отримати звіт на пристрої - головним чином про те, чи справді файл створено в Lolly і чи не змінено його відтоді. Веб-перегляд Verify виходить далеко за межі облікових даних: він позначає **контент, згенерований ШІ**, виявляє **Lolly Imprint**, перевіряє підписи **SEAL** і (за бажанням) сторонні піксельні водяні знаки та показує **приховані дані** - усе на пристрої, нічого не завантажується. Див. [Content Credentials Identity → Beyond the credential](/info/content-credentials-identity.html#beyond-the-credential-what-else-verify-shows).
- **Приватність.** Усе відбувається на вашому пристрої: ключ підписування створюється для експорту і ніколи не покидає браузер, нічого не завантажується, а заява містить лише те, що вже несуть метадані походження. Утиліти приватності (перетворення на пристрої *ваших власних* файлів) ніколи не додають облікових даних, а *Strip Hidden Data* видалить маніфест C2PA так само, як будь-які інші вбудовані метадані.
- **Взаємодії.** Для PDF Content Credentials і **захист паролем** (будь-який із рівнів - див. вище) взаємовиключні (зашифрований PDF не може отримати вкладення облікових даних). Обліковий запис додається як завершальний крок над готовими байтами - після проставлення DPI/EXIF/кольорового профілю, метаданих PDF/X і міток друку.

## На телефоні

Елементи керування експортом розташовані за плаваючою кнопкою **Render**, яка відкриває аркуш **Export** - ті самі формати, розмір, копіювання, завантаження та спільний доступ, підлаштовані під сенсорне керування.

## Довідник форматів

Кожен ідентифікатор, який може вивести хост, згрупований. Це також значення параметра URL `format=` і прапорця CLI `--export=` - див. [URL Mode](/info/url-mode.html) і [CLI](/info/cli.html). Інструмент пропонує лише підмножину, заявлену його автором, тому список вибору завжди коротший за цей перелік.

| Тип | Ідентифікатори |
|---|---|
| Растр | `png` · `jpg`/`jpeg` · `webp` · `avif` · `tiff` (RGB TIFF) · `cmyk-tiff` (Print TIFF) · `bmp` · `ico` |
| Вектор | `svg` · `svgz` (gzipped SVG) · `emf` · `wmf` · `eps` · `eps-cmyk` (EPS CMYK) · `dxf` (файл для різання) |
| Сторінка та документ | `pdf` · `pdf-cmyk` (Print PDF) · `pptx` (PowerPoint) · `scorm` (пакет курсу SCORM, zip) · `penpot` (файл дизайну Penpot) · `docx` (Word) · `odt` (OpenDocument Text) |
| Рух | `gif` · `apng` (Animated PNG) · `webp-anim` (Animated WebP) · `svg-anim` (Animated SVG) · `webm` · `mp4` |
| Аудіо | `wav` · `mp3` · `m4a` · `opus` |
| Текст і дані | `html` · `md` · `txt` · `json` · `csv` · `ics` · `vcf` · `css` · `scss` · `gpl` (палітра GIMP) |
| Пакет | `zip` |

Ще кілька ідентифікаторів походять з **власного хука експорту інструмента**, а не з спільного шляху рендерингу: `ase` (Adobe Swatch Exchange, з Palette Lab), `exr` і `hdr` (растри з високим динамічним діапазоном у Darkroom) та `ttf` / `otf` / `woff` (Font Convert). Вони обираються так само - список вибору, `format=`, `--export=` - просто байти будує сам інструмент. Font Convert - єдиний виняток: він перетворює файл шрифту, який надаєте *ви самі*, тому для звичайного URL немає що рендерити.
