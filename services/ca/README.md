# lolly-ca

Lives at `services/ca/` in the [`lolly`](https://github.com/lolly-tools/lolly) repository.
Before 2026-09-11 this was its own repository, `lolly-ca`, mounted as a git submodule; its
history came across intact and is archived at the old URL with a redirect notice.

Builds **within the repository** - depends on sibling workspace packages
(`@lolly/engine`) / relative paths that only exist in that layout.

Hosted deployments must configure `CA_RATE_LIMIT_REST_URL` and
`CA_RATE_LIMIT_REST_TOKEN` (or their shared `LOLLY_RATE_LIMIT_*` names) for a
Redis-compatible HTTPS REST endpoint. Authentication, enrolment, and email
dispatch then share cross-instance fixed-window limits; limiter outages fail
closed with 503 and exceeded budgets return 429. Raw IP and email values are
hashed locally before bucket keys leave the process. In-memory limiting is for
local development only; `CA_ALLOW_IN_MEMORY_RATE_LIMIT=1` is an explicit,
weaker escape hatch.

Forwarded client addresses are ignored unless `CA_TRUST_PROXY=1` and the direct
peer is an exact member of `CA_TRUSTED_PROXIES`. Keep both unset when the
platform already exposes the real peer address or the proxy boundary is not
known.


## OIDC verification policy

Google and SUSE use authorization code with PKCE S256. The CA requires HTTPS
endpoints, exact agreement between configured and discovered issuer, and a signed
RS256 ID token with issuer, subject, audience, expiry, issue time and the request
nonce. The client must be the only audience; a supplied `azp` must name that client.
Discovery and keys are cached for ten minutes, with an early key refresh when a
new signing key appears. Requests reject redirects, time out after ten seconds,
and accept at most one MiB of response data. JWT signatures and standard claims
are verified by `jose`.

`GOOGLE_TOKEN_AUTH_METHOD` and `SUSE_TOKEN_AUTH_METHOD` accept
`client_secret_post` (the existing default) or `client_secret_basic`. Configure
the method registered at the provider. Unsupported advertised methods are refused.

Email must carry boolean `email_verified: true`. For a managed SUSE issuer whose
directory guarantees ownership but omits the claim, an operator can explicitly set
`SUSE_EMAIL_VERIFICATION=trusted`. This exception applies only to the configured
SUSE issuer and an absent claim; false, strings and other malformed values remain
refused. Google has no such exception. GitHub certificate enrollment requires a
verified email record from its email API and does not fall back to public profile
email. Review these settings before upgrading an issuer that omitted verification.

Run `node --test tests/ca-oidc.test.ts tests/ca-service.test.ts` for protocol and
enrollment regressions. The container installs the verifier from the workspace
lockfile. The Vercel handler is regenerated by `pnpm run build:ca-fn`.

## Deploy and maintain hosted identity

1. Install from the repository root with `pnpm install --frozen-lockfile`, or build
   `deploy/docker/ca.Dockerfile` from that root. The CA runtime now includes `jose`;
   copying only the service source without its installed dependency is insufficient.
   Rebuild the serverless artifact with `pnpm run build:ca-fn` when deploying that adapter.
2. Register a separate provider client for certificate identity. For each enabled
   provider, allow exactly `https://<ca-host>/api/ca/callback/google`,
   `/api/ca/callback/suse` or `/api/ca/callback/github` as appropriate. Preserve the
   external HTTPS scheme and host through the reviewed proxy configuration. Do not
   reuse Work's callback path or assume its session supplies CA identity.
3. Supply the provider credentials and the registered token authentication method
   through the deployment secret manager. Set `CA_ALLOWED_ORIGINS` to the exact
   approved shell origins. Supply the service signing secret and durable admission
   configuration described in `.env.example`, and select the issuer mode explicitly.
   Follow managed intermediate configuration below for Vault deployments; only legacy
   root mode accepts a root private key. Keep `CA_DEV_FAKE_PROVIDER` unset in production.
   Authority custody and backup are independent of IdP client-secret rotation.
4. Before rollout, verify the provider's ID token has the supported audience,
   issuer, algorithm and boolean email verification claim. Use the explicit managed
   SUSE exception only after confirming that the directory controls those addresses.
   Test verified enrollment, unverified refusal, wrong origin and a newly rotated
   IdP signing key through the candidate ingress. Health only reports liveness.
5. Pin the qualified image or generated function together with its environment
   configuration. Retain the previous release and secret versions. Rotate client
   secrets with provider-supported overlap, update every replica, and test fresh
   enrollment. Keep old JWKS public keys available while their tokens remain valid;
   a new `kid` refreshes early, while reuse of a `kid` may need the ten-minute cache
   to expire. Discovery also caches for ten minutes.

This release makes missing SUSE email verification fail by default and removes
GitHub's unverified public-email fallback. Review that compatibility change before
an upgrade. A rollback to older code loses these checks, so retain the verification
policy or restrict enrollment while resolving a provider mismatch. Existing issued
certificates keep their original lifetime; Work offboarding and IdP logout do not
retroactively invalidate Content Credentials certificates. Set issuance lifetimes
under the organisation's certificate policy.

For organisation SSO and SCIM, deploy Work separately and follow its
[enterprise identity runbook](https://github.com/lolly-tools/lolly-work/blob/main/docs/enterprise-identity.md).

## Managed intermediate enrollment

The service supports `CA_ISSUER_MODE=vault-pki` with protocol version 2. It delegates
issuance to Vault PKI, validates the returned chain and policy, requires fresh signed
CRL status, and supports device-authorized certificate revocation. Managed mode does
not load a root private key and has no local signing fallback. Missing configuration,
unavailable shared admission or provider failures prevent enrollment. Provider edition,
managed-key custody, TLS, network enforcement and operational policy still require
qualification with the candidate deployment.

Legacy deployments keep the existing root issuer when no Vault settings are present;
set `CA_ISSUER_MODE=legacy-root` explicitly during migration. Version 1 clients work
only with that legacy mode. A deployment with any `CA_VAULT_*` setting must select
managed mode. New clients require a version 2-capable service and send an empty-subject, empty-attribute P-256
PKCS#10 CSR and a separate signature over the token and CSR digest. Managed enrollment
consumes a random authentication identifier atomically before calling the signing API.
The shared store retains only a keyed identifier and request digest for at most ten
minutes. A repeated or uncertain request requires fresh authentication; the service
never retries an issuance whose provider outcome is unknown and stores no certificate
response cache or identity inventory.

Configure the following through the deployment's reviewed configuration and workload
secret delivery. The repository supplies no root, endpoint, domain, OID or key reference.

| Setting | Required value |
| --- | --- |
| `CA_VAULT_ADDR`, `CA_VAULT_MOUNT` | Approved HTTPS origin and PKI mount |
| `CA_VAULT_AUTH=agent` | `CA_VAULT_TOKEN_FILE`, an absolute projected token-file path |
| `CA_VAULT_AUTH=kubernetes` | Exact auth mount, role and projected audience-bound JWT file |
| `CA_VAULT_NAMESPACE` | Optional reviewed Vault namespace |
| `CA_ENROLLMENT_TRUST_JSON` | Public version 1 trust bundle described below |
| `CA_VAULT_ROLES_JSON` | Provider-to-role, PKI issuer key ID and approved managed-key reference |
| `CA_VAULT_REVOCATION_TOKEN_FILE` | Separate short-lived revocation workload credential, when enabled |
| `CA_RATE_LIMIT_REST_URL`, `CA_RATE_LIMIT_REST_TOKEN` | Shared HTTPS admission store |

Workload tokens must have a positive lifetime of at most fifteen minutes and cannot
carry the `root` policy. Vault Agent credentials are read afresh from the projected
file and checked with `auth/token/lookup-self`; Kubernetes login reauthenticates before
its short-lived credential expires. Grant self lookup, reads of only the approved role
and issuer metadata, and update access to only the approved sign role. Revocation uses
its own restricted credential and accepts certificate bytes only after a device-bound,
single-use challenge verifies. No device private key enters the service or Vault API.
Use a separate revocation workload and ingress route when pod-level separation is
required; mounting both credentials in one pod does not provide that separation.

The public trust bundle has `version: 1`, nonempty certificate PEM arrays in `roots`,
`issuers` entries containing immutable `id` and `certificate`, and a `providers` map.
Each provider entry fixes `issuer`, `policyOid` and exact lowercase email `domains`.
Specify `defaultLifetimeSeconds: 86400`, `maxLifetimeSeconds: 604800`, an approved
`crlMaxAgeSeconds` no longer than that maximum, and explicit boolean `unifiedCrl`.
Shorter defaults or ceilings are supported. Empty policy values fail closed. The private
role map fixes `role`, `issuerKeyId` and `managedKeyId` per approved provider. The PKI
key ID binds metadata to the provisioned issuer; the managed-key reference records the
approved external key. These identifiers and ordinary certificate signatures do not,
by themselves, prove HSM custody. Qualify provider-side key operations and denied export.

The adapter checks the role and issuer metadata before issuance: an immutable issuer,
P-256, only digital signature and email-protection usage, exact policy/domain mapping,
no arbitrary name or alternate-name authority, CSR identity/extensions ignored, no
certificate storage and no lease generation. Pin the role's issuer, disable TLS/client
and code-signing flags, and set its maximum TTL within the seven-day ceiling. Keep
`use_csr_common_name=false`, `use_csr_sans=false`, `no_store=true` and
`generate_lease=false`. Additional unsupported role permissions or changed issuer
metadata prevent issuance. Every returned certificate is independently checked against
the pinned root/intermediate, identity, public key, validity and constraints.

Distribute the same **public** trust JSON independently to each shell. Set
`VITE_CA_ENROLLMENT_TRUST_JSON` at web/native frontend compilation; the reusable release
workflow accepts it as a public input and binds the resulting bytes in its signed
artifact receipt. An enrollment response or `/root.pem` is never an automatic trust
update. Node shells read `LOLLY_ENROLLMENT_TRUST=/path/public-trust.json` and
`LOLLY_ENROLLMENT_CRLS` as a JSON map from configured issuer ID to local DER/PEM CRL
file. Operators refresh those status files. Renewal requires a new hosted sign-in;
existing certificates cannot authorize renewal.

Web/native clients retrieve only the configured issuer's full CRL through
`GET /api/ca/issuer/<id>/crl`. The bounded gateway verifies signature, issuer and
freshness before publication. Signing and file verification also check those bytes
locally. Missing, stale, tampered, delta or indirect status prevents managed trust;
exports use an anonymous credential when their identity cannot be checked. Cached
status remains usable only within the approved age and `nextUpdate`. Revocation may
therefore take that freshness interval to reach a previously offline client. Configure
full unified CRLs for multi-cluster revocation, and qualify Vault's publication delay.
OCSP is not used by this implementation; other Content Credentials verifiers need
separate CRL/OCSP and historical-signature qualification. Intermediate withdrawal
requires an approved trust-bundle update. There is no automatic directory offboarding
or identity-to-serial inventory.

Run `node --test tests/ca-managed.test.ts tests/ca-deployment.test.ts` for protocol,
OpenSSL cross-checks, adapter, policy, replay, revocation and deployment regressions.
The native shells share certificate validators; their endpoint/window flow and
WebCrypto persistence still need qualification on each candidate platform.
Set `LOLLY_CA_BROWSER_TESTS=1` to exercise a disposable real Chrome profile and
IndexedDB identity persistence. Rebuild the generated CA function with
`pnpm run build:ca-fn`. The image copies only the certificate dependency closure and
checks the real handler import. The charts require managed workload values and explicit
egress peers/ports, omit legacy authority secrets, and project a ten-minute Kubernetes
JWT with the chosen audience. Platform-level TLS, Vault/HSM, admission-store, retention,
backup and verifier acceptance evidence remains a deployment prerequisite.

## Managed intermediate operational design

The managed chain is an offline organisation root, one constrained intermediate,
then a device leaf. Root custody and recovery stay outside the hosted service.
The intermediate uses a non-exportable P-256 signing key in an approved HSM or
KMS, accessed through Vault Enterprise Managed Keys. The device generates its
own key and signs Content Credentials locally. Hosted authentication and
enrollment remain available, while the service receives no CA or device private
key. [Vault's managed-key design](https://developer.hashicorp.com/vault/tutorials/pki/managed-key-pki)
delegates private-key operations to the external provider. Qualify that provider's
P-256 signing mechanism, key export policy and operational evidence before
asserting hardware custody.

An HSM-backed Vault seal protects Vault's encryption root key. It does not make
an ordinary PKI or Transit key perform each signature in hardware. A software
Transit key that cannot be exported through the API is also a different custody
model. Require a configured managed signing key and evidence that successful
certificate signatures use that key. See [seal configuration](https://developer.hashicorp.com/vault/docs/configuration/seal)
and [Managed Keys](https://developer.hashicorp.com/vault/api-docs/system/managed-keys).

### Issuance API and enrollment protocol

Prefer Vault PKI so the provider owns certificate issuance and revocation. The
operator generates an intermediate CSR with
`POST /v1/<mount>/intermediate/generate/kms` and its managed-key reference,
obtains an offline root signature, and imports the public chain with
`POST /v1/<mount>/intermediate/set-signed`. The service uses only
`POST /v1/<mount>/sign/<role>` with a device CSR, an approved identity, `ttl` and
`format=pem`. Keep the role's issuer explicit; exclude issuer-override and
privileged signing endpoints from its ACL. These APIs and role fields are
defined in the [PKI API](https://developer.hashicorp.com/vault/api-docs/secret/pki).

Version 2 carries a bounded DER CSR signed by the device P-256 key. The service
verifies its signature, curve and exact SPKI equality with the separately signed
proof before calling Vault. The proof binds protocol version, token and CSR SHA-256.
Atomic single-use admission prevents concurrent replicas from issuing twice; a
retry after an uncertain provider response requires fresh hosted authentication.
Renewal also requires fresh authentication. Origin restrictions and shared
admission limits remain in effect.

Identity, organisation, permitted SAN, lifetime and role come from verified
server policy. A CSR cannot choose its own identity or extensions. Set
`use_csr_common_name=false` and `use_csr_sans=false`; request the approved identity
separately. Inspect the issued certificate before returning it, checking SPKI,
SAN, issuer, constraints, policy and lifetime against the request. On an unknown
provider, malformed response or provider outage, fail issuance without a local
signing fallback. Return leaf-first intermediate chains; keep root anchors in
the client's separately managed trust configuration.

If PKI cannot produce the required certificate profile, a separate design can
retain local DER assembly and use a Transit external signer. For a managed P-256
key, `POST /v1/<transit>/sign/<key>/sha2-256` receives the base64 binary SHA-256
of the exact TBSCertificate, `prehashed=true`, an explicit `key_version`, and
`marshaling_algorithm=asn1`. Validate the `vault:v<version>:` envelope and DER
ECDSA signature, verify it against the pinned intermediate SPKI, then encode
the X.509 BIT STRING with zero unused bits. Never hash the digest again or treat
JWS `r||s` as DER. [Transit signing](https://developer.hashicorp.com/vault/api-docs/secret/transit)
provides these parameters, but a general digest-signing permission leaves
certificate policy enforcement in the caller. That broader authority, CSR
creation, revocation and DER assembly need separate review; this is not an
automatic fallback from PKI.

### Constraints and provider assurance

The offline signer must issue an intermediate with critical `CA=true`,
`pathLenConstraint=0`, certificate/CRL signing usage, approved validity and
critical name constraints for the approved RFC822 identity domains. Do not assume
a CSR request makes the offline signer preserve these fields. Configure the
leaf profile for `CA=false`, P-256, digital signature and the Content Credentials
EKU supported by the current verifier (`emailProtection`). Prohibit TLS EKUs,
DNS/IP/URI SANs, arbitrary extensions and additional CAs. If an intermediate
EKU constraint is used, qualify the complete chain with every supported Content
Credentials verifier. Role restrictions supplement certificate constraints.

Allocate policy OIDs under the organisation's registered arc for each supported
assurance class. Managed organisation SSO, consumer verified email and email-link
ownership must have distinct policy values. Select a fixed role per class with
its `policy_identifiers`; the request cannot supply an OID. Managed deployments
can accept only their approved SSO class. A policy OID describes the verified
enrollment policy, not device hardware or legal identity assurance. Keep the
issuer/provider-to-policy mapping versioned and reviewed; unregistered OIDs and
provider classes fail closed.

Client validation must build a leaf-to-pinned-root path and enforce every
signature, validity bound, basic constraint, path length, key usage, name
constraint, permitted policy and unsupported critical extension. Checking just
the leaf or a claimed provider label is insufficient. The hosted response is
not a trust anchor. Refuse chains containing another intermediate under the
path-length-zero issuer, an out-of-domain identity, a substituted root or a leaf
that outlives its issuer.

### Workload access and operational boundaries

Use short-lived workload authentication tied to the exact service deployment.
On Kubernetes, bind a Vault auth role to the exact service account, namespace
and token audience; renew a short-lived Vault token within a bounded maximum
lifetime. [Vault Kubernetes auth](https://developer.hashicorp.com/vault/docs/auth/kubernetes)
supports these bindings. For another platform, qualify an equivalent workload
identity mechanism before rollout. Never distribute an operator or root token
to the service, CI, a browser or a general build container.

Grant the enrollment workload update access only to its approved sign roles and
read access only to the public issuer material it needs. A deployment restricted
to managed SSO cannot call a consumer or email-link role. A separate restricted
revocation workload receives revoke authority. Neither can manage keys, change
roles, select arbitrary issuers, sign intermediates, import keys or administer
Vault. Operators control key creation, role/issuer updates, trust distribution,
CRLs and recovery through reviewed changes. Permit network access only to the
approved Vault endpoint and required IdP/rate-limit dependencies; bound response
sizes, timeouts and retries, verify TLS and refuse redirects. Monitor aggregate
failure counts, issuer expiry and revocation publication without identities or
certificate bytes in application logs.

### Lifetime, revocation and retained data

Use a 24-hour leaf default and seven-day ceiling, further capped by the
remaining intermediate lifetime. Offline use and renewal prompts must be tested
before adopting those limits. Renew with fresh identity verification, preferably
a fresh device key. Configure revocation distribution and a revocation freshness
budget, then qualify how each Content Credentials verifier handles unavailable
or stale status and timestamped historical signatures. Expiry, IdP logout and
Work offboarding are different events; no automatic directory-driven revocation is implemented.

Keep any application issuance records minimal: a keyed HMAC of issuer plus serial,
issuer identifier, expiry, policy class and status. Exclude email, IdP subject,
IP, tokens, CSR and certificate bytes. Restrict the records' HMAC key and access,
set expiry-based retention, and avoid exposing it as a public lookup API. Such a
record set cannot find every certificate for a departing person. Automatic
offboarding needs a separately approved identity-to-serial mapping or a managed
certificate inventory with an explicit retention policy.

Propose PKI `no_store=true` and `generate_lease=false` for issuance. This removes
ordinary issuance storage and serial-only revocation. An authorised revocation
service must accept the issued certificate plus authenticated authority or a
device-signed revocation challenge, then call Vault's certificate-based revoke
API. Keep device private keys on the device; do not use an API that asks the
client to upload one. Vault BYOC revocation can still retain the certificate DER,
including its identity SAN, as shown by the
[vendor revocation implementation](https://github.com/hashicorp/vault/blob/main/builtin/logical/pki/path_revoke.go).
Therefore this design cannot promise that Vault stores no personal data. Review
revoked-certificate storage, backups, tidy safety windows and deletion behavior
for the exact qualified Vault version before enabling revocation.

Keep Vault private. Publish only approved issuer certificates and CRL/OCSP
surfaces through a restricted gateway; block individual-certificate retrieval
and enumeration routes. Treat revocation serials as potentially linkable.
[Vault audit devices](https://developer.hashicorp.com/vault/docs/audit) normally
HMAC most string fields, with exceptions. Inspect real enrollment, errors and
revocation events and configure redaction, retention and access for all audit
sinks, gateways and traces. HMAC defaults are not evidence that every field is
private. Require approval of the resulting data inventory and retention policy
before rollout.

### Rollover, acceptance and implementation work

Use a new managed key and offline-signed intermediate for each rollover. Pin an
explicit issuer per role and switch only after clients accept the new public
chain. Retain the old intermediate and its revocation publication through the
last issued leaf's validity and the approved historical-validation window.
During overlap, issue from only the selected new issuer while validating both
approved chains. Root replacement needs a separate trust-anchor distribution
plan. A provider failure pauses enrollment; rollback must retain external
custody and cannot restore a root private key to the service.

Provider qualification must cover workload authentication, managed signing custody,
trust-bundle distribution, renewal behavior, revocation publication and privacy
retention. The local protocol and adapter suites do not replace that evidence.
Actual Vault edition/version, HSM/KMS model, endpoint, key references, root,
identity domains, OIDs, roles, revocation availability and retention remain
deployment inputs requiring a reviewed configuration change.

Acceptance requires the following evidence from disposable test authorities,
then the candidate provider and every supported shell:

1. Correct authentication and CSR proof issue a conforming leaf; replay,
   cross-key proof, identity substitution, wrong origin, unknown assurance,
   excessive lifetime and forbidden extensions are refused. Parallel enrollment
   and retry tests produce at most one issued result per token.
2. Verify constraints and policies along the complete path. Reject another CA,
   an out-of-domain SAN, a different root, an expired issuer and a missing policy.
   Exercise both normal validation and independently changed certificate bytes.
3. Check that no issuer key enters service configuration, memory exports, build
   artifacts or logs. Confirm provider-side signing evidence and denied key
   export/admin operations. Test revoked workload credentials, outages, audit
   sink failure and bounded retries without local signing.
4. Exercise issuance, authorized/unauthorized revocation, CRL/OCSP refresh,
   expiry, retention cleanup and restored backups. Inspect persistent provider
   records and audit output for identity data, and verify private lookup routes
   stay unreachable through the public gateway.
5. Rehearse intermediate overlap, trust update, issuer switch and rollback.
   Demonstrate old Content Credentials remain verifiable according to the
   approved timestamp/revocation policy, while new enrollments use the selected
   issuer. Security and service owners approve the evidence before a small
   enrollment cohort is enabled; expand only after renewal and monitoring pass.
